Pre-training vs Post-training

p9~14 · 1차시

Pre-training (사전학습)

방대한 텍스트 데이터를 이용한 Self-supervised learning을 통해 언어 패턴, 지식 등을 배운다.

  • 학습 목표: 다음 단어 예측 (Next Token Prediction)
  • 예시: "내일은 비가 ___" → "온다"의 확률을 가장 높게 만들도록 파라미터 업데이트
goes, to, make, tasty, tea, [END] ↑ ↑ ↑ ↑ ↑ Decoder (Transformer, LSTM, ...) ↑ ↑ ↑ ↑ ↑ Iroh, goes, to, make, tasty, tea // Next Token Prediction
원본 슬라이드 p.9

Post-training (사후학습)

유저의 의도를 파악하고 원하는 답변을 모델이 응답하도록 사후 학습을 진행한다.

대표 기법
  • Instruction-tuning
  • RLHF (Reinforcement Learning from Human Feedback)
  • DPO (Direct Preference Optimization)
  • RLVR (Reinforcement Learning with Verifiable Reward)

Pre-training만 거친 모델의 한계

PROMPT: "달 착륙을 6살 어린이에게 몇 문장으로 설명해줘."

Pre-training만 (GPT-3)Post-training 거친 모델 (Human 답변형)
질문을 잇는 비슷한 질문들을 계속 생성할 뿐, 실제 답변을 하지 않음 (예: "중력 이론을 6살 어린이에게 설명해줘." 등 반복) 거대한 로켓이 지구에서 우주비행사들을 태우고 달로 날아갔다는 식으로 실제 요청에 맞는 답변을 생성

→ 사전학습 후 거대 언어모델은 유저의 의도와 일치하지 않음. 이를 해결하기 위해 파인튜닝(Post-training)을 진행.

Instruction-tuning

p15~28 · 1차시

Instruction-tuning이란?

언어모델이 사람이 내린 지시문(instruction)을 따르도록 학습하는 단계. 정답 레이블이 요구되며, 다양한 태스크를 풀 수 있도록 적응하는 것에 중점을 둠.

Step 1: PretrainStep 2: Finetune (Instruction-tuning)
목표일반적인 언어 지식 학습 (Lots of text)많은 태스크에 적응 (Not many labels per task)
입력형태… the movie was …다양한 태스크의 (지시문, 응답) 쌍

즉, 다양한 태스크에서 (지시문, 응답) 쌍을 모아서 언어모델을 파인튜닝한다. 학습에 사용되지 않은 새로운 태스크에서도 평가를 진행한다 (Zero-shot generalization).

(참고) 파인튜닝(Fine-tuning) 이란? — 더 넓은 개념

이미 사전 학습된 기존 모델에 특정 작업이나 도메인에 맞게 추가로 학습시키는 과정. Instruction-tuning은 이 파인튜닝의 한 종류다.

RLHF (Reinforcement Learning from Human Feedback)

p29~50 · 1차시

Instruction-tuning의 한계

"정답 데이터를 수집하는 것이 비싸다"는 명확한 한계 말고도 다른 문제들이 있다:

  • 문제 1: 개방형/창의적 생성과 같은 태스크에는 정답이 존재하지 않는다 (예: "개와 개가 기르는 메뚜기에 대한 이야기를 만들어줘")
  • 문제 2: 언어 모델링은 모든 토큰 레벨의 오류를 동일하게 취급하지만, 어떤 오류는 다른 오류보다 심하게 작용한다
  • 문제 3: 사람이 만든 답변(정답 레이블)이 최적이 아닐 수 있다

→ Instruction-tuning을 하더라도, 언어모델의 목표(LM objective)와 "인간의 선호를 만족시키는 것" 사이에는 여전히 불일치가 존재한다.

인간의 선호도(Human Preference)란?

  • 단답형: "상대성 이론을 발표한 과학자는 누구인가?" → "알베르트 아인슈타인" (정답 명확)
  • 주관식: "아인슈타인이 오늘날 살아있다면, 현대 과학기술에 어떤 기여를 했을까?" (정답 없음 — 응답의 스타일·품질에 대한 선호가 갈림)

주관식 질문엔 "정답"이 없다 — 실제 4개 LLM 비교

같은 주관식 질문("아인슈타인이 오늘날 살아있다면?")에 대해 서로 다른 모델이 서로 다른 스타일·내용으로 답한다 — 어느 쪽이 "더 나은 답"인지는 사람의 선호(preference)에 달려 있다.

Claude Sonnet 4Gemini 2.5 Flash
"양자컴퓨팅과 양자정보학 분야에서 혁신적 기여를 했을 것" — 양자암호학·양자통신, 중력파 검출, 블랙홀 물리학 연구 참여 가능성 등을 구체적으로 서술"통일장 이론을 완성하고 양자역학과 상대성 이론을 통합하는 데 기여했을 것" — 네 가지 기본 힘을 하나로 통합하는 '모든 것의 이론' 완성에 주력했을 것으로 서술

Copilot·GPT-5 등 다른 모델들도 각기 다른 강조점(GPS·상대성이론의 실용적 영향 vs 다중우주·암흑물질 등)으로 답변 — 정답이 없는 질문이기에 리워드 모델도 결국 "사람이 어떤 스타일을 선호하는가"를 학습하게 됨

보상을 점수로 상상하기

언어모델을 학습한다고 가정했을 때 (e.g., 요약 태스크), 어떤 지시문 x와 언어모델의 응답 y가 있을 때, 해당 응답에 대한 인간이 준 보상(human reward)을 얻을 수 있다고 상상해보자:

R(x, y) ∈ ℝ, 점수가 높을수록 좋음

언어모델의 응답 중 기대 보상(expected reward)을 최대화 하는 것을 목표로 한다:

E{ŷ~pθ(y|x)} [R(x, ŷ)]

예: 뉴스 요약 태스크에서 같은 원문 x에 대한 두 요약 y₁, y₂ 중 사람이 y₁에 8.0점, y₂에 1.2점을 준다면 R(x,y₁)=8.0, R(x,y₂)=1.2 — 이렇게 점수가 매겨진다고 "상상"한 뒤, 이 기대 보상을 최대화하도록 언어모델을 학습시키는 것이 RLHF의 목표

Intuition: Human-in-the-loop ML

사람이 매긴 Labeled Data → 모델 학습(Training Model) → 헷갈리는 데이터 선별(Selecting Confusing Data) → 다시 사람이 라벨링, 의 순환 구조.

인간의 선호도를 어떻게 모델링 할 것인가?

  • 문제: 인간의 판단은 일관성이 떨어지고, 기준이 어긋날 수 있다
  • 해결 방법: 직접 점수를 매기지 않고, 응답을 비교(pairwise comparison)하는 방식을 활용
  • 해당 비교 데이터로 리워드 모델(Reward Model)을 학습시키게 된다

예: y₁, y₃, y₂ 세 응답 중 사람이 보기엔 y₂ > y₁ > y₃ → 비교 결과가 리워드 모델 학습의 데이터가 됨

Bradley-Terry 비교 모델 손실함수
JRM(φ) = −E(x,yw,yl)~D [log σ(RMφ(x,yw) − RMφ(x,yl))]

yw = winning sample(더 선호되는 응답), yl = losing sample. yw가 yl보다 높은 점수를 받도록 학습.

구체 예 (샌프란시스코 지진 요약): Human preference y₂ > y₁ > y₃ → Pairwise label 3쌍 (y₂>y₁, y₁>y₃, y₂>y₃)으로 분해 → Loss = −Σ log σ(RM(x,y₂)−RM(x,y₁)) − log σ(RM(x,y₁)−RM(x,y₃)) − log σ(RM(x,y₂)−RM(x,y₃)) 를 최소화하도록 리워드 모델 학습

어떻게 최적화 할 것인가? — 강화학습

  • 강화학습(RL) 분야는 오랫동안 이론적/관련된 문제들을 연구해 왔음
  • 2013년 전후로, RL이 딥러닝과 게임 플레이에 적용되면서 다시 급증 (예: AlphaGo)
  • 언어모델에 RL을 적용하려는 관심은 비교적 최근인 2019년부터 이루어짐 [Ziegler et al. 2019, Stiennon et al. 2020, Ouyang et al. 2022]
  • 언어모델에 적용될 수 있는 RL 알고리즘: PPO (Proximal Policy Optimization) [Schulman et al., 2017]

RLHF는 pre-training·instruction-tuning보다 더 나은 성능 향상 제공

모델 크기(1.3B~12.9B)에 관계없이 human feedback 기반 정책 pRL(y|x)이 Reference summaries 대비 선호율에서 가장 높음:

pRL > pIFT > pPT (RL 학습 > Instruction fine-tuned > Pretrain only)

📌 1차시 강의 정리

  • Pre-training (사전학습): 인터넷 텍스트 등 대규모 비라벨 데이터로 언어의 구조와 지식을 학습
  • Post-training (사후학습): 사전학습된 모델을 사람의 의도에 맞게 조정하는 단계 — 대표 방식: Instruction-tuning(지시학습), RLHF(인간 피드백 기반 강화학습)
  • Instruction-tuning: Fine-tuning의 한 종류로, 사람이 작성한 지시문(instruction)-응답(output) 쌍으로 지도학습(Supervised) → 모델의 명확한 태스크 수행 능력 습득. 데이터셋 예시: Super-NaturalInstructions, Alpaca, Flan-T5 등
  • RLHF란? 인간의 피드백(Human Feedback)을 통해 언어모델이 '사람이 선호하는 답변'을 학습하는 방법. 한계점: Reward Hacking 발생, Hallucination(환각) 발생
  • RLHF 이후의 진화: 1) DPO — RL(강화학습)을 제거, 사람의 선호 데이터를 직접 확률 최적화 / 2) RLVR — 인간 피드백 대신 정답 검증이 가능한 문제에서 자동으로 보상을 계산하는 방식

Retrieval-augmented LM 이란?

추론 시 외부 데이터 저장소를 불러와 활용하는 언어모델.

Typical LM (Training/Test 동일)Retrieval-based LM (Test time)
동작"The capital city of Ontario is ___" → LM만으로 예측Datastore를 조회하여 "The capital city of Ontario is ___" 예측에 활용
구성요소

원본 슬라이드 p.71

Datastore / Query / Index / Retrieval

  • Datastore: 가공되지 않은 대규모 텍스트 코퍼스. 최소 수십억~수조 단위 토큰. 라벨링된 데이터셋도, 지식베이스(구조화 데이터)도 아님
  • Query(쿼리): 검색 질의/Retrieval input. 언어모델의 질의(input)와 같아야 하는 것은 아님
  • Index(인덱스): 문서·단락 같은 검색 가능한 항목들을 체계적으로 정리하여 더 쉽게 찾을 수 있도록 함
  • Retrieval(검색): Datastore의 수많은 정보 중, 주어진 쿼리와 가장 관련성이 높은 정보를 찾아내는 과정

Retrieval-augmented Generation (RAG)

사용자의 질문에 답하기 위해, datastore에서 관련 정보를 검색(Retrieval)해와서, 이를 언어모델이 생성(Generation) 단계에 함께 활용하는 방법.

예: "Who is the president of the US?" → Retriever가 Wikipedia에서 "Joe Biden is the 46th and current president..." 문서를 검색(Memory: 새 도메인·뉴스로 지식 확장·갱신 가능) → Generator가 이를 근거로 "Joe Biden" 답변 생성(근거 문서를 함께 제시해 Interpretability 확보)

Information Retrieval(정보검색) 이란?

  • 정보검색(IR): 사용자의 질의(Query)에 맞는 정보를 대규모 데이터에서 찾아 제공하는 과정
  • 주요 목표는 사용자의 검색 질의(Query)에 가장 관련성이 높은 정보를 제공하는 것
  • 예: "녹차의 효능?" 질문 → IR이 관련 문서를 찾아 제공
IR의 활용 사례
웹 서치 (구글, 네이버) 이커머스 (아마존, 쿠팡) 추천 시스템 (OTT) RAG

Retriever 종류: Sparse vs Dense

방식전통적 IR 기법. 쿼리-문서 간 정확한 용어 일치에 기반쿼리와 문서를 표현하기 위해 dense vector(embeddings)를 활용, 의미에 기반

TF-IDF (Term Frequency-Inverse Document Frequency)

문서 내 특정 단어의 중요도를 나타내는 가중치 방식.

wx,y = tfx,y × log(N / dfx)

TF = 문서 안에서 자주 등장하는 단어는 중요 / IDF = 너무 많은 문서에 등장하는 단어는 덜 중요 ("this, is, and" 처럼 IDF값이 낮아져 가중치가 0에 가까워짐)

Dense Retriever — 임베딩 모델

임베딩 모델(e.g., BERT)은 단어/문장의 의미를 벡터 공간에 표현할 수 있음.

Bi-encoder

대조 학습(contrastive learning)으로 학습, 쿼리가 긍정 문서와는 가깝게, 부정 문서와는 멀어지게 유도. 두 문장을 따로 인코딩 → 매우 빠름, 대규모 검색에 적합, 정확도는 상대적으로 낮음

예: Query "When was Dubai founded?" + Document 1(정답 문서) → Positive pair로 가깝게, + Document 2("New York is the most populous...", 무관 문서) → Negative pair로 멀게. Loss = −log[ exp(sim(q,p⁺)) / (exp(sim(q,p⁺)) + Σexp(sim(q,pⱼ⁻))) ]를 최소화

Cross-encoder

"query [SEP] document" 형태로 두 텍스트를 하나의 시퀀스로 결합해 self-attention으로 완전히 상호작용 → 정확도 높으나, 모든 쿼리-문서 쌍을 개별 입력해야 하므로 계산 비용이 크고 느림

예: "Query: When was Dubai founded? + Document 1" → Score 0.8 / "...+ Document 2" → Score 0.4 처럼 쿼리-문서 쌍마다 개별적으로 관련도 점수를 계산

Why Retrieval-augmented LM?

  1. 거대언어모델은 모든 지식을 다 파라미터에 저장하지 못한다 — pre-training 데이터에 자주 나타나는 쉬운 정보를 기억하는 경향이 있음 [Kandpal et al. 2022]. 자주 등장하지 않는 정보에 RAG가 큰 효과.
  2. 거대언어모델이 보유한 지식은 금세 시대에 뒤쳐지며, 갱신이 어렵다 — 지식 편집(knowledge editing) 메서드들은 확장성 부족. 반면 저장소(Datastore)는 쉽게 업데이트 가능
  3. 거대언어모델의 답변은 해석과 검증이 어렵다 — RAG는 근거(reference to source) 문서를 함께 제공해 해석 가능성(Interpretability) 확보
  4. 기업 내부 정보와 같은 보안 정보는 언어모델 학습에 활용되지 않음 — 사내 챗봇/기업 시스템에 LLM을 학습시키면 정보 유출 위험이 있으므로, RAG로 학습 없이 내부 지식 활용
원본 슬라이드 p.96 — "BTS 정국의 신곡 제목이 뭐야?" 질문에 ChatGPT(GPT-3.5)는 "2022년 1월 이후 정보를 알지 못해 답할 수 없다"고 답하는 반면, 검색 기반 BingChat은 최신 정보를 찾아 정답을 제시

여러 외부 문서에 흩어진 정보를 통합해야 정답 도출 가능 (예: ChatGPT iOS 출시일 - 여러 문서 정보를 종합해야 "5월 18일과 3월 1일"처럼 정확히 답할 수 있음)외부 문서에 반사실적(counterfactual) 정보가 포함된 경우(예: 조작된 올림픽 발상지 문서), 이를 식별하지 못하면 "제공된 문서에는 사실 오류가 있어 정답은 애매합니다"와 같이 명확히 인지하지 못하는 문제 발생

Information Integration 예: "ChatGPT iOS 앱과 ChatGPT API가 언제 출시되었나요?" — 외부 문서에 "2023년 5월 18일 iOS 앱 출시"와 "3월 1일 API 접근 발표" 두 정보가 분리되어 있으면, 이를 통합해 "5월 18일과 3월 1일"로 답해야 함

Counterfactual Robustness 예: "2004년 올림픽은 어느 도시에서 개최되었나요?" — 외부 문서가 "발상지인 뉴욕으로 돌아왔다"는 반사실적(조작된) 정보를 담고 있다면, RAG는 이를 그대로 따르지 않고 "제공된 문서에는 사실 오류가 있으며, 정답은 아테네입니다"라고 명확히 인지해야 함

원본 슬라이드 p.111

📌 2차시 강의 정리

  • Retrieval-Augmented LM (RAG): 언어모델이 추론 시 외부 데이터 저장소(Datastore)를 불러와 활용하는 구조. 기존 LM은 내부 파라미터에만 의존하지만, RAG는 외부 검색(Retrieval)을 통해 최신·정확한 정보를 반영. 장점: 최신 정보 반영, 근거 기반 답변, 모델 재학습 불필요 / 한계: 검색 품질에 따라 성능 변동, 외부 데이터 관리 필요
  • Information Retrieval(IR): 사용자의 질의(Query)에 맞는 정보를 대규모 데이터에서 검색·제공하는 과정. 목표: Query와 관련성이 가장 높은 정보를 제공하는 것. 구성요소: User → Query → IR System → Retrieved Information
  • Sparse Retriever – TF-IDF: 단어의 중요도를 계산하는 통계 기반 가중치 기법. TF(문서 내 등장 빈도) × IDF(전체 문서에서의 희귀도)
  • Dense Retriever (임베딩 기반 검색): BERT 등 임베딩 모델을 사용해 단어·문장을 의미 공간에 매핑, 단어 간 의미적 유사성(Semantic Similarity)을 활용해 검색 수행. Bi-encoder(각각 인코딩, 빠름) vs Cross-encoder(하나로 결합 입력, 정확)
  • RALM(RAG)의 필요성: 거대 언어모델(LLM)은 모든 지식을 파라미터에 저장할 수 없음 → 학습 데이터에 자주 등장하는 정보만 잘 기억하고, 최신 정보나 희귀한 사실은 누락됨. RAG는 자주 등장하지 않는 정보에 효과적이며, 모델의 지식 공백을 보완
  • RALM의 핵심 과제: 컨텍스트 구성 문제(→ 언어모델의 컨텍스트 길이 확장) / 검색 모델의 성능 의존성(→ 노이즈 포함 학습) / 사전지식과 컨텍스트 간 충돌(→ Grounding 학습 및 답변 회피/거절 학습) / 복잡한 추론 및 사실 오류 대응(→ Information Integration, Counterfactual Robustness)
✅ 확인문제 핵심 포인트
Q. Information Retrieval은 언어모델이 내부 파라미터만 사용하여 정보를 생성하는 방식이다? (O/X)
A. X. IR은 외부 데이터 저장소에서 사용자의 질의에 맞는 정보를 검색하는 과정이다. RAG는 이 IR을 활용해 검색된 문서로 더 정확한 답변을 생성한다.
Q. Bi-encoder와 Cross-encoder 중 "질의와 문서를 별도 인코더로 각각 임베딩하고, 두 벡터의 유사도(Cosine similarity)로 관련성을 계산"하는 구조는?
A. Bi-encoder. 계산량이 적어 대규모 검색에는 빠르게 적용 가능하지만, 상호작용이 적어 정확도는 Cross-encoder(문맥적 상호작용 가능, 느림)보다 낮다.
Q. RALM(Retrieval-Augmented LM)의 특징으로 옳은 것은?
A. 외부 데이터 저장소를 불러와 활용함으로써 최신 정보 기반의 추론이 가능하다. (검색기 없이 답변을 생성하거나, 정보검색 단계를 제거하는 것이 아니라 오히려 추가하여 정확성을 높인다)

Model Context Protocol (MCP)

p149~161 · 3차시

Why MCP?

외부 툴을 활용하는 연구가 급증하면서 회사/모델마다 각기 다른 툴 호출 방식 및 스키마를 개발.

문제점
  • 호환성 부족 (모델마다 다름)
  • 재사용 어려움 (같은 툴도 다른 모델에서는 다시 정의해야 함)

비유: USB Type-A, Type-B, Micro-B, Type-C처럼 제각각 다른 커넥터 → MCP는 이를 표준화된 하나의 규격으로 통합

MCP란?

언어 모델이 외부 툴과 상호작용하기 위한 표준화된 방식으로 정의한 프로토콜. 툴 호출, 응답 전달, 컨텍스트 공유를 하나의 공통 규격으로 처리.

Before MCP: LLM마다 Unique API로 각 도구 연결 (N×M 조합 폭발) → After MCP: Model Context Protocol(MCP)로 통합된 API 하나로 모든 도구 연결

  • LLM Agent란? LLM이 환경을 이해하고 추론·계획·행동을 수행하는 에이전트로, 환경과 상호작용하며 학습함. Controller(계획) - Tool Set(도구 집합) - Environment(플랫폼) - Perceiver(피드백 요약) 프레임워크로 구성
  • Tool Learning: 모방 학습(WebGPT) → 자기지도학습(Toolformer) → 대규모 API 데이터셋(ToolLLM) → 멀티모달·강화학습으로 진화
  • MCP (Model Context Protocol): 모델/툴마다 제각각이던 연결 방식을 표준화한 프로토콜. Data Layer(JSON-RPC 기반 메시지·툴 정의) + Transport Layer(stdio, HTTP 등 실제 통신) 두 계층으로 구성
✅ 확인문제 핵심 포인트
Q. LLM Agent 프레임워크의 4가지 핵심 구성요소와 역할을 올바르게 연결한 것은?
A. Controller - LLM의 핵심 두뇌 역할, 계획 수립 / Tool Set - 서로 다른 기능을 가진 도구들의 집합 / Perceiver - Environment의 실행 결과를 요약 / Environment - 도구들이 실제로 작동하는 플랫폼 제공
Q. Meta의 Toolformer가 자기지도학습(Self-supervised)으로 API 활용 데이터를 생성하는 과정의 올바른 순서는?
A. ㄱ. API 호출 후보 샘플링 → ㄴ. 실제로 실행하여 결과 수집 → ㄷ. 손실 함수(Loss)로 유용성 평가 → ㄹ. 유용한 API 호출만 선별하여 최종 데이터셋 생성
Q. MCP의 두 계층(Layer)과 각각의 역할에 대한 설명으로 옳은 것은?
A. Data Layer는 JSON-RPC 2.0 기반으로 메시지 형식과 Tools/Resources를 정의하고, Transport Layer는 stdio, HTTP 등 실제 데이터 전송을 담당한다.

Environment Representation & Understanding

p163~183 · 4차시

환경(Environment)과 에이전트 활용 예시들

챗봇로보틱스 임바디드(Embodied) 에이전트 게임소프트웨어 개발

에이전트가 환경을 이해하기 위해 필요한 것: 환경에 접근하기 위한 툴(Tool) / 환경의 표현(Representation) / 환경을 이해·탐색하기 위한 방법론들

환경의 표현: 텍스트 (Text)

ALFWorld [Shridhar et al., 2021] — 텍스트 기반 임바디드 에이전트 시뮬레이션 엔진. 물리적 세계에 대한 정보를 언어모델이 텍스트 기반으로 이해하고 명령을 수행할 수 있도록 환경을 표현함.

환경의 표현: 이미지 (Image)

Touchdown [Chen et al., 2018] — Google Street View 기반 내비게이션 및 지시 따르기(Navigation & Instruction Following) 데이터셋. 사용자가 제공한 자연어 지시문에 따라 실제 도시 환경 이미지 내에서 경로 탐색을 수행. 시각적 환경을 텍스트와 연결하여 지시 수행 및 환경 이해를 가능하게 함.

원본 슬라이드 p.175

이미지 기반 표현의 문제점: 좋은 성능을 위해 세부적 이해가 중요 (예: OCR, 복잡한 레이아웃에서의 그라운딩) — 많은 모델이 이런 태스크에서 실패하지만 학습으로 개선 가능

환경의 표현: 텍스트 기반 웹 (Textual Web)

WebArena [Zhou and Xu et al., 2024] — 웹 환경을 텍스트(HTML, DOM, Accessibility Tree)로 표현하여 에이전트가 상호작용 가능. 단순한 스크린샷 이미지 대신 구조화된 웹 표현을 제공, 에이전트가 버튼 클릭·항목 선택·값 입력 같은 작업을 더 정확히 수행할 수 있음.

복잡한 환경은 어떻게 이해할 수 있을까?

모델은 자신이 상호작용하는 환경에 대해 모든 것을 알고 있지 않다. 일부 지식은 LLM 파라미터 안에 포함(예: 코딩 지식, 자주 쓰는 웹사이트 탐색법), 다른 지식은 실시간으로 환경과의 상호작용을 통해 발견해야 함.

접근법핵심 아이디어
환경 특화 프롬프트
(Environment-specific Prompts)		환경에 맞게 수동으로 프롬프트 제작 (예: SteP [Sochi et al. 2023] - 웹 탐색용 프롬프트 템플릿). 문제점: 일반화(Generalization) — 특정 환경에는 잘 작동하지만 새 환경에서는 성능 저하
비지도 프롬프트 유도
(Unsupervised Induction of Prompts)		Agent Workflow Memory [Wang et al. 2024] - 성공적으로 수행된 워크플로우(workflow)를 기억, 이를 기반으로 새로운 프롬프트를 생성해 에이전트에 제공. 프롬프트를 수동 설계하지 않고, 에이전트가 경험을 통해 자동 생성 및 일반화
환경 탐색
(Environment Exploration)		모델이 환경을 탐색할 때 보상(reward)을 부여하여 학습을 유도 → 호기심(curiosity) 기반 보상. 예: Super Mario Bros에서 외적 보상 없이(without rewards) 예측 불가능한 상태공간 진입 시 내적 보상 부여 → 탐색 가속
탐색 기반 궤적 기억
(Exploration-based Trajectory Memorization)		BAGEL [Murtey et al. 2024] - 명령어를 샘플링하여 실행한 뒤, 더 정확한 새로운 명령어로 궤적(trajectory)을 재라벨링. LM-agent가 환경을 탐색하고, LM-labeler가 이를 바탕으로 지시를 다시 정제. 기존 데이터에 의존하지 않고, 탐색과 자기교정(self-correction)을 통해 데이터 생성 → 에이전트의 일반화 성능과 환경 적응력 향상

Reasoning & Planning

p183~191 · 4차시

Controller: Planning 종류

국소적 계획 (Local Planning)전역적 계획 (Global Planning)
한 단계씩(step by step) 계획을 세움. 매 스텝마다 사용할 하나의 툴(tool) 결정. 단순하고 직관적이나, 장기 의존성 문제 발생 가능실행 가능한 전체 계획 경로(planning path)를 한 번에 생성. 여러 개의 툴을 조합하여 시퀀스 형태로 결정. 효율적이나, 복잡한 환경에서는 실패 가능
원본 슬라이드 p.186

Local Planning — ReAct

ReAct [Yao et al. 2023] — 추론(reasoning)과 액션(action)을 결합하여 에이전트가 환경과 상호작용하도록 하는 방식. 단순한 추론/행동 분리를 넘어, 두 과정을 결합해 상황 응형(local) 계획 가능. 다양한 도구 사용 및 웹 탐색, 추론 기반 Q&A 등에서 좋은 성능.

Global Planning — Plan-and-Solve Prompting

[Wang et al. 2023] — 전체 계획을 세운 뒤, 그 계획에 따라 순차적으로 문제를 해결. 단순한 step-by-step 방식보다 체계적이고 안정적인 추론 가능. 복잡한 문제 해결에서 오류 축적 감소.

예: "Let's first understand the problem and devise a plan to solve it. Then, let's carry out the plan..." 형태로 Plan → Solution 순서로 진행

오류 식별과 회복 (Error identification and Recovery)

에이전트는 에러/실수에서 회복할 방법이 필요. Reflexion [Shinn et al. 2023] — 수행한 궤적(trajectory)을 평가 후 잘못된 부분을 Reflection 단계에서 분석하여 재시도하는 방식. 단순히 오류를 탐지하는 것에 그치지 않고, 스스로 반성(reflect) 후 개선된 행동을 수행. 의사결정, 프로그래밍, 추론 등 다양한 태스크에서 성능 회복 및 향상을 보여줌.

계획 재검토 (Revisiting Plans)

CoAct [Hou et al. 2024] — 에이전트가 실행 도중 계획을 재검토(revisit)하고 수정 가능. 두 개의 에이전트(Global Planning Agent + Local Execution Agent)가 서로 협력하여 오류 발생 시 재계획과 피드백을 수행. 초기 계획이 불완전하더라도 실행 과정에서 보완 가능 → 장기 작업(Long-horizon tasks)에서 안정성과 성공률 향상.

  • 연구와 산업 현장에서 빠르게 표준으로 자리잡음

  • 다양한 LLM provider(OpenAI, Anthropic, Google 등)와 통합하여 모델/회사별 API 차이를 공통 인터페이스로 관리 가능

  • LangGraph 기반으로 복잡한 워크플로우를 시각적으로 설계 및 관리 가능
