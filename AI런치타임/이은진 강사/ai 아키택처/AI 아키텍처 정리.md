# AI 아키텍처 정리 (이은진 강사)

> 한 줄 요약
> **서비스를 잘게 쪼개고 자주 배포하는 시대 → "어떻게 나누고 어떻게 연결할지"(설계)가 핵심 →
> AI(에이전트)에게 일을 시키는 시대에도, 큰 그림(아키텍처)을 그리고 정확히 지시하는 능력이 경쟁력이다.**

---

## 1. 전체 관계 매트릭스 — 왜 아키텍처가 중요해졌나

![전체 관계 매트릭스](./전체%20관계%20매트릭스%20다이어%20그램.png)

| 시기 | 개발 프로세스 | 애플리케이션 아키텍처 | 배포 & 패키징 | 인프라 |
|---|---|---|---|---|
| ~1980–1990 | **Waterfall** | **Monolithic** | Physical Server | Datacenter |
| ~2000 | **Agile** | **N-Tier** | Virtual Servers | Hosted |
| ~2010 (현재) | **DevOps** | **Microservices (MSA)** | Containers | Cloud |

**가로(한 줄)로 읽기 = 그 시대의 한 세트**

- **과거**: 폭포수(Waterfall)처럼 순서대로 한 번에 개발 → 거대한 프로그램 하나(Monolithic) → 물리 서버에 올림
- **2000년대**: 요구사항이 자주 바뀜 → 짧게 반복하는 Agile → 프로그램을 계층으로 나눔(N-Tier: UI / 비즈니스 / DB) → 가상 서버
- **현재**: 개발과 운영을 붙인 DevOps → 서비스를 잘게 쪼갠 MSA → 컨테이너(Docker 등)에 담아 → 클라우드에 올림

**세로(한 칸)로 읽기 = 점점 "작게, 자주, 독립적으로"**

- 프로세스: 한 번에 → 짧게 반복 → 계속(지속적 통합·배포)
- 구조: 한 덩어리 → 몇 개의 층 → 수많은 작은 서비스
- 배포 단위·인프라도 같은 방향으로 작아지고 유연해짐

**결론 (그림에서 빨간 박스로 강조된 부분: DevOps + MSA)**

> 잘게 쪼개고 자주 배포할수록, **"어떻게 나누고 어떻게 연결할지"를 정하는 설계가 더 중요해진다.**
> 조각이 많아질수록 조각끼리 엉키면 감당이 안 되기 때문 → 그래서 나오는 해법이 **클린 아키텍처**.

## 2. 그림으로 보는 클린 아키텍처 구조

![클린 아키텍처 구조](./그림으로%20보는%20클린%20아키택처%20구조.png)

**핵심 문장: 바깥이 아무리 변해도, 가장 안쪽(엔티티)은 절대 변하지 않고 중심을 지킨다.**

동심원 4개, 안쪽일수록 **중요하고 안 변하는 것**, 바깥쪽일수록 **자주 바뀌는 세부사항**.

| 층 (안 → 밖) | 이름 | 한마디로 | 설명 | 예시 (은행) |
|---|---|---|---|---|
| 1층 (중심) | **Entities** (엔티티) — Enterprise Rules | 변하지 않는 핵심 규칙 | 화면·DB·프레임워크와 무관한, 업무 자체의 가장 핵심적이고 보편적인 규칙과 데이터 구조. UI가 바뀌든 DB를 통째로 갈든 **한 줄도 수정되지 않아야** 함 | `Account`(계좌)의 잔액 계산식, 유효성 검증 규칙 |
| 2층 | **Use Cases** (유스케이스) — Application Rules | 도메인이 원하는 것 (= 기능) | "이 앱이 무엇을 하는가". 엔티티를 사용해 실제 기능 흐름을 수행 | "A가 B에게 송금한다" (잔액 확인 → 출금 → 입금) |
| 3층 | **Interface Adapters** (인터페이스 어댑터) — Controllers / Presenters / Gateways | 흐름 · 변환기 | 바깥 세계의 데이터 형식 ↔ 안쪽(유스케이스)이 쓰는 형식을 **변환·연결** | HTTP 요청 → 송금 명령으로 변환, 결과 → JSON/화면용으로 변환 |
| 4층 (바깥) | **Frameworks & Drivers** (프레임워크 & 드라이버) — DB / Web / UI / Devices | 갈아 끼울 수 있는 도구 | 프레임워크, UI, DB, 외부 장치 등 **세부 구현** | Django, React, MySQL, 외부 결제 API |

### 의존성 규칙 (가장 중요)

```
Frameworks & Drivers  ──▶  Interface Adapters  ──▶  Use Cases  ──▶  Entities
       (밖)                                                          (안)
```

- **의존성(코드가 다른 코드를 아는 방향)은 항상 바깥 → 안쪽으로만.**
- 안쪽은 바깥쪽의 존재를 **모른다.** (엔티티 코드에 `import django`, SQL 같은 게 있으면 위반)
- 그래서 바깥(DB, UI, 프레임워크)을 바꿔도 안쪽은 영향을 안 받는다 → "중심을 지킨다"의 의미.

## 3. 클린 아키텍처 설계 원칙 6가지

| 원칙 | 뜻 | 얻는 것 |
|---|---|---|
| **의존성 규칙** | 의존 방향은 밖 → 안으로만 | 나머지 5개 원칙이 모두 여기서 나옴 |
| **프레임워크 독립성** | 핵심 로직이 특정 프레임워크에 묶이지 않음 | 프레임워크 교체/업그레이드가 쉬움 (프레임워크는 "도구"일 뿐) |
| **테스트 용이성** | UI·DB·웹서버 없이도 핵심 규칙을 테스트 가능 | 빠르고 안정적인 단위 테스트 |
| **UI 독립성** | 화면을 바꿔도 비즈니스 규칙은 그대로 | 웹 → 앱 → 콘솔로 바꿔도 핵심 코드 유지 |
| **데이터베이스 독립성** | 저장소를 바꿔도 비즈니스 규칙은 그대로 | MySQL → PostgreSQL → MongoDB 교체 가능 |
| **외부 에이전시 독립성** | 핵심 규칙은 외부 시스템(외부 API, 서비스)을 모름 | 외부 서비스가 바뀌거나 죽어도 중심은 안전 |

> 외우는 팁: **"의존성 규칙 1개 + ○○ 독립성 4개(프레임워크·UI·DB·외부) + 테스트 용이성"**

## 4. AI 분야의 세 갈래

| 구분 | 하는 일 | 비고 |
|---|---|---|
| **AI 엔지니어링** | 모델 분석, 기술 분석 — 모델 자체를 연구·개발 | 기본적으로 **석·박사** 위주로 채용 |
| **AI 네이티브** | *(필기 비어 있음)* 일반적으로: 처음부터 AI 활용을 전제로 일하고 서비스를 만드는 방식 | 강의 내용 확인 후 보충 필요 |
| **AI 서비스** | 만들어진 모델(LLM)을 활용해 실제 서비스를 만드는 일 | ← 우리가 목표로 하는 영역 |

## 5. AI 서비스 시대의 경쟁력 = 아키텍처

논리 흐름:

1. 요즘 LLM 서비스는 대부분 **에이전트**를 포함한다.
2. 그 에이전트에게 **지시를 내리는 건 사람**이다.
3. 지시는 보통 **md 파일**(프롬프트, 규칙 문서 등) 형태로 내린다.
4. → **"이 지시를 얼마나 정확하게 내리느냐"가 경쟁력**이다.
5. 정확히 지시하려면 **큰 그림(아키텍처)을 그릴 수 있어야** 한다.
   (무엇을 어떤 층에 두고, 어떻게 나누고, 어떻게 연결할지 알아야 AI에게 정확히 시킬 수 있다)
6. → 즉, **클린 아키텍처를 잘 짜는 능력이 중요하다.**

### 아키텍처 흐름 (작업 순서)

```
요구사항 분석  ──▶  아키텍처 설계  ──▶  시스템 분배 설계
 (무엇을 원하나)     (큰 구조·계층)       (어디에 나눠 담나: 서비스/모듈/서버)
```

### 예시: 클린 아키텍처를 AI 서비스에 대입하면 (이해를 돕기 위한 예시)

| 층 | AI 챗봇 서비스에서 |
|---|---|
| Entities | 대화 기록, 사용자, 답변 정책 같은 핵심 규칙 |
| Use Cases | "문서를 요약해 준다", "질문에 답한다" |
| Interface Adapters | LLM 호출 어댑터(프롬프트 조립, 응답 파싱), API 컨트롤러 |
| Frameworks & Drivers | Claude/GPT API, 벡터 DB, FastAPI, 웹 UI |

→ LLM 모델을 다른 회사 것으로 바꿔도 **바깥 층만 수정**하면 됨 = 외부 에이전시 독립성.
→ AI에게 코드를 시킬 때도 "이 기능은 유스케이스 층, DB 접근은 어댑터 층에" 처럼 **층을 지정해 지시**하면 결과가 훨씬 정확해진다.
