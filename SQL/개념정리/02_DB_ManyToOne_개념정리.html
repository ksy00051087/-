Many to one relationships

관계 · 관계의 종류 · N:1 예시 · 댓글과 게시글 · FK 위치

1-1관계 (relationship)

데이터베이스 내 여러 테이블 간의 논리적인 연결 관계를 나타냅니다.

'강사' 테이블과 '학생' 테이블이 있을 때 "OOO 강사가 김싸피 학생을 가르치고 있다"는 정보를 저장하려면 두 테이블 간의 관계를 설정해야 합니다. 이를 위해 한 테이블에 다른 테이블의 기본 키(Primary Key)를 저장하며, 이처럼 다른 테이블의 기본 키를 참조하는 속성을 외래 키(Foreign Key)라고 합니다. 외래 키는 두 테이블 간의 논리적인 연결 고리 역할을 하며, 이를 통해 연관된 데이터를 효율적으로 관리할 수 있습니다.

1-2관계의 종류

관계의미예시
1:1 (One to One)한 테이블의 레코드가 다른 테이블의 단 하나의 레코드와만 1:1로 매칭되는 관계한 명의 사용자(User)는 오직 하나의 프로필(Profile)만 가짐
N:1 (Many to One)여러 개의 레코드(N)가 하나의 레코드(1)에 소속되는 관계하나의 게시글(1)에 여러 댓글(N)이 달릴 수 있음. 하지만 특정 댓글 하나가 여러 게시글에 동시에 달릴 수는 없음 — Comment.article_id(FK) → Article.id(PK)
N:M (Many to Many)여러 레코드가 여러 레코드와 양방향으로 연결되는 관계. 두 테이블 사이에 연결을 위한 중개 테이블(Through Table)이 필요한 학생은 여러 수업을 신청하고, 한 수업에는 여러 학생이 수강 — Student · Enrollment(중개) · Lecture
1:1 관계는 N:1 관계와 사용 방법이 유사하며, N:M 관계는 추후 진행됩니다.

1-3Many to one relationships

한 테이블의 0개 이상의 레코드가 다른 테이블의 레코드 한 개와 관련된 관계.

1-4댓글과 게시글의 관계

Comment(N) : Article(1)

  • 하나의 게시글에는 여러 개의 댓글이 달림
  • 단, 게시글에 댓글이 없는 경우도 존재
  • 댓글이 소속된 게시글이 없는 경우는 없음

→ 즉, 0개 이상의 댓글은 1개의 게시글에 작성될 수 있다.

1-5Many to one 예시

관계설명
SSAFY Track(1) : Student(N)한 트랙에 여러 교육생, 한 교육생은 트랙이 중복될 수 없음
Account(N) : Bank(1)하나의 계좌는 한 은행에만 소속, 한 은행은 여러 계좌
Baseball Team(1) : Member(N)한 팀에 여러 선수, 한 선수가 다른 팀에 동시 소속 불가
Order(N) : Customer(1)한 고객이 여러 주문, 하나의 주문을 여러 고객이 낼 수 없음
Country(1) : City(N)한 국가에 여러 도시, 한 도시가 여러 국가에 포함되지 않음
Movie(N) : Actor(M)N:1 관계 아님 — 영화에 여러 배우, 배우도 여러 영화에 출연

1-6테이블 관계 설정 — 외래 키는 어디에?

✗ '1'쪽(Article)에 FK를 두면✓ 'N'쪽(Comment)에 FK를 두면
구조Article 테이블에 Comment 정보(외래 키) 컬럼Comment 테이블에 Article 정보(외래 키) 컬럼
결과댓글 생성마다 Comment 정보와 함께 Article 정보(id, title, content …)가 매번 중복 저장되어 낭비 발생Comment가 생성되면 Article의 정보만 저장하면 됨
외래 키(FK)의 적절한 위치는 N:1에서 N을 담당하는 테이블입니다. 외래 키 컬럼에 저장되는 데이터는 참조하는 데이터를 대표하는 Primary Key(PK) 정보입니다.

댓글 모델 구현

ForeignKey 클래스 · on_delete · Comment 모델 · migration 결과 · shell로 댓글 생성

2-1ForeignKey 클래스

ForeignKey(to, on_delete)

한 모델이 다른 모델을 참조하는 관계를 설정하는 클래스 → N:1 관계를 표현할 때 사용하며, 데이터베이스에서 외래 키로 구현됩니다.

  • to — 참조하는 모델 class 이름 (N:1에서 N이 아닌 1의 class 정보)
  • on_delete — 외래 키가 참조하는 객체(1)가 사라졌을 때, 외래 키를 가진 객체(N)를 어떻게 처리할지 정의하는 설정 (데이터 무결성)
to와 on_delete 속성은 ForeignKey 설정에 필수 요소입니다.

데이터 무결성 — 데이터가 정확하고 일관되며, 유효하게 유지되는 상태 (데이터베이스에 저장된 데이터의 정확성, 일관성, 유효성을 유지하는 것)

2-2on_delete 속성 종류

값동작
CASCADE참조된 객체(부모)가 삭제될 때 이를 참조하는 모든 객체도 삭제. 예) 게시글이 삭제되면 해당 게시글의 모든 댓글 삭제
PROTECT삭제하려는 부모 객체에 자식 객체가 존재하면 부모 객체를 삭제하지 못하도록 지정. 예) 댓글이 있는 게시글은 삭제 불가
SET_NULL부모 객체가 삭제되면 해당 필드에 NULL 저장. 단, 해당 ForeignKey 필드에 null=True가 설정되어야 함

기타 on_delete 설정 값: https://docs.djangoproject.com/en/5.2/ref/models/fields/#arguments

2-3댓글 모델 정의하기

# articles/models.py
class Comment(models.Model):
    article = models.ForeignKey(Article, on_delete=models.CASCADE)
    content = models.CharField(max_length=200)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

ForeignKey 클래스의 인스턴스 이름은 참조하는 모델 클래스 이름의 단수형(소문자)으로 작성하는 것을 권장합니다.

단수형을 권장하는 이유 — 단일 객체를 참조하므로 속성명을 단수형으로 쓰면 의미가 명확해지고, 코드 작성 시 문맥이 자연스럽습니다 (comment.article).

2-4Migration 이후 댓글 테이블 확인

articles_comment 테이블 컬럼: id · content varchar(200) · created_at datetime · updated_at datetime · article_id bigint

  • 만들어지는 외래 키 필드 이름 규칙: '작성한 외래 키 필드명' + '_' + 'id' → article_id
  • 참조하는 클래스 이름의 소문자(단수형)로 작성하는 것이 권장되었던 이유이기도 함
  • bigint 자료형 — 큰 정수형으로 약 900경까지 저장할 수 있어 숫자 고갈 걱정이 없으므로 Django는 PK를 선언할 때 해당 자료형을 사용. 외래 키는 이 PK 정보를 저장하므로 동일하게 bigint
외래 키는 models.py의 클래스 내에서 ForeignKey 필드를 작성하는 순서와 관계없이 테이블의 마지막 필드로 생성됩니다.

관계 모델 참조

참조 · 역참조 · related manager · 이름 규칙 · 연습

3-1참조

참조 필드를 가진 쪽(N)에서 연결된 쪽(1)의 데이터에 접근하는 것을 "참조한다"고 말합니다. 친구의 연락처를 가지고 있어 언제든 연락할 수 있는 것과 같습니다 — 댓글(Comment)에는 ForeignKey 필드인 article이 있어 게시글 정보에 쉽게 접근할 수 있으므로, 댓글은 게시글을 참조합니다.

예시) 댓글이 달린 게시글 내용에 접근: comment.article.content

3-2특정 게시글의 댓글 조회하기

# .all() — 특정 게시물의 댓글이 아닌 모든 댓글을 조회함
comments = Comment.objects.all()

# .filter() — 특정 게시글 정보를 가져온 후 filter 이용
article = Article.objects.get(pk=1)
comments = Comment.objects.filter(article=article)
Django에는 더 직관적인 방법(역참조)이 존재합니다.

3-3역참조

참조 필드가 없는 쪽(1)에서, 나를 참조하는 쪽(N)의 데이터를 거꾸로 조회하는 것.

"내 번호를 저장한 사람들이 누구인지 찾는 것"과 같습니다. 내 휴대폰에는 그 사람들의 정보가 없으므로 반대로 내 번호가 저장된 연락처를 찾아야 합니다. 게시글(Article)에는 댓글을 가리키는 필드가 없고, 어떤 게시글의 댓글인지에 대한 정보(article_id)는 댓글 테이블에만 저장되어 있습니다. 그래서 "article_id가 이 게시글인 댓글"을 거꾸로 찾아야 하며, 앞의 Comment.objects.filter(article=article)이 바로 이 작업입니다.

Django는 ForeignKey를 정의하면 반대쪽 모델에서 사용할 역참조 이름(comment_set)을 자동으로 만들어 주므로 article.comment_set.all()로 간단히 조회할 수 있습니다.

코드방향
참조comment.article댓글 → 게시글 (내 칸의 article_id를 읽음)
역참조article.comment_set.all()게시글 → 댓글 (article_id = 1인 행을 찾음)
참조와 역참조는 "같은 연결선을 어느 쪽에서 출발하느냐"의 차이입니다. articles_article에는 연결 정보가 없고, 연결 정보(FK)는 articles_comment에만 있습니다.

3-4역참조 기본 구조 — article.comment_set.all()

부분이름설명
article1. 모델 인스턴스models.py에 정의된 모델 클래스로 생성된 실제 데이터. article.title처럼 속성에 접근·수정 가능. 역참조는 참조 필드가 없는 '1'쪽 모델(Article)의 인스턴스에서 시작함 — 특정 게시글에 작성된 댓글 전체를 조회하는 요청
.comment_set2. related manager (역참조 이름)N:1 혹은 N:M 관계에서 역참조 시에 사용하는 매니저. 'objects' 매니저로 QuerySet API를 사용했던 것처럼 related manager를 통해 QuerySet API를 사용할 수 있게 됨
.all()3. QuerySet API데이터를 가져오기 위한 쿼리 결과 집합을 만드는 인터페이스

3-5related manager 이름 규칙

N:1 혹은 M:N 관계에서 FK를 정의하지 않은 모델에서 연결된 객체들을 조회할 수 있게 해 주며, FK를 정의한 모델의 이름을 소문자로 바꾸고 _set을 붙인 것이 기본 값으로 Django가 자동 생성합니다.

  • 특정 댓글의 게시글 참조 (Comment → Article): comment.article
  • 특정 게시글의 댓글 목록 역참조 (Article → Comment): article.comment_set.all()

4-6save 메서드의 commit 인자 (10/12)

View decorators

View decorator · 종류 · Allowed HTTP methods 3가지

10-1View decorator

View 함수의 동작을 수정하거나 추가 기능을 제공하는 데 사용되는 Python 데코레이터.

View decorator는 일종의 "사전 체크리스트"처럼 동작합니다. 뷰 함수 위에 붙여서 작동하며, 코드 흐름을 방해하지 않고 깔끔하게 조건을 설정할 수 있습니다. 자주 쓰이는 View decorator는 로그인 여부, 권한 검사, HTTP 요청 방식 확인 등으로 사용자 접근을 보다 안전하고 체계적으로 관리할 수 있습니다.

10-2View decorators 종류

  • Allowed HTTP methods — 뷰가 허용하는 HTTP 요청 방식(GET, POST 등)을 제한
  • Conditional view processing — 클라이언트가 보낸 요청을 확인한 후 조건에 따른 응답 처리
  • GZip compression — 서버에서 응답 데이터를 압축해서 전송

추가 view decorators: https://docs.djangoproject.com/en/5.2/topics/http/decorators/

Allowed HTTP methods 데코레이터를 사용하면 View 로직을 보호하면서 사용자에게도 올바른 인터페이스를 제공할 수 있고, 각 view의 역할도 명확하게 분리됩니다.

10-3주요 Allowed HTTP methods

데코레이터허용 method
require_http_methods(["METHOD1", "METHOD2", ...])지정된 HTTP method만 허용
require_safe()GET과 HEAD method만 허용
require_POST()POST method만 허용
허용되지 않은 method로 요청하는 경우 405 (Method Not Allowed) 오류, 즉 HttpResponseNotAllowed를 반환합니다.

10-4require_http_methods(request_method_list)

  • 인자는 list이며, list의 요소는 요청이 허용될 HTTP method를 문자열(대문자)로 작성
  • list에 작성된 method 이외의 method로 요청하면 HttpResponseNotAllowed(405) 반환
from django.views.decorators.http import require_http_methods

@require_http_methods(['GET', 'POST'])
def func(request):
    pass

10-5require_safe() · require_POST()

from django.views.decorators.http import require_safe, require_POST

@require_safe       # GET, HEAD 이외 → 405
def func(request):
    pass

@require_POST       # POST 이외 → 405
def func(request):
    pass
require_GET이 있지만 require_safe를 권장하는 이유 — GET과 HEAD는 서버 상태를 변경하지 않고 조회를 수행하는 safe method로 정의돼 있습니다. HEAD 요청은 주로 브라우저가 리소스를 받지 않고 메타 데이터 정보를 조회할 때 사용합니다. 즉 require_safe가 require_GET보다 더 포괄적이며 표준 HTTP 클라이언트와의 호환성이 높습니다.

ERD

정의 · 구성 요소(엔티티 · 속성 · 관계 · Cardinality) · 중요성 · 제작 사이트

11-1ERD (Entity-Relationship Diagram)

데이터베이스의 구조를 시각적으로 표현하는 도구. Entity(개체), 속성, 그리고 엔티티 간의 관계를 그래픽 형태로 나타내어 시스템의 논리적 구조를 모델링하는 다이어그램입니다. 각 박스는 테이블을, 그 안의 필드는 속성(컬럼)을 나타내며, 이를 통해 개발자와 디자이너가 데이터 구조를 한눈에 이해할 수 있습니다.

ERD 예시: https://www.lucidchart.com/pages/er-diagrams

11-2ERD의 구성 요소

요소의미예
엔티티 (Entity)데이터베이스에 저장되는 객체나 개념. 주로 테이블로 표현됨'게시글', '댓글', '회원'
속성 (Attribute)엔티티가 가지는 고유한 데이터 항목. 테이블의 컬럼으로 표현됨'게시글'의 '제목', '내용', '작성일자', '생성일자'
관계 (Relationship)엔티티 간의 연관성. 테이블 간의 연결된 선으로 표현됨게시글을 '작성'한 회원, 게시글에 '달린' 댓글

예: User(id integer · name varchar · address varchar) — Comment(id integer · content varchar · created_at datetime · user_id integer)를 선으로 연결.

11-3Cardinality

한 엔티티와 다른 엔티티 간의 수적 관계를 나타내는 표현.

  • 일대일 (1:1) — 한 엔티티의 레코드가 다른 엔티티의 하나의 레코드와만 연결. 예) 한 '사람'은 하나의 '여권'만 소유하고, '여권'도 한 '사람'에게만 발급
  • 다대일 (N:1) — 여러 레코드가 하나의 엔티티와 연결되며, 반대 방향에서는 하나만 연결. 예) 여러 명의 '학생'이 하나의 '학교'에 소속
  • 다대다 (M:N) — 양쪽 모두 여러 레코드와 연결. 예) '학생'은 여러 '과목'을 수강하고, '과목'도 여러 '학생'이 수강
Cardinality 표현 (Crow's foot)

선의 끝부분에 숫자나 기호(까마귀 발)로 표시: One (and only one) · Zero or one · One or many · Zero or many. 예) User 1명 — Comment 0개 이상.

11-4ERD의 중요성

  • 데이터베이스 설계의 핵심 도구 — 엔티티·속성·관계를 명확히 정의해 논리적 데이터 구조를 시각적으로 표현. 복잡한 비즈니스 로직을 직관적인 다이어그램으로 정리하고, 중복 데이터를 제거해 효율적인 저장 구조를 만들 수 있음
  • 시각적 모델링으로 효과적인 의사소통 지원 — 개발자·기획자·디자이너 등 다양한 직군이 협업 가능. 요구사항 분석 단계에서 누락된 기능·관계를 빠르게 파악하고, 비전문가에게도 시스템 구조를 쉽게 설명
  • 실제 시스템 개발 전 데이터 구조 최적화에 중요 — 데이터 흐름과 연관 관계를 사전에 분석해 불필요한 관계·비효율적 설계를 방지. DB 구축 단계의 중대한 구조적 오류를 줄이고, 변경·유지보수 시에도 ERD 기반으로 안정적으로 수정

Many to One Relationships 01 — 게시글과 댓글 (11/03 오전, 슬라이드 81장)

개념설명예시
ForeignKey다른 모델과 N:1 관계를 정의할 때 사용하는 필드article = models.ForeignKey(Article, on_delete=models.CASCADE)
Many to One여러 하위 객체가 하나의 상위 객체를 참조하는 모델 관계여러 댓글 → 하나의 게시글
ORMDjango에서 데이터베이스를 객체처럼 다루는 방식Comment.objects.create(...)
역참조상위 모델에서 연결된 하위 모델을 조회하는 방식article.comment_set.all()
admin 등록admin 사이트에서 모델을 시각적으로 관리하도록 설정admin.site.register(Comment)
for-empty 문법반복문에서 데이터가 없을 경우를 처리하는 Django 템플릿 문법{% for comment in comments %}...{% empty %}...{% endfor %}
데이터 무결성관계 설정 시 데이터 일관성과 안정성을 유지하는 것on_delete=models.CASCADE

이 문서의 큰 줄기

  • FK는 N쪽에: 여러 댓글이 하나의 게시글에 속하므로 Comment에 article = ForeignKey(Article, on_delete=...). DB에는 article_id(bigint) 컬럼이 마지막에 생긴다.
  • 참조 vs 역참조: comment.article(N→1) / article.comment_set.all()(1→N, related manager).
  • 댓글 CREATE: 폼에서 FK 필드를 빼고(fields = ('content',)), URL의 게시글 pk로 객체를 가져와 save(commit=False) → comment.article = article → save().
  • READ·DELETE: detail에서 역참조로 목록을 넘기고, 삭제 URL에 article_pk와 comment_pk를 함께 둔다.

Many to One Relationships 02 — 게시글·댓글과 User (11/03 오후, 슬라이드 76장)

개념설명예시
User 참조 방법settings.AUTH_USER_MODEL로 사용자 모델을 참조models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
View DecoratorView 함수에 조건을 부여해 특정 요청만 허용@require_http_methods(["POST"])
인증 기반 기능로그인된 사용자만 특정 기능을 수행할 수 있도록 제한request.user.is_authenticated 조건문 활용
ERD엔티티(테이블), 속성(컬럼), 관계(선)로 구성된 데이터베이스 설계 다이어그램게시글 - 댓글 - 사용자 사이의 관계선 연결
댓글 기능 제한비로그인 사용자의 댓글 작성/삭제 요청은 처리하지 않음if not request.user.is_authenticated: return redirect(...)
Article-User 관계하나의 User가 여러 개의 Article을 작성할 수 있는 구조여러 게시글 → 하나의 작성자
Comment-User 관계하나의 User가 여러 개의 Comment를 작성할 수 있는 구조여러 댓글 → 하나의 작성자

이 문서의 큰 줄기

  • User 참조: models.py에서는 settings.AUTH_USER_MODEL(문자열, 지연 평가), 그 밖에서는 get_user_model()(클래스).
  • 작성자 저장 패턴: 폼에서 user 필드를 빼고 save(commit=False) → obj.user = request.user → save(). 기존 데이터가 있으면 migration 때 기본값(1)을 넣는다.
  • 본인만 수정·삭제: 템플릿에서는 request.user == obj.user로 버튼을 숨기고, view에서도 같은 비교를 다시 한다(브라우저 밖 요청 대비).
  • View decorators로 허용할 HTTP method를 제한(405)하고, @login_required로 인증된 사용자만 접근하게 한다.
  • ERD: 엔티티(테이블) · 속성(컬럼) · 관계(선) + Cardinality(Crow's foot)로 설계를 먼저 그린다.
