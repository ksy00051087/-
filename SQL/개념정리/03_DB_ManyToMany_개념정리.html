학습 시작 — 여러 개와 여러 개를 잇기

Onboarding · 학습 목표

"한 환자가 여러 의사에게, 한 의사가 여러 환자에게 — N:1만으로는 이 관계를 표현하기 어렵습니다."

어떻게 하면 데이터를 중복 없이 효율적으로 저장할 수 있을까요? 중개 모델을 사용하면 예약 정보와 함께 부가 정보(필드)를 추가할 수 있고, 실제 서비스에서 유연하고 확장성 있는 구조를 만들 수 있습니다. 이번 시간에는 M:N 관계를 어떻게 구현하고 Django에서 이를 어떻게 다루는지 학습합니다.

학습 목표
  • N:1 구조로 M:N 관계를 표현할 때의 한계를 설명할 수 있다.
  • 중개 모델을 직접 정의하고 ManyToManyField로 M:N 관계를 설정할 수 있다.
  • add() / remove()로 관계를 추가·삭제하고, through로 추가 정보를 저장할 수 있다.
  • through · related_name · symmetrical 인자의 역할을 구분할 수 있다.
  • Article - User 간 M:N 관계로 좋아요 기능을 구현할 수 있다.
1

Many to many relationships

정의 · 병원 진료 시스템 실습 · N:1의 한계 3가지

1-1다대다 관계 (Many to many relationships)

한 테이블의 0개 이상의 레코드가 다른 테이블의 0개 이상의 레코드와 관련된 경우. 영화와 배우처럼 한쪽의 여러 개가 다른 쪽의 여러 개와 연결되는 복잡한 관계를 말합니다. 다대다 관계를 설정하면 한 영화에 여러 배우를 추가하거나, 한 배우가 출연한 모든 영화를 쉽게 찾아낼 수 있습니다.

실습 목표 — M:N 관계의 역할과 필요성 이해하기
  • '병원 진료 시스템 모델 관계'를 직접 만들어 보기 — 환자와 의사 2개의 모델로 구조 구상
  • 기존의 N:1 구조로 환자와 의사 테이블을 구성했을 때 어떤 한계가 있는지 확인
  • M:N 관계는 데이터베이스에서 어떻게 관리하는지 확인
  • 제공된 '99-mtm-practice' 프로젝트를 기반으로 진행

1-2의사와 환자 간 모델 관계 설정 (N:1)

한 명의 의사에게 여러 환자가 예약할 수 있도록 Patient(환자) 모델에 Doctor 외래 키를 정의하고 Migration까지 진행합니다.

# hospitals/models.py
class Doctor(models.Model):
    name = models.TextField()

    def __str__(self):  # print 시 출력될 text 정의
        return f'{self.pk}번 의사 {self.name}'


class Patient(models.Model):
    doctor = models.ForeignKey(Doctor, on_delete=models.CASCADE)
    name = models.TextField()

    def __str__(self):
        return f'{self.pk}번 환자 {self.name}'

1-3의사와 환자 데이터 생성

# $ python manage.py shell -v 2
doctor1 = Doctor.objects.create(name='allie')
# <Doctor: 1번 의사 allie>
doctor2 = Doctor.objects.create(name='barbie')
# <Doctor: 2번 의사 barbie>

# 2명의 환자를 생성하고 각 환자는 서로 다른 의사에게 예약
patient1 = Patient.objects.create(name='carol', doctor=doctor1)
# <Patient: 1번 환자 carol>
patient2 = Patient.objects.create(name='duke', doctor=doctor2)
# <Patient: 2번 환자 duke>

1-4N:1의 한계 상황

# (1/3) 1번 환자(carol)가 두 의사 모두에게 진료를 받고자 한다면
patient3 = Patient.objects.create(name='carol', doctor=doctor2)
# <Patient: 3번 환자 carol>  → 환자 테이블에 carol이 중복으로 입력됨

# (2/3) 진료 받을 의사 정보를 동시에 저장하려 하면 에러
patient4 = Patient.objects.create(name='carol', doctor=doctor1, doctor2)
# SyntaxError: positional argument follows keyword argument
  1. 동일한 환자지만 다른 의사에게도 진료 받기 위해 예약하려면 객체를 하나 더 만들어야 하며, 이때 동일한 환자 정보를 또 작성해 저장하게 됨
  2. 환자 정보가 바뀌면 모든 행을 다 고쳐야 하는 문제가 발생하고, 실수로 하나라도 누락하면 데이터 일관성이 깨지게 됨
  3. 외래 키 컬럼에 '1, 2' 형태로 저장하는 것은 DB 타입 문제로 불가능 — 제1정규형을 만족하지 못함
의사의 정보도 외래 키로 참조하고, 환자의 정보도 외래 키로 참조하는 별개의 테이블을 만든다면 위 문제를 해결할 수 있습니다. 즉, "예약 테이블을 따로 만들자".
2

중개 모델

정의 · 예약 모델 생성 · 예약 데이터 생성과 조회

2-1중개 모델

다대다 관계에서 두 모델을 연결하는 역할을 하는, 특별한 기능을 가진 모델.

의사와 환자가 '예약'이라는 관계로 연결될 때, 단순히 '의사 A와 환자 B가 연결됐다'는 사실 외에 '언제 예약했는지', '예약의 상태는 무엇인지' 같은 추가 정보가 필요할 수 있습니다. 중개 모델을 사용하면 Doctor 모델이나 Patient 모델을 건드리지 않고 이런 정보를 저장할 수 있어 복잡한 현실 세계의 관계를 더욱 정교하게 표현할 수 있습니다.

2-2예약 모델 생성

환자 모델의 외래 키를 삭제하고 별도의 예약 모델을 새로 생성합니다. 예약 모델은 의사와 환자에 각각 N:1 관계를 가집니다.

# hospitals/models.py
# 외래 키 삭제
class Patient(models.Model):
    name = models.TextField()

    def __str__(self):
        return f'{self.pk}번 환자 {self.name}'


# 중개 모델 작성
class Reservation(models.Model):
    doctor = models.ForeignKey(Doctor, on_delete=models.CASCADE)
    patient = models.ForeignKey(Patient, on_delete=models.CASCADE)

    def __str__(self):
        return f'{self.doctor_id}번 의사의 {self.patient_id}번 환자'

예약 테이블 구조: id · doctor_id bigint · patient_id bigint

2-3예약 데이터 생성 · 조회

# 데이터베이스 초기화 후 Migration 진행 및 shell 실행
doctor1 = Doctor.objects.create(name='allie')
# <Doctor: 1번 의사 allie>
patient1 = Patient.objects.create(name='carol')
# <Patient: 1번 환자 carol>
reservation1 = Reservation.objects.create(doctor=doctor1, patient=patient1)
# <Reservation: 1번 의사의 1번 환자>

# 의사 -> 예약 정보 찾기 (중개 테이블 역참조)
doctor1.reservation_set.all()
# <QuerySet [<Reservation: 1번 의사의 1번 환자>]>

# 환자 -> 예약 정보 찾기
patient1.reservation_set.all()
# <QuerySet [<Reservation: 1번 의사의 1번 환자>]>

2-4추가 예약 생성 · 전체 예약 조회

# 1번 의사에게 새로운 환자 예약 생성
patient2 = Patient.objects.create(name='duke')
# <Patient: 2번 환자 duke>
reservation2 = Reservation.objects.create(doctor=doctor1, patient=patient2)
# <Reservation: 1번 의사의 2번 환자>

# 1번 의사의 전체 예약 정보 조회
doctor1.reservation_set.all()
# <QuerySet [<Reservation: 1번 의사의 1번 환자>, <Reservation: 1번 의사의 2번 환자>]>

hospitals_reservation 테이블: (id 1, doctor_id 1, patient_id 1), (id 2, doctor_id 1, patient_id 2).

이렇게 다대다 관계에서는 중개 테이블을 생성해 데이터를 효율적으로 관리할 수 있습니다. Django에서는 'ManyToManyField'를 통해 두 모델 간의 중간 테이블(중개 모델)이 자동으로 만들어집니다.
3

ManyToManyField

정의 · add() · remove() · 실습 1~6 · 기본 필드의 한계

3-1ManyToManyField()

M:N 관계 설정 모델 필드. 이 필드를 설정하면 Django는 자동으로 중간 테이블(중개 모델)을 생성하여 각 모델 간의 관계를 관리합니다.

  • 모델 클래스 내부에 필드로 정의하며, 어느 모델에 정의해도 관계는 동일하게 유지됨
  • 필드명은 다대다 관계를 나타내기 위해 복수형으로 작성을 권장
  • 필수 인자는 관계를 가지는 모델 클래스

3-2ManyToManyField 조작

메서드설명
add()중개 테이블에 새로운 데이터를 추가할 때 사용. 인자로 연결할 대상 모델의 인스턴스를 넣어서 사용
remove()중개 테이블에 있는 데이터를 삭제할 때 사용. 인자로 전달한 인스턴스를 중개 테이블에서 제거하며, 대상 객체 자체는 삭제되지 않음
# 단일 인스턴스 추가 / 여러 인스턴스 한 번에 추가
patient.doctors.add(doctor1)
patient.doctors.add(doctor2, doctor3)

# 단일 관계 삭제 / 여러 관계 한 번에 삭제
patient.doctors.remove(doctor1)
patient.doctors.remove(doctor2, doctor3)

의사 모델에 작성해도 상관없으며 참조/역참조 관계만 잘 기억하면 됩니다 — 환자 모델이 의사 모델을 참조하고, 의사 모델은 역참조를 통해 환자 모델에 접근합니다.

DB 초기화 후 Migration → 생성된 중개 테이블 hospitals_patient_doctors(id · patient_id · doctor_id) 확인. 중개 테이블 이름은 '앱이름_모델클래스명_필드명'으로 생성됩니다.

필드가 아닌 테이블이 생성됨에 유의하세요 (patient 테이블에 doctors 컬럼은 없음).

3-7기본 ManyToManyField의 한계

  • 기본 ManyToManyField로 생성된 중개 테이블은 의사와 환자의 외래 키 정보만 저장함
  • 예약 중개 테이블에 병의 증상, 예약 일정, 방문 횟수 같은 추가 정보가 필요하면 기본 ManyToManyField를 그대로 사용할 수 없음
  • 추가 정보를 저장하려면 사용자가 직접 중개 테이블을 정의해야 함
  • 단, through 없이 중개 모델만 따로 정의하면 .add(), .remove() 메서드를 사용할 수 없음
ManyToManyField에 'through' 속성으로 사용자가 작성한 중개 테이블을 등록하면, 추가 정보 저장과 .add() · .remove() 메서드를 그대로 활용할 수 있습니다.
4

'through' argument

through 속성 · 실습 1~6 · M:N 관계 주요 사항

4-1ManyToManyField의 'through' 속성

중개 테이블에 '추가 데이터'를 사용해 M:N 관계를 형성하려는 경우에 사용.

class Patient(models.Model):
    doctors = models.ManyToManyField(Doctor, through='Reservation')
    name = models.TextField()

    def __str__(self):
        return f'{self.pk}번 환자 {self.name}'


class Reservation(models.Model):
    doctor = models.ForeignKey(Doctor, on_delete=models.CASCADE)
    patient = models.ForeignKey(Patient, on_delete=models.CASCADE)
    symptom = models.TextField()
    reserved_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return f'{self.doctor.pk}번 의사의 {self.patient.pk}번 환자'

이제 예약 정보에 "증상(symptom)"과 "예약일(reserved_at)"이라는 추가 필드가 생깁니다. 중개 테이블 hospitals_reservation: id · symptom TEXT · reserved_at datetime · doctor_id · patient_id.

4-2예약 생성 방법 1 — Reservation class

# DB 초기화 후 Migration, 의사 1명 · 환자 2명 생성
doctor1 = Doctor.objects.create(name='allie')
patient1 = Patient.objects.create(name='carol')
patient2 = Patient.objects.create(name='duke')

reservation1 = Reservation(doctor=doctor1, patient=patient1, symptom='headache')
reservation1.save()

doctor1.patient_set.all()
# <QuerySet [<Patient: 1번 환자 carol>]>
patient1.doctors.all()
# <QuerySet [<Doctor: 1번 의사 allie>]>

4-3예약 생성 방법 2 — through_defaults

Patient 또는 Doctor의 인스턴스를 통한 예약 생성. .add() 메서드의 through_defaults 인자에 {필드명: 값} 형태로 전달하면 중개 모델의 해당 필드에 값이 저장됩니다.

patient2.doctors.add(doctor1, through_defaults={'symptom': 'flu'})

doctor1.patient_set.all()
# <QuerySet [<Patient: 1번 환자 carol>, <Patient: 2번 환자 duke>]>
patient2.doctors.all()
# <QuerySet [<Doctor: 1번 의사 allie>]>

4-4실습 (5~6/6) — 확인과 삭제

중개 테이블(hospitals_reservation)에 (1, headache), (2, flu) — 두 방법 모두 잘 저장되었습니다.

# Reservation을 이용한 예약 삭제 (중개 테이블 인스턴스 직접 삭제)
reservation1.delete()
# (1, {'hospitals.Reservation': 1})

# 의사를 통한 예약 삭제
doctor1.patient_set.remove(patient2)
# 환자 데이터를 통해서도 동일하게 예약 삭제 가능

4-5M:N 관계 주요 사항 정리

  • M:N 관계로 맺어진 두 테이블에는 물리적인 변화가 없음
  • ManyToManyField는 중개 테이블을 자동으로 생성
  • ManyToManyField는 M:N 관계를 맺는 두 모델 어디에 위치해도 상관 없음 — 대신 필드 작성 위치에 따라 참조와 역참조 방향을 주의할 것
  • N:1은 완전한 종속의 관계였지만 M:N은 종속적인 관계가 아니며, '의사에게 진찰받는 환자'와 '환자를 진찰하는 의사' 2가지 형태 모두 표현 가능

6-3M:N 관계의 related_name을 바꾸는 것이 더 좋은 이유 2가지

  1. '소유' 관계의 기본값 유지 — ForeignKey(N:1) 관계는 보통 '소유'나 '소속'의 의미를 가짐(예: 게시글의 소유자는 유저). Django의 기본 역참조 이름 'article_set'은 'User가 소유한 Article의 집합'이라는 매우 직관적인 의미를 가지므로, 가장 중요하고 대표적인 관계의 기본값을 그대로 유지하는 것이 코드의 예측 가능성을 높임
  2. '행위' 관계의 명확한 이름 부여 — ManyToManyField(M:N) 관계는 보통 '참여'나 '행위'의 의미를 가짐(예: 유저가 게시글에 '좋아요를 누르는' 행위). 이 관계에 related_name='like_articles'처럼 행위의 의미가 드러나는 구체적인 이름을 붙이면 코드의 가독성이 크게 향상됨
코드의미
user.article_set.all()"이 유저가 작성한 모든 글" (소유 관계, 기본)
user.like_articles.all()"이 유저가 좋아요를 누른 모든 글" (행위 관계, 명시적)
핵심적인 '소유' 관계(N:1)는 기본값을 유지하고, 부가적인 '행위' 관계(M:N)에 구체적인 이름을 붙여주는 것으로 설계합니다.

9-1팔로우 기능의 모델 관계

User(M) - User(N) — 팔로우는 유저와 유저의 관계를 나타냅니다.

  • 회원은 여러 명의 팔로워를 가질 수 있고, 한 명도 가지지 않을 수도 있음

9-2팔로우 모델 관계 설정

# accounts/models.py
class User(AbstractUser):
    followings = models.ManyToManyField('self', symmetrical=False, related_name='followers')
  • User 모델 클래스에 ManyToManyField로 팔로우 필드 추가
  • User 모델과 관계를 맺으므로 settings.AUTH_USER_MODEL을 써도 되지만, 자기 자신과의 관계이므로 'self'로 표현할 수 있음
  • 팔로우는 단방향 관계이므로 반드시 symmetrical=False
  • 참조 필드 followings = 내가 팔로우하는 사람들. 역참조는 user_set을 써도 되지만 명확한 의미를 위해 related_name으로 followers로 변경
참조·역참조 이름은 서로 바뀌어도 상관없으나, 관계 조회 시 생각하기 편한 방향으로 정해 작성합니다. 생성된 중개 테이블: id · from_user_id · to_user_id.

Fixtures

사용 목적 · 초기 데이터의 필요성 · dumpdata · loaddata · 주의 사항

10-1Fixtures

Django가 데이터베이스로 가져오는 방법을 알고 있는 데이터 모음. 데이터베이스 구조에 맞추어 작성되어 있습니다.

Fixtures 사용 목적
  • 초기 데이터 세팅 — 웹 서비스가 처음 시작될 때 필요한 기본 데이터(기본 권한 그룹, 상품 카테고리 등)를 미리 세팅
  • 테스트 샘플 데이터 준비 — 항상 동일하고 예측 가능한 데이터 환경으로 테스트의 신뢰성과 반복 가능성을 높임
  • 협업 시 동일한 데이터 환경 맞추기 — 팀원 모두가 같은 초기 데이터·테스트 데이터 셋을 쉽게 공유·적용해 개발 환경 간 일관성을 유지하고 협업 효율을 높임

10-2초기 데이터의 필요성

  1. 협업하는 유저 A가 먼저 프로젝트를 작업 후 원격 저장소에 push — .gitignore 때문에 DB는 업로드되지 않음
  2. B가 원격 저장소에서 A가 push한 프로젝트를 pull(혹은 clone) — 결과적으로 B는 DB가 없는 프로젝트를 받게 됨

이처럼 프로젝트의 앱을 처음 설정할 때 동일하게 준비된 데이터로 데이터베이스를 미리 채우는 것이 필요한 순간이 있고, Django는 fixtures로 앱에 초기 데이터(initial data)를 제공합니다.

명령어역할
dumpdata데이터베이스에서 데이터를 내보낼 때 사용. 주로 파일(JSON) 형태로 추출하며, 특정 테이블의 데이터만 추출도 가능
loaddata내보내기 형태로 저장된 JSON 등을 읽어와서 데이터베이스에 저장

10-3실습 사전 준비

M:N까지 모두 작성된 Django 프로젝트에서 유저·게시글·댓글 데이터를 준비합니다.

  • 유저 — 최소 3명을 회원 가입으로 준비
  • 게시글 — 유저별로 1~2개씩
  • 댓글 — 게시글당 2~3개씩, 유저별로 0~2개 정도

10-4dumpdata — 데이터베이스의 특정 앱 혹은 모델 전체 데이터 추출

$ python manage.py dumpdata [앱이름.모델이름] [옵션] > 추출파일명.json
  • 앱이름.모델이름 지정 — 특정 모델의 데이터를 추출
  • 앱이름 혹은 모델명을 지정하지 않으면 — 프로젝트 전체 모델 데이터를 추출
  • --format 옵션으로 JSON, YAML 등 형식 지정 가능 (기본값: JSON)
# articles 앱의 Article 모델 데이터 추출 (--indent 4: 4칸 들여쓰기)
$ python manage.py dumpdata --indent 4 articles.article > articles.json

# comment 모델과 user 모델의 데이터 추출
$ python manage.py dumpdata --indent 4 articles.comment > comments.json
$ python manage.py dumpdata --indent 4 accounts.user > users.json

명령어 실행 후 프로젝트 폴더에 JSON 파일이 생성되고, 파일에는 해당 모델의 모든 데이터가 JSON 형식으로 작성됩니다. Fixtures 파일명은 자유롭게 작성할 수 있습니다.

10-5loaddata — 추출한 데이터 파일을 다시 DB에 반영

$ python manage.py loaddata 파일경로
  • Fixtures 파일의 기본 경로: app_name/fixtures/
  • Django는 설치된 모든 app의 디렉토리에서 fixtures 폴더 이후의 경로로 fixtures 파일을 찾아 load를 진행
실습 사전 준비

articles 폴더 안에 fixtures 폴더를 만들고 dumpdata로 생성한 파일들(articles.json, comments.json, users.json)을 옮긴 뒤, db.sqlite3 파일을 삭제하고 migrate로 데이터베이스를 초기화합니다.

10-6loaddata 명령어 예시 · 순서

# 한 번에 불러오기 — 모든 데이터를 넣은 뒤 마지막에 관계를 검사하므로 순서 상관 없음
$ python manage.py loaddata articles.json users.json comments.json

# 별도로 실행한다면 모델 관계에 따라 순서가 중요

$ python manage.py loaddata articles.json
$ python manage.py loaddata comments.json

comment는 article과 user에 대한 key가, article은 user에 대한 key가 필요하므로 user → article → comment 순으로 load해야 오류가 발생하지 않습니다. comments.json을 먼저 load하면 작성자·게시글 정보를 찾을 수 없어 에러:

'articles_comment' with primary key '1' has an invalid foreign key:
articles_comment.user_id contains a value '1' that does not have a corresponding value in accounts_user.id.

10-7loaddata 주의 사항 · 정리

  • loaddata를 실행하기 전에 해당 모델에 대한 마이그레이션이 완료되어 있어야 함
  • 같은 PK를 가진 데이터가 이미 있으면 중복 에러가 발생할 수 있음 — 기존 데이터를 지우거나 새로운 Fixture 파일을 사용

dumpdata는 DB의 데이터를 파일로 백업하는 도구이고, loaddata는 그 Fixture 파일을 DB로 불러오는 명령어로 개발 환경 준비나 협업 시 매우 유용합니다. 마이그레이션 상태를 먼저 확인하고 인코딩 문제 등을 사전에 해결하면 매끄럽게 데이터를 복원할 수 있습니다.

11-2N+1 Problem

1개의 쿼리로 데이터를 가져왔더라도, 관련 데이터를 추가로 가져오기 위해 추가 쿼리가 N개 더 실행되는 상황. ORM에서 관련 객체를 반복적으로 접근할 때, 초기 1번의 쿼리로 기본 데이터를 조회한 후 각 객체마다 관련 데이터를 가져오는 쿼리가 N번 실행되어 총 N+1개의 쿼리가 발생합니다.

11-4annotate

SQL의 GROUP BY를 사용하여 쿼리셋의 각 객체에 계산된 필드를 추가합니다. 각 행(row)별로 계산된 필드를 추가하며, 집계 함수(Count, Sum 등 여러 데이터를 요약해 분석하는 함수)와 함께 사용합니다.

Book.objects.annotate(num_authors=Count('authors'))
  • 결과 객체에 'num_authors'라는 새로운 필드를 추가 — 각 책과 연관된 저자의 수를 계산
  • book.num_authors로 해당 책의 저자 수에 접근
  • 'num_authors'는 새로 추가되는 필드명이며 다른 명칭으로 작성해도 됨. 생략하면 'authors__count'로 필드명이 자동 생성

11-5① 댓글 개수 — annotate 적용

/articles/index-1/ : "11 queries including 10 similar". 전체 게시글 쿼리 1개 + 각 게시글 댓글 개수 확인 쿼리 10개 — 매번 DB로 쿼리를 보내 댓글 데이터를 받아오고 있습니다. 게시글이 100개이고 여러 명이 동시에 요청하면 그만큼 서버 부하가 커집니다.

    articles = Article.objects.annotate(comment_count=Count('comment')).order_by('-pk')

        'articles': articles,

11-6select_related

  • ForeignKey 또는 OneToOne 관계에서 사용되는 Django ORM 메서드
  • 내부적으로 SQL INNER JOIN을 사용하여 관련 객체를 한 번에 불러옴
  • 단일 쿼리로 관련 객체를 함께 가져와 성능을 향상
Book.objects.select_related('publisher')

Book과 연관된 Publisher 데이터를 함께 가져옵니다. ForeignKey 관계인 'publisher'를 JOIN해 단일 쿼리만으로 조회하므로 book.publisher.name 같은 접근을 추가 쿼리 없이 할 수 있습니다.

11-8prefetch_related

  • SQL이 아닌 Python을 사용한 JOIN을 진행
  • 관련 객체들을 미리 가져와 메모리에 저장하여 성능을 향상
  • M:N 또는 N:1 역참조 관계에서 사용
  • ManyToManyField나 역참조 관계에 대해 별도의 쿼리를 실행
Book.objects.prefetch_related('authors')

Book과 Author가 ManyToMany 관계라고 가정하면, Book을 조회한 후 Django가 별도의 쿼리로 연관된 모든 Author를 미리 로드해 관계를 설정합니다. for author in book.authors.all() 같은 반복이 추가 쿼리 없이 실행됩니다.

11-11섣부른 최적화는 악의 근원

12-1.exists() 특징

  • QuerySet에 결과가 하나 이상 존재하는지 여부를 확인하는 메서드 — 결과가 있으면 True, 없으면 False 반환
  • 데이터베이스에 최소한의 쿼리만 실행하여 효율적
  • 전체 QuerySet을 평가하지 않고 결과의 존재 여부만 확인 — 해당 데이터를 불러오지 않고 DB 수준에서 빠르게 판단
  • → 대량의 QuerySet에 있는 특정 객체 검색에 유용

12-2exists 적용 예시

# articles/views.py — 좋아요 기능
def likes(request, article_pk):
    article = Article.objects.get(pk=article_pk)
    # if request.user in article.like_users.all():
    if article.like_users.filter(pk=request.user.pk).exists():
        article.like_users.remove(request.user)
    else:
        article.like_users.add(request.user)
    return redirect('articles:index')

def follow(request, user_pk):

a) 데이터 중복 발생 — N:1 관계에서는 동일한 객체(예: 환자)가 여러 상대(예: 의사)와 연결될 경우, 동일한 데이터가 여러 번 저장되어 중복 문제가 발생할 수 있다.

  1. OneToOneField

  3. ManyToManyField
  4. CharField
정답 · 해설 보기
c) ManyToManyField — 이 필드는 두 모델 간의 중간 테이블을 자동으로 생성해 관계를 관리한다.

4. O/X — 중개 모델은 두 객체 간 관계 외에 추가 정보를 함께 저장할 수 있다.

Many to Many Relationships 01 — 중개 모델과 좋아요 (11/04 오전, 슬라이드 75장)

개념설명예시
M:N 관계여러 개의 인스턴스가 서로를 참조하는 관계학생 ↔ 수업
중개 모델M:N 관계를 표현하면서 추가 정보를 포함시키는 중간 모델예약 ↔ 예약 날짜, 예약 시간
ManyToManyFieldDjango에서 M:N 관계를 정의하는 필드like_users = models.ManyToManyField(settings.AUTH_USER_MODEL, related_name='like_articles')
throughManyToMany 관계에 사용자 정의 중개 모델을 지정할 때 사용through='Reservation'
related_name역참조 시 사용할 이름 지정related_name='like_articles'
symmetrical관계의 대칭성을 설정하는 속성친구 관계는 대칭적, 팔로우는 비대칭
역참조 충돌같은 두 모델 사이에 관계가 둘 이상이면 기본 역참조 이름(article_set)이 겹침작성자 FK와 좋아요 M2M → related_name으로 해결

이 문서의 큰 줄기

  • N:1로는 M:N을 못 담는다: 같은 환자를 중복 저장하게 되고, FK 칸에 '1, 2'는 넣을 수 없다(제1정규형) → 양쪽을 FK로 참조하는 중개(예약) 테이블을 만든다.
  • ManyToManyField가 중개 테이블(앱이름_모델명_필드명)을 자동 생성하고 add() · remove()로 관계를 다룬다. 어느 모델에 둬도 되지만 참조/역참조 방향이 달라진다.
  • through로 직접 만든 중개 모델을 등록하면 추가 필드(증상·예약일)를 저장하면서 add(through_defaults=...)·remove()를 그대로 쓸 수 있다.
  • related_name · symmetrical: 역참조 이름 변경 / 'self' 관계의 대칭 여부(기본 True).
  • 좋아요: Article에 like_users = ManyToManyField(User, related_name='like_articles') — 소유(FK)는 기본 이름, 행위(M2M)에 새 이름. view는 "있으면 remove, 없으면 add".

개념설명예시
self 관계모델이 자기 자신을 참조하는 관계유저 ↔ 유저 (팔로우)

이 문서의 큰 줄기

  • 프로필: username으로 유저를 찾고 person.article_set · comment_set · like_articles로 활동을 보여준다.
  • 팔로우: followings = ManyToManyField('self', symmetrical=False, related_name='followers') — 중개 테이블은 from_user_id(나) · to_user_id(상대). 본인은 팔로우 불가.
  • fixtures: dumpdata로 추출, app/fixtures/에 두고 loaddata. 따로 load하면 user → article → comment 순서. 인코딩 문제는 python -Xutf8.
  • N+1 해결: 집계는 annotate, FK 정참조는 select_related(JOIN), 역참조·M:N은 prefetch_related(별도 쿼리), 겹치면 Prefetch(..., queryset=...select_related(...)).
  • exists()로 "이미 눌렀나/팔로우했나"를 데이터를 다 불러오지 않고 판단한다. 단, 측정 없는 섣부른 최적화는 피한다.
