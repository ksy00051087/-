Onboarding · 학습 목표

"멋진 웹 페이지를 만들었습니다! 다른 사람들에게도 보여주고 싶다면?"

  1. 웹 브라우저는 클라이언트로서 인터넷 상의 컴퓨터에 요청을 보냅니다.
  2. 이 요청을 받은 서버는 요청에 따라 알맞은 응답을 보냅니다.
  3. 이러한 형태로 제공되는 서비스를 웹 애플리케이션이라고 하며, 이를 빠르게 개발할 수 있도록 도와주는 도구가 웹 프레임워크입니다.
  • 자신이 만든 웹 페이지를 인터넷을 이용해 공유할 수 있습니다.

학습 목표

  • 웹 애플리케이션이 무엇인지 이해한다.
  • 클라이언트-서버 구조를 설명할 수 있다.
  • 가상 환경을 통해 서로 다른 프로젝트의 패키지를 독립적으로 관리할 수 있다.
  • Django 프로젝트를 생성하고 시작할 수 있다.
  • Django를 활용해 사용자 브라우저에 페이지를 응답할 수 있다.

1-1Web application (web service) 개발

  • 인터넷을 통해 사용자에게 제공되는 소프트웨어 프로그램을 구축하는 과정
  • 다양한 디바이스(모바일, 태블릿, PC 등)에서 웹 브라우저를 통해 접근하고 사용할 수 있음
  • 예: 네이버를 비롯한 포털, 인터넷 쇼핑몰부터 Google Docs 같은 업무 도구까지 모두 웹 애플리케이션

1-2클라이언트-서버 구조

인터넷에 연결된 서로 다른 두 컴퓨터가 데이터를 주고받는 웹의 동작 방식 중 하나입니다.

  • Client — 서비스를 요청하는 주체
    (사용자의 웹 브라우저, 모바일 앱)
  • Server — 클라이언트의 요청에 응답하는 주체
    (웹 서버, 데이터베이스 서버)

클라이언트가 요청을 보내면 서버는 요청에 알맞은 데이터 또는 파일을 응답합니다.

1-3우리가 웹 페이지를 보게 되는 과정

  1. 웹 브라우저(클라이언트)에서 google.com을 입력
  2. 브라우저는 인터넷에 연결된 전 세계 어딘가에 있는 구글 컴퓨터(서버)에게 '메인 홈페이지.html' 파일을 달라고 요청
  3. 요청을 받은 구글 컴퓨터는 데이터베이스에서 '메인 홈페이지.html' 파일을 찾아 응답
  4. 브라우저는 전달받은 '메인 홈페이지.html' 파일을 사람이 볼 수 있도록 해석해 주고, 사용자는 구글의 메인 페이지를 보게 됨

1-4웹 개발에서의 Frontend와 Backend

구분역할기술대표 프레임워크

1-5Web Framework와 Django

"웹 서비스 개발"에는 무엇이 필요할까? 로그인/로그아웃, 회원관리, 데이터베이스, 보안 등 너무 많은 기술이 필요합니다. 모든 걸 직접 만드는 대신 잘 만들어진 것을 가져와 좋은 환경에서 잘 쓰는 것도 능력입니다.

Web Framework — 웹 애플리케이션을 빠르게 개발할 수 있도록 도와주는 도구. 개발에 필요한 기본 구조, 규칙, 라이브러리 등을 제공합니다.

Django Framework — Python 기반의 대표적인 웹 프레임워크. 클라이언트-서버 구조의 "서버"를 구현하는 것이 Django를 배우는 목적입니다.

Django를 사용해야 하는 이유
  • 다양성 — Python 기반으로 웹, 모바일 앱 백엔드, API 서버 및 빅데이터 관리 등 광범위한 서비스 개발에 적합
  • 확장성 — 대량의 데이터에 대해 빠르고 유연하게 확장할 수 있는 기능을 제공
  • 보안 — 취약점으로부터 보호하는 보안 기능이 기본적으로 내장되어 있음
  • 커뮤니티 지원 — 개발자를 위한 지원, 문서 및 업데이트를 제공하는 활성화된 커뮤니티

검증된 웹 프레임워크 — 대규모 트래픽 서비스에서도 안정적인 서비스 제공(Spotify, Instagram, Delivery Hero 등).

웹 개발 시장을 주도하는 백엔드 프레임워크(2024~2025, LinkedIn·GitHub Contributors·OSS Insight 자료 종합): ① Django(Python) ② Spring Boot(Java) ③ ASP.NET Core(C#) ④ Laravel(PHP) ⑤ Express.js(Node.js)

가상 환경 (Virtual Environment)

가상 환경이 필요한 이유 · 생성/활성화/비활성화 · 의존성 패키지 · requirements.txt · 주의사항

2-1가상 환경이란?

Python 애플리케이션과 그에 따른 패키지들을 격리하여 관리할 수 있는 독립적인 실행 환경입니다. 나의 컴퓨터 안에서 또 다른 독립된 파이썬 환경을 만들어, 프로젝트끼리 서로 간섭하지 않게 됩니다.

  • Python global — 컴퓨터 전체에서 사용되는 기본 Python 환경
  • 가상 환경 A, 가상 환경 B는 Python global과 분리된 각자의 패키지 공간을 가짐
  • 패키지 — 연관된 모듈들을 하나의 디렉토리에 모아놓은 것

2-2필요한 시나리오 1 — 버전 충돌

  1. 한 개발자가 2개의 프로젝트(A와 B)를 진행해야 하는 상황
  2. 프로젝트 A는 requests 패키지 버전 1이 필요
  3. 프로젝트 B는 requests 패키지 버전 2가 필요
  4. 하지만 파이썬 환경에서 패키지는 1개의 버전만 존재할 수 있음
  5. A와 B 프로젝트의 다른 패키지 버전 사용을 위한 독립적인 개발 환경이 필요

2-3필요한 시나리오 2 — 패키지 충돌

  1. 한 개발자가 2개의 프로젝트(A와 B)를 진행해야 하는 상황
  2. 프로젝트 A는 water 패키지가 필요
  3. 프로젝트 B는 fire라는 패키지가 필요
  4. 하지만 파이썬 환경에서 water 패키지와 fire 패키지를 함께 사용하면 충돌이 발생하기 때문에 설치할 수 없음
  5. A와 B 프로젝트의 패키지 충돌을 피하기 위해 각각 독립적인 개발 환경이 필요

2-4가상 환경 생성 · 활성화 · 비활성화

# 1. 가상 환경 venv 생성 (venv 모듈로 'venv'라는 이름의 가상 환경을 만든다)
$ python -m venv venv

# 2. 가상 환경 활성화 (Windows / Git Bash)
$ source venv/Scripts/activate
# macOS / Linux
$ source venv/bin/activate

# 3. 비활성화 → 다시 Python Global 환경으로 돌아옴
$ deactivate
  • venv 폴더 안에는 파이썬 실행 파일, 라이브러리 등을 담을 공간이 마련됨
  • 가상 환경 이름은 임의로 지정 가능하나 관례적으로 venv를 사용
  • 활성화 후 프롬프트 앞에 (venv)와 같이 표시된다면 성공
OS별 명령어 차이 — 사용하고 있는 운영체제(Windows, macOS, Linux 등)에 따라 만들어진 venv 폴더의 구조가 다릅니다. 그렇기 때문에 가상 환경을 실행하는 명령어의 경로(Scripts vs bin)도 다릅니다.

2-5의존성 (Dependencies)

의존성 — 하나의 소프트웨어가 동작하기 위해 필요로 하는 다른 소프트웨어나 라이브러리. (예: 게임이 잘 작동하기 위해서는 CPU, GPU, RAM 등이 필요 → 이들은 게임 입장에서 의존성)

의존성 패키지 — 프로젝트가 의존하는 "개별 라이브러리"들을 가리키는 말. 즉 "프로젝트가 실행되기 위해 꼭 필요한 각각의 패키지". (CPU, GPU, RAM 각각을 의존성 패키지라고 할 수 있음)

$ pip list            # 현재 가상 환경에 설치된 라이브러리 목록 확인
Package    Version
---------- -------
pip        24.0
setuptools 65.5.0     # 갓 생성된 가상 환경은 기본 환경 구성을 위한 pip, setuptools만 존재

pip — 파이썬의 패키지 관리 시스템.

의존성 리스트 예시 — requests 설치 후 패키지 목록 변화

requests(Python에서 HTTP 요청을 보낼 수 있게 해주는 패키지) 하나만 설치했는데 1개만 설치되는 것이 아님. requests가 필요로 하는 의존성들이 함께 설치되기 때문입니다.

2-6의존성 기록과 설치 — requirements.txt

# 1. 의존성 기록 (내보내기): 가상 환경에 설치된 모든 패키지를 버전과 함께 특정 형식으로 출력해 파일로 저장
$ pip freeze > requirements.txt

# 2. 의존성 설치 (가져오기): requirements.txt에 명시된 라이브러리를 한 번에 설치
$ pip install -r requirements.txt
  • 다른 파일명으로도 가능하나 관례적으로 requirements.txt를 사용
  • >는 pip 명령어가 아닌 CLI(Shell)의 Redirection operator로, 이전 명령어의 결과를 파일로 저장(redirect)함. 이미 있는 파일에 쓰면 이전 내용은 덮어써짐
  • -r은 --requirement의 축약형. 패키지 이름을 하나씩 직접 입력하는 대신 "지정된 텍스트 파일을 읽어서 그 안에 적힌 모든 패키지를 설치해라"라고 지시하는 옵션
의존성 리스트 공유 시나리오
  1. 2명(A와 B)의 개발자가 하나의 프로젝트를 함께 개발한다고 가정
  2. 개발자 A가 먼저 가상 환경을 생성 후 프로젝트를 설정하고 관련 패키지를 설치하고 개발하다가 협업을 위해 GitHub에 프로젝트를 push
  3. 개발자 B는 해당 프로젝트를 clone 받고 실행해보려 하지만 실행되지 않음
  4. 개발자 B는 A가 이 프로젝트를 위해 어떤 패키지를 설치했고, 어떤 버전을 설치했는지 A의 가상 환경 상황을 알 수 없음
  5. 가상 환경에 대한 정보, 즉 패키지 목록이 공유되어야 함
왜 버전까지 맞춰야 하나? 패키지 버전이 다를 경우 함수명이나 동작이 달라질 수 있습니다. "내 컴퓨터에선 되는데 네 컴퓨터에선 안 돼" 문제를 해결하고, 프로젝트가 커질수록 늘어나는 패키지를 팀원 간 동일한 개발 환경으로 즉시 구축할 수 있습니다.

2-7가상 환경 주의사항 및 권장사항

  1. 가상 환경에 "들어가고 나오는" 것이 아니라 사용할 Python 환경을 "On/Off"로 전환하는 개념
    • 가상 환경 활성화는 현재 터미널 환경에만 영향을 끼침
    • 새 터미널 창을 열면 다시 활성화해야 함
  2. 프로젝트마다 별도의 가상 환경을 사용
  3. 일반적으로 가상 환경 폴더 venv는 관련된 프로젝트와 동일한 경로에 위치시킴
  4. 폴더 venv는 .gitignore 파일에 작성되어 원격 저장소에 공유하지 않음
    • 저장소 크기를 줄여 효율적인 협업과 배포를 가능하게 함
    • OS별 차이점으로 인한 문제를 방지하기 위함
    • 대신 requirements.txt를 공유하여 각자의 가상 환경을 만듦

2-8가상 환경이 필요한 이유 · 사용 흐름 정리

  1. 프로젝트마다 다른 버전의 라이브러리 사용 — 한 프로젝트에서는 Django 4.2를, 다른 프로젝트에서는 Django 5.2를 사용해야 할 수도 있음. 가상 환경을 쓰면 서로 다른 버전을 동시에 설치해도 충돌 없이 각각 유지
  2. 의존성 충돌 방지 — 프로젝트별로 라이브러리를 독립적으로 관리. 여러 프로젝트가 동시에 같은 라이브러리를 쓰더라도 버전 충돌 문제를 예방
  3. 팀 협업 시 환경 통일 — 동일한 방식으로 가상 환경을 만들어 똑같은 버전의 라이브러리를 설치하면 에러 가능성을 줄일 수 있음
python -m venv venv→source venv/Scripts/activate→pip install→pip freeze > requirements.txt→(팀원) pip install -r requirements.txt→deactivate

Django 프로젝트 생성 및 서버 실행

Django 설치 · startproject · runserver · 프로젝트 생성 전체 루틴

3-1설치 → 프로젝트 생성 → 서버 실행

Django Design Pattern

디자인 패턴 · MVC · MTV · 프로젝트와 앱 · 프로젝트 및 앱 구조

4-1디자인 패턴 (Design Pattern)

소프트웨어 설계에서 반복적으로 발생하는 문제에 대한, 검증되고 재사용 가능한 일반적인 해결책. "애플리케이션의 구조는 이렇게 구성하자"라는 모범 답안 또는 관행입니다. 대표적인 디자인 패턴이 MVC입니다.

4-2MVC 디자인 패턴

하나의 애플리케이션을 구조화하는 대표적인 구조적 디자인 패턴. 시각적 요소와 뒤에서 실행되는 로직을 서로 영향 없이, 쉽게 유지보수할 수 있는 애플리케이션을 만들기 위해 사용합니다.

  • Model — 데이터 및 비즈니스 로직을 처리
  • View — 사용자에게 보이는 화면을 담당
  • Controller — 사용자의 입력을 받아 Model과 View를 제어

4-3MTV 디자인 패턴

Django에서 애플리케이션을 구조화하는 디자인 패턴 (Model, Template, View).

MVCMTV
ModelModel
ViewTemplate
ControllerView
기존 MVC 패턴과 동일하나 단순히 명칭을 다르게 정의한 것입니다.

4-4Django project & Django application

구분설명
Django project애플리케이션의 집합. DB 설정, URL 연결, 전체 앱 설정 등을 처리
Django application독립적으로 작동하는 기능 단위 모듈. 각자 특정한 기능을 담당하며 다른 앱들과 함께 하나의 프로젝트를 구성
만약 온라인 커뮤니티 카페를 만든다면?
  • 프로젝트: 카페 (전체 설정 담당)
  • 앱: 게시글, 댓글, 회원 관리 등 (DB, 인증, 화면)
다양한 서비스에 대입해보면
  • 카페 프로젝트 → 게시글 앱, 댓글 앱, 회원 관리 앱
  • 교육 관리 프로젝트 → 문제 관리 앱, 점수 관리 앱

Django와 요청 & 응답

URLs → View → Template · 템플릿 경로 규칙 · 데이터 흐름에 따른 코드 작성

5-1요청과 응답의 흐름

사용자가 http://127.0.0.1:8000/articles/로 접속하면 다음 순서로 처리됩니다.

브라우저 요청→urls.py→views.py⇄models.py→templates→HTTP 응답(HTML)

5-21. URLs

http://127.0.0.1:8000/articles/로 요청이 왔을 때, request 객체를 views 모듈의 index view 함수에 전달하며 호출합니다.

# urls.py
from django.contrib import admin
from django.urls import path
from articles import views      # articles 패키지에서 views 모듈을 가져오는 것

urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', views.index),
]
URL 문자열은 반드시 '/'(slash)로 끝나야 합니다.

5-32. View

view 함수가 정의되는 곳. 특정 경로에 있는 template과 request 객체를 결합해 응답 객체를 반환합니다.

# views.py
from django.shortcuts import render

def index(request):
    return render(request, 'articles/index.html')
  • 모든 view 함수는 첫 번째 인자로 요청 객체를 필수적으로 받음
  • 매개변수 이름이 request가 아니어도 되지만 관례적으로 request로 작성함

5-43. Template

  1. articles 앱 폴더 안에 templates 폴더 생성 (폴더명은 반드시 templates여야 하며 개발자가 직접 생성해야 함)
  2. templates 폴더 안에 articles 폴더 생성
  3. articles 폴더 안에 템플릿 파일 생성
<!-- articles/templates/articles/index.html -->
<!DOCTYPE html>
<html lang="en">
<head><title>Document</title></head>
<body>
  <h1>Hello, Django!</h1>
</body>
</html>

5-5Django에서 template을 인식하는 경로 규칙

실제 파일 위치render에 쓰는 이름
app폴더/templates/articles/index.html'articles/index.html'
app폴더/templates/example.html'example.html'

Django는 app폴더/templates/ 이후의 경로로 템플릿을 찾습니다. templates 안에 앱 이름 폴더를 한 번 더 만드는 이유는 다른 앱의 같은 이름 템플릿과 구분하기 위해서입니다.

결과: localhost:8000/articles/ → "Hello, Django!" 페이지 응답.

5-6데이터 흐름에 따른 코드 작성하기

사용자의 요청에서부터 데이터의 흐름은 URLs → View → Template 순서입니다. 코드의 작성도 마찬가지로 데이터의 흐름 순서에 따라 작성합니다.

path('articles/', views.index)                         # 1. urls.py
def index(request):                                    # 2. views.py
    return render(request, 'articles/index.html')
articles/templates/articles/index.html                 # 3. template

6-1LTS (Long-Term Support)

프레임워크나 라이브러리 등의 소프트웨어에서 장기간 지원되는 안정적인 버전을 부를 때 사용합니다. 기업이나 대규모 프로젝트는 업그레이드에 많은 비용과 시간이 필요하기 때문에 안정적이고 장기간 지원되는 버전이 필요합니다.

6-2Django는 Full Stack framework인가요?

Django는 Frontend 기능(템플릿)도 제공하기 때문에 Full Stack 영역에서 볼 수도 있습니다. 하지만 Django가 제공하는 Frontend 기능은 다른 전문적인 Frontend Framework들에 비해서는 매우 미흡합니다.

엄밀히 말하면 Full Stack 영역에서 Backend에 속함. 그래서 Full Stack 혹은 Backend Framework라고 부릅니다.

6-3Python 패키지 설치 시 버전 지정 방법

명령어 예시기호의미

6-4render 함수

주어진 템플릿을 주어진 컨텍스트 데이터와 결합하고 렌더링된 텍스트와 함께 HttpResponse 응답 객체를 반환하는 함수.

render(request, template_name, context)
  • request — 응답을 생성하는 데 사용되는 요청 객체
  • template_name — 템플릿 이름의 경로
  • context — 템플릿에서 사용할 데이터 (생략 가능, 딕셔너리 타입으로 작성, 다음 챕터에서 활용)

6-5MTV 디자인 패턴 정리

  • Model — 데이터와 관련된 로직을 관리. 응용프로그램의 데이터 구조를 정의하고 데이터베이스의 기록을 관리
  • Template — 레이아웃과 화면을 처리. 화면상의 사용자 인터페이스 구조와 레이아웃을 정의
  • View — Model & Template과 관련한 로직을 처리해서 응답을 반환. 클라이언트의 요청에 대해 처리를 분기하는 역할 (데이터가 필요하다면 Model에 접근해서 가져오고, 가져온 데이터를 Template으로 보내 화면을 구성하고, 구성된 화면을 응답으로 만들어 클라이언트에게 반환)
HTTP Request→URLs→ forward to appropriate view →View⇄ read/write dataModel/Template→HTTP Response (HTML)

6-6왜 Django는 MVC가 아니라 MTV라고 부를까? (공식 FAQ 요약)

Django의 해석에서 "뷰"는 사용자에게 보여지는 데이터를 설명합니다. 데이터가 어떻게 보이는지가 아니라 어떤 데이터를 보여주는지를 뜻합니다. 그래서 Django의 "뷰"는 특정 URL에 대한 파이썬 콜백 함수이며, 데이터가 어떻게 보일지는 템플릿에 위임합니다. "컨트롤러"는 URL 설정에 따라 요청을 적절한 뷰로 보내는 프레임워크 자체라고 볼 수 있습니다. 이름이 무엇이든 가장 논리적인 방식으로 작업을 끝내면 됩니다.

https://docs.djangoproject.com/ko/5.2/faq/general/#faq-mtv

6-7Trailing Comma (후행 쉼표)

정의 — 컴마로 구분된 목록의 마지막 요소 뒤에 붙는 쉼표. 요소가 하나인 튜플을 만들 때도 사용합니다 (예: ('title',)).

  • 새로운 요소를 추가하거나 순서를 변경할 때 편리
  • 값의 목록, 인자, 또는 import 항목들이 시간이 지남에 따라 확장될 것으로 예상되는 경우에 주로 사용
  • 여러 줄에 걸쳐 작성된 데이터 구조에서 유용하며, 코드의 가독성과 유지보수성을 향상시키는 데 도움
  • 닫는 괄호/대괄호/중괄호는 다음 줄에 배치. 닫는 구분 기호와 같은 줄에 후행 쉼표를 두는 것은 권장하지 않음
# Correct:
FILES = [
    'setup.cfg',
    'tox.ini',
]
initialize(FILES,
           error=True,
)

# Wrong:
FILES = ['setup.cfg', 'tox.ini',]
initialize(FILES, error=True,)

6-8지금까지 등장한 Django의 규칙

  1. urls.py에서 각 url 문자열 경로는 반드시 '/'로 끝남
  2. views.py에서 모든 view 함수는 첫 번째 인자로 요청 객체를 받음 (매개변수 이름은 request로 지정하기)
  3. Django는 특정 경로에 있는 template 파일만 읽어올 수 있음 (특정 경로: app폴더/templates/)

프레임워크의 규칙에는 이유가 있습니다. Django의 설계 철학 문서를 찾아보세요! — https://docs.djangoproject.com/ko/5.2/misc/design-philosophies/

키워드정리
웹 애플리케이션인터넷을 통해 사용자에게 제공되는 소프트웨어 프로그램. 다양한 디바이스에서 웹 브라우저로 접근
클라이언트 / 서버서비스를 요청하는 주체(웹 브라우저, 모바일 앱) / 요청에 응답하는 주체(웹 서버, DB 서버)
Frontend / BackendUI와 상호작용(HTML, CSS, JS) / 서버에서 요청 처리와 DB 상호작용(서버 언어, 프레임워크, DB, API)
웹 프레임워크웹 애플리케이션을 빠르게 개발하도록 기본 구조·규칙·라이브러리를 제공 (Django, Spring, Express)
가상 환경하나의 컴퓨터 안의 또 다른 독립된 파이썬 환경. 의존성 충돌 방지, 팀원 간 같은 버전 사용
디자인 패턴설계에서 공통적인 문제를 해결하는 형식화된 관행 (MVC, MTV). 데이터·사용자 인터페이스·비즈니스 로직을 분리
프로젝트 / 앱전체 웹 애플리케이션 설정 관리(앱의 집합) / 독립적으로 작동하는 기능 단위 모듈
요청과 응답① 브라우저가 URL로 요청 → ② 요청 경로와 일치하는 view 함수 호출 → ③ view 함수가 응답 객체 생성·반환 → ④ 브라우저가 응답 객체를 해석해 페이지 렌더링

이 문서의 큰 줄기

서버가 있다면 웹 페이지를 브라우저에 보내줄 수 있습니다. 웹 프레임워크인 Django를 활용하면 이 서버를 만들 수 있고, 가상 환경 → 프로젝트 → 앱 → URL → View → Template 순서로 만들면 브라우저 요청에 HTML로 응답할 수 있습니다.
