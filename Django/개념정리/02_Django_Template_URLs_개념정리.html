  3. Django의 URL Dispatcher는 많은 URL들을 관리하기 위한 다양한 기능을 갖추고 있습니다.

1

Template System

Django Template system · DTL 4가지 문법 · DTL 예시

1-1Django Template system

파이썬 데이터(context)와 HTML 문서(Template)를 결합하여, 로직과 표현을 분리한 채 동적인 웹페이지를 생성하는 도구입니다.

뉴스 사이트를 떠올려 보세요. 모든 기사는 헤더, 폰트, 광고 위치 등 동일한 페이지 틀(Template)을 사용합니다. 하지만 각 페이지에 들어가는 데이터(context), 즉 기사 제목, 내용, 기자 이름은 모두 다릅니다.

HTML의 콘텐츠를 변수 값에 따라 변경하기
# views.py
def index(request):
    context = {
        'name': 'Jane',
    }
    return render(request, 'articles/index.html', context)
<!-- articles/index.html -->
<body>
  <h1>Hello, {{ name }}!</h1>     <!-- 결과: Hello, Jane! -->
</body>

context['name']이 변경되면 응답 받은 HTML의 출력도 변경됩니다. 템플릿 시스템의 목적은 페이지 '틀'에 '데이터'를 동적으로 결합하는 것입니다.

1-2Django Template Language (DTL)

Template에서 조건, 반복, 변수 등의 프로그래밍적 기능을 제공하는 시스템. 문법(DTL Syntax)은 4가지입니다.

문법형태설명
1. Variable{{ variable }}
{{ variable.attribute }}		render 함수의 세 번째 인자로 딕셔너리 타입으로 전달됨. 해당 딕셔너리의 key에 해당하는 문자열이 template에서 사용 가능한 변수명이 됨. dot('.')을 사용하여 변수 속성에 접근
2. Filters{{ variable|filter }}
{{ name|truncatewords:30 }}		표시할 변수를 수정할 때 사용 (변수 + '|' + 필터). chained(연결)이 가능하며 일부 필터는 인자를 받기도 함. 약 60개의 built-in template filters 제공
3. Tags{% tag %}
{% if %} {% endif %}		반복 또는 논리를 수행하여 제어 흐름을 만듦. 일부 태그는 시작과 종료 태그가 필요. 약 24개의 built-in template tags 제공
4. Comments{# 한 줄 주석 #}
{% comment %} ... {% endcomment %}		DTL에서의 주석 (여러 줄은 comment 태그)
{# context = {'login': False, 'nums': [1, 2, 3]} #}
{% if login %}
  <p>로그인 되었습니다.</p>
{% else %}
  <p>로그인이 필요합니다.</p>
{% endif %}

{% for num in nums %}
  <p>{{ num }}</p>
{% endfor %}

{% comment %}
  여러 줄 주석
{% endcomment %}

https://docs.djangoproject.com/en/5.2/ref/templates/builtins/

1-3DTL 예시 — 오늘의 저녁 메뉴

# urls.py
urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', views.index),
    path('dinner/', views.dinner),
]

# views.py
import random

def dinner(request):
    foods = ['국밥', '국수', '카레', '탕수육']
    picked = random.choice(foods)
    context = {
        'foods': foods,
        'picked': picked,
    }
    return render(request, 'articles/dinner.html', context)
<!-- articles/dinner.html -->
<h1>{{ picked }} 메뉴는 {{ picked|length }}글자입니다.</h1>
<h2>메뉴판</h2>
<ul>
  {% for food in foods %}
    <li>{{ food }}</li>
  {% endfor %}
</ul>
{% if foods|length == 0 %}
  <p>메뉴가 소진 되었습니다.</p>
{% else %}
  <p>아직 메뉴가 남았습니다.</p>
{% endif %}

예시 코드이며, 다르게 구현할 수도 있습니다.

템플릿 상속 (Template inheritance)

기존 템플릿 구조의 한계 · skeleton 템플릿 · extends · block

2-1기존 템플릿 구조의 한계

만약 모든 템플릿에 Bootstrap을 적용하려면? → 모든 템플릿에 Bootstrap CDN을 작성해야 할까? 공통 요소를 매번 반복하는 대신 템플릿 상속을 사용합니다.

템플릿 상속 — 페이지의 공통 요소를 포함하고, 하위 템플릿이 재정의할 수 있는 공간을 정의하는 기본 'skeleton' 템플릿을 작성하여 상속 구조를 구축합니다.

skeleton 코드 — 핵심 로직(구현부)은 비어 있고, 프로그램의 전반적인 파일 구조나 함수/클래스의 입출력 형태 등 기본적인 뼈대만 갖춘 코드

2-2상속 구조 만들기 — 상위 템플릿

  1. 모든 템플릿이 공유했으면 좋겠는 공통 요소를 작성
  2. 템플릿 별로 재정의할 부분은 block 태그를 활용
<!-- articles/base.html -->
<!DOCTYPE html>
<html lang="en">
<head>
  {% comment %} bootstrap CDN 생략 {% endcomment %}
</head>
<body>
  <h1>Hello, Django!</h1>
  {% block content %}
  {% endblock content %}
</body>
</html>

2-3상속 구조 만들기 — 하위 템플릿

기존 하위 템플릿들이 상위 템플릿을 상속받도록 변경합니다. extends 태그로 상속받을 템플릿을 결정하고, 상위 템플릿과 같은 이름으로 작성된 block 태그의 내용을 대체합니다.

<!-- articles/dinner.html -->
{% extends 'articles/base.html' %}

{% block content %}
  <h1>{{ picked }} 메뉴는 {{ picked|length }}글자입니다.</h1>
  <ul>
    {% for food in foods %}<li>{{ food }}</li>{% endfor %}
  </ul>
{% endblock content %}

2-4'extends' tag · 'block' tag

태그의미규칙
{% extends 'articles/base.html' %}자식(하위) 템플릿이 부모 템플릿을 확장한다는 것을 알림반드시 자식 템플릿 최상단에 작성되어야 함. extends 태그는 2개 이상 사용 불가
{% block content %}{% endblock content %}하위 템플릿에서 재정의할 수 있는 블록을 정의상위 템플릿에서 작성하며 하위 템플릿이 작성할 수 있는 공간을 지정. 하위 템플릿의 block이 상위 템플릿의 block 내용을 대체

block 이름은 자유롭게 정할 수 있고(content는 관례), endblock 뒤의 이름은 생략 가능하지만 가독성을 위해 씁니다.

요청과 응답 — HTML form

데이터를 보내고 가져오기 · action & method · input · name · Query String · request 객체 · throw-catch

3-1HTML form

데이터를 보내고 가져오기(Sending and Retrieving form data) — HTML 'form' element를 통해 사용자와 애플리케이션 간의 상호작용을 이해합니다.

  • HTML form은 HTTP 요청을 서버에 보내는 가장 편리한 방법입니다. (클라이언트-서버 구조: 컴퓨터가 데이터를 주고받는 웹의 동작 방식 중 하나)
  • 실제 웹 서비스 예: 네이버·구글의 로그인 화면과 검색창이 모두 HTML form 요소
  • 'form' element — 사용자로부터 할당된 데이터를 서버로 전송. 웹에서 사용자 정보를 입력하는 여러 방식(text, password, checkbox 등)을 제공

3-2form 이용해 Naver로 요청 보내기 — "fake Naver"

# urls.py
urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', views.index),
    path('dinner/', views.dinner),
    path('search/', views.search),
]

# views.py
def search(request):
    return render(request, 'articles/search.html')
<!-- articles/search.html -->
{% extends 'articles/base.html' %}
{% block content %}
  <form action="https://search.naver.com/search.naver" method="GET">
    <input type="text" name="query">
    <input type="submit" value="submit">
  </form>
{% endblock content %}
  1. action 없이 input에 hello를 입력하고 제출 → 브라우저 URL: http://127.0.0.1:8000/search/?query=hello (input에 입력한 데이터가 URL에 붙음)
  2. 실제 Naver에서 검색 후 URL 확인 → https://search.naver.com/search.naver?query=hello (목적지 URL + input의 name 속성 + 입력 데이터). 실제 URL은 더 길지만 위의 URL만 사용해도 정상적으로 검색이 됩니다.
  3. action에 Naver 검색 URL을 넣고 테스트 → 우리 페이지에서 Naver로 검색 요청이 전송됨

3-3form 핵심 속성: action & method

데이터를 어디(action)로 어떤 방식(method)으로 요청할지 결정합니다.

  • action — 입력 데이터가 전송될 URL을 지정 (목적지). action을 지정하지 않으면 데이터는 현재 페이지의 URL로 보내짐
  • method — 데이터를 어떤 방식으로 보낼 것인지 정의. 데이터의 HTTP request method(GET, POST)를 지정

3-4'input' element · 'name' attribute

  • input — 사용자의 데이터를 입력 받을 수 있는 HTML 요소. type 속성 값에 따라 다양한 유형의 입력 데이터를 받음
  • name — input의 핵심 속성. 사용자가 입력한 데이터에 붙이는 이름(key). 데이터를 제출했을 때 서버는 name 속성에 설정된 값을 통해서만 사용자가 입력한 데이터에 접근할 수 있음

3-5Query String Parameters

사용자의 입력 데이터를 URL 주소에 파라미터를 통해 서버로 보내는 방법입니다.

  • 문자열은 앰퍼샌드('&')로 연결된 key=value 쌍으로 구성되며, 기본 URL과는 물음표('?')로 구분됨
  • 예: http://host:port/path?key=value&key=value

3-6HTML form 활용 — 사용자 입력 데이터를 받아 그대로 출력하는 서버 만들기

view 함수는 몇 개가 필요할까? → 2개: 입력 페이지를 주는 throw, 데이터를 받아 출력하는 catch.

# urls.py
urlpatterns = [
    path('throw/', views.throw),
    path('catch/', views.catch),
]

# views.py
def throw(request):
    return render(request, 'articles/throw.html')

def catch(request):
    message = request.GET.get('message')
    context = {
        'message': message,
    }
    return render(request, 'articles/catch.html', context)
<!-- articles/throw.html -->
{% extends 'articles/base.html' %}
{% block content %}
  <h1>Throw</h1>
  <form action="/catch/" method="GET">
    <input type="text" name="message">
    <input type="submit" value="submit">
  </form>
{% endblock content %}

<!-- articles/catch.html -->
{% extends 'articles/base.html' %}
{% block content %}
  <h1>Catch</h1>
  <h3>{{ message }}를 받았어!!</h3>
{% endblock content %}

3-7HTTP request 객체

form으로 전송한 데이터뿐만 아니라 Django로 들어오는 모든 요청 관련 데이터가 담겨 있습니다. (view 함수가 호출될 때 첫 번째 인자로 전달됨)

def catch(request):
    print(request)                         # <WSGIRequest: GET '/catch/?message=...'>
    print(type(request))
    print(request.GET)                     # <QueryDict: {'message': ['...']}>
    print(request.GET.get('message'))      # 딕셔너리의 get 메서드로 키의 값을 조회
    return render(request, 'articles/catch.html')

dir(request) → 'COOKIES', 'FILES', 'GET', 'META', 'POST', ..., 'path', 'session', 'user' 등

3-8throw - catch 간 요청과 응답 정리

브라우저에 /throw/ 입력 시
  1. throw/로 요청 (throw 페이지를 줘!)
  2. 'throw/' 문자열과 일치하는 urls.py의 path 함수 호출
  3. throw view 함수 호출
  4. throw view 함수가 응답 객체를 반환
throw 페이지에서 제출 시
  1. form 데이터 작성 후 제출 (form 요소의 action 속성 값으로 요청)
  2. catch/로 요청 (+ 사용자 입력 데이터와 함께)
  3. 'catch/' 문자열과 일치하는 path 함수 호출
  4. catch view 함수 호출
  5. catch view 함수에서 사용자가 보낸 form 데이터 추출 후 응답 객체를 반환
  6. 응답 객체 전달 → 7. 응답 객체 해석 후 화면 출력
4

Django URLs

URL dispatcher · Variable Routing · App URL 정의(include) · URL 구조 변화

4-1요청과 응답에서 Django URLs의 역할

요청 URL에 따라 실행될 view 함수가 달라집니다.

URL dispatcher (운항 관리자, 분배기) — URL 패턴을 정의하고 해당 패턴이 일치하는 요청을 처리할 view 함수를 연결(매핑)합니다.

4-2Variable Routing

현재 URL 관리의 문제점 — 템플릿의 많은 부분이 중복되고, URL의 일부만 변경되는 상황이라면 계속해서 비슷한 URL과 템플릿을 작성해 나가야 할까?

urlpatterns = [
    path('articles/1/', ...),
    path('articles/2/', ...),
    path('articles/3/', ...),     # ... 글이 늘어날 때마다 계속 추가?
]
# ↓ Variable Routing
urlpatterns = [
    path('articles/<int:num>/', ...),
]

Variable Routing — URL 일부에 변수를 포함시키는 것. 변수는 view 함수의 인자로 전달할 수 있습니다. 형태: <path_converter:variable_name>

  • Path Converter — URL 변수의 타입을 지정. str, int 등 5가지 타입 지원 (str, int, slug, uuid, path)
  • 요청 URL의 <int:num>, <str:name> 위치에 들어있는 값이 변수처럼 취급됨
  • 정수 num 변수가 views.detail에, 문자열 name 변수가 views.greeting에 키워드 인자로 전달됨
  • 예) 요청 URL이 /articles/10/이면 views.detail(request, num=10)의 형태로 호출

키워드 인자 — 함수 호출 시 인자의 순서를 무시하고 특정 매개변수에 값을 할당하는 인자

4-3Variable Routing 실습 — detail

# urls.py
path('articles/<int:num>/', views.detail),

# views.py
def detail(request, num):
    context = {
        'num': num,
    }
    return render(request, 'articles/detail.html', context)
<!-- articles/detail.html -->
{% extends 'articles/base.html' %}
{% block content %}
  <h3>{{ num }}번 글입니다.</h3>
{% endblock content %}
Path Converter의 변수명과 View 함수의 파라미터 이름은 같아야 합니다.

# urls.py
path('hello/<str:name>/', views.greeting),

# views.py
def greeting(request, name):

        'name': name,
    }
    return render(request, 'articles/greeting.html', context)
<!-- articles/greeting.html -->

URL 변화에 따라 템플릿 출력이 바뀌는지 관찰: /articles/1/, /hello/Alice/

4-5App URL mapping — App URL 정의

App URL mapping — 각 앱에 URL을 정의하는 것. 프로젝트와 각 앱이 URL을 나누어 관리를 편하게 하기 위함입니다. 지금은 앱이 하나밖에 없지만, 앞으로 앱이 늘어나면 서로 다른 앱의 URL들이 섞이지 않도록 나누어 관리합니다.

2번째 앱 pages를 추가하면 생기는 문제
# urls.py  (권장되지 않으므로 작성하지 말 것)
from articles import views as article_views
from pages import views as page_views

urlpatterns = [
    path('pages/', page_views.index),
    # 본래 views로 사용되던 모든 곳을 article_views로 바꿔야 함!
]

→ "URL을 각자 앱에서 관리하자". 기존에는 프로젝트 urls.py에 모든 URL이 담겨 있었다면, 변경된 구조에서는 각 앱의 urls.py에서 각자의 URL을 관리합니다.

4-6include 함수

include() — 프로젝트 내부 앱들의 URL을 참조할 수 있도록 매핑하는 함수. URL의 일치하는 부분까지 잘라내고, 남은 문자열 부분은 후속 처리를 위해 include된 URL로 전달합니다.

# firstpjt/urls.py
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', include('articles.urls')),
    path('pages/', include('pages.urls')),
]

# articles/urls.py  (앱 폴더에 직접 생성)
from django.urls import path
from . import views          # '.' = 현재 디렉토리(앱)에서 views를 가져옴

urlpatterns = [
    path('', views.index),
    path('dinner/', views.dinner),
    path('search/', views.search),
    path('throw/', views.throw),
    path('catch/', views.catch),
    path('<int:num>/', views.detail),
    path('hello/<str:name>/', views.greeting),
]

# pages/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path('', views.index),
]

요청 URL이 http://127.0.0.1:8000/articles/index/일 때: 프로젝트 urls.py에서 articles/까지 일치한 뒤 → articles/urls.py에서 나머지 index/를 일치시킵니다.

URL의 변화: 템플릿의 링크도 /dinner/ → /articles/dinner/처럼 바뀌어야 합니다.

<a href="/articles/dinner/">dinner</a>
<a href="/articles/search/">search</a>
<a href="/articles/throw/">throw</a>
5

URL 이름 지정과 이름 공간

Naming URL patterns · DTL url tag · app_name 속성

5-1URL 구조 변경에 따른 문제점

기존 주소 앞에 'articles/'가 붙으면서 해당 URL을 사용하는 모든 위치를 찾아가 변경해야 합니다. → "URL에 이름을 지어주면 이름만 기억하면 되지 않을까?"

5-2Naming URL patterns

URL에 이름을 지정하는 것. path 함수에 name 인자를 키워드 인자로 정의해서 사용합니다.

# articles/urls.py
urlpatterns = [
    path('', views.index, name='index'),
    path('dinner/', views.dinner, name='dinner'),
    path('search/', views.search, name='search'),
    path('throw/', views.throw, name='throw'),
    path('catch/', views.catch, name='catch'),
    path('<int:num>/', views.detail, name='detail'),
    path('hello/<str:name>/', views.greeting, name='greeting'),
]

# pages/urls.py
urlpatterns = [
    path('', views.index, name='index'),
]
<!-- articles/base.html : url 태그로 링크 변경 -->
<a href="{% url 'index' %}">index</a>
<a href="{% url 'dinner' %}">dinner</a>
<a href="{% url 'search' %}">search</a>
<a href="{% url 'throw' %}">throw</a>
a 태그의 href 속성 값뿐만 아니라 form의 action 속성처럼 URL을 작성하는 모든 위치에서 변경해 주어야 합니다.

5-3DTL URL tag

{% url 'url_name' arg1 arg2 %}
  • 주어진 URL 패턴의 이름과 일치하는 절대 경로 주소를 반환 (브라우저에서 확인하면 href="/articles/dinner/"처럼 렌더링됨)
  • URL 패턴에 변수가 포함되어 있으면, 'url_name' 이후에 인자를 추가
  • 태그 이름, URL 이름, 인자들은 공백으로 구분되며 쉼표(,)로 구분되지 않습니다
<!-- path('<int:num>/', views.detail, name='detail') -->
<a href="{% url 'detail' 1 %}">Article 1</a>
<a href="{% url 'detail' 2 %}">Article 2</a>

<!-- DTL for 태그에서 사용: 변수 이름도 인자로 사용 가능 -->
{# views.index: context = {'nums': [1, 2, 3]} #}
{% for num in nums %}
  <a href="{% url 'detail' num %}">Article {{ num }}</a>
{% endfor %}

5-4app_name 속성 — URL 이름 지정 후 남은 문제

articles 앱의 url 이름과 pages 앱의 url 이름이 같은 상황(둘 다 index). 단순히 이름만으로는 완벽하게 분리할 수 없습니다. "누구의 index인지 어떻게 구분하는가?" → "이름에 성(key)을 붙이자"

# articles/urls.py
app_name = 'articles'
urlpatterns = [
    path('', views.index, name='index'),
    ...
]

# pages/urls.py
app_name = 'pages'
urlpatterns = [
    path('', views.index, name='index'),
]
{% url 'app_name:path_name' arg1 arg2 %}

<a href="{% url 'articles:index' %}">index</a>
<a href="{% url 'articles:dinner' %}">dinner</a>
<a href="{% url 'articles:detail' num %}">Article {{ num }}</a>
<a href="{% url 'pages:index' %}">pages</a>
  • app_name이 추가 또는 수정되면 url 태그에도 해당 내용이 반영되어야 함 (반영하지 않으면 NoReverseMatch 에러)
  • HTML 반영 후 확인 — 최종 링크는 변하지 않음 (/articles/, /articles/dinner/ ...)

6-1추가 템플릿 경로 지정

앱 폴더 내부 templates 폴더(기본 경로) 외에 템플릿을 위치하고 싶을 때 — 예: 모든 앱이 함께 쓰는 base.html을 프로젝트 최상위 templates/ 폴더에 둘 때.

# settings.py
TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'],     # ← 추가 경로
        'APP_DIRS': True,                     # 각 앱의 templates 폴더도 탐색
        'OPTIONS': {
            'context_processors': [
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',
                'django.contrib.messages.context_processors.messages',
            ],
        },
    },
]
<!-- 하위 템플릿에서 extends의 경로 수정 (프로젝트 최상위 templates/base.html) -->
{% extends 'base.html' %}

6-2BASE_DIR

settings.py에서 경로 지정을 편하게 하기 위해 최상단 지점을 지정해 둔 변수 (manage.py가 있는 프로젝트 폴더).

# settings.py
BASE_DIR = Path(__file__).resolve().parent.parent

Python의 객체 지향 파일 시스템 경로: https://docs.python.org/ko/3.11/library/pathlib.html

6-3DTL 주의사항

  • Python처럼 일부 프로그래밍 구조(if, for 등)를 사용할 수 있지만 명칭을 그렇게 설계했을 뿐, Python 코드로 실행되는 것이 아니며 Python과는 관련 없음
  • 프로그래밍적 로직이 아니라 표현을 위한 것임을 명심하기
  • 프로그래밍적 로직은 되도록 view 함수에서 작성 및 처리할 것
  • 공식 문서를 참고해 다양한 태그와 필터 사용해보기

6-4URL의 Trailing Slashes

  • Django는 URL 끝에 '/'가 없다면 자동으로 붙임
  • "기술적인 측면에서, foo.com/bar와 foo.com/bar/는 서로 다른 URL" — 검색 엔진 로봇이나 웹 트래픽 분석 도구에서는 이 두 주소를 서로 다른 페이지로 보기 때문
  • 그래서 Django는 검색 엔진이 혼동하지 않게 하기 위해 무조건 붙이는 것을 선택한 것
  • 그러나 모든 프레임워크가 이렇게 동작하는 것은 아니니 주의
