규칙지금까지 등장한 Django의 규칙

  • 각 값을 별도의 줄에 배치하고, 항상 후행 쉼표를 추가한 뒤 닫는 괄호를 다음 줄에 배치

    'setup.cfg',
    'tox.ini',

# Wrong:
FILES = ['setup.cfg', 'tox.ini',]

MTV·요청과 응답·render

Design Pattern · MVC · MTV · 요청과 응답 · render 함수

개념디자인 패턴 → MVC → MTV

디자인 패턴 — 소프트웨어 설계에서 반복적으로 발생하는 문제에 대한 검증되고 재사용 가능한 일반적인 해결책 · 공통적인 문제를 해결하는 데 쓰이는 형식화 된 관행

MVC 디자인 패턴 — 하나의 애플리케이션을 구조화하는 대표적인 구조적 디자인 패턴 (Model: 데이터 및 비즈니스 로직 처리 / View: 사용자에게 보이는 화면 담당 / Controller: 사용자의 입력을 받아 Model과 View를 제어)

MTV 디자인 패턴 (Model, Template, View) — Django에서 애플리케이션을 구조화하는 디자인 패턴. 기존 MVC 패턴과 동일하나 단순히 명칭을 다르게 정의한 것 (View → Template, Controller → View)

MTVMTV 디자인 패턴 정리
Model데이터와 관련된 로직을 관리 · 응용프로그램의 데이터 구조를 정의하고 데이터베이스의 기록을 관리
Template레이아웃과 화면을 처리 · 화면상의 사용자 인터페이스 구조와 레이아웃을 정의
ViewModel & Template과 관련한 로직을 처리해서 응답을 반환 · 클라이언트의 요청에 대해 처리를 분기하는 역할

흐름Django에서의 요청과 응답

  1. 브라우저가 URL로 요청
  2. 주소와 일치하는 view 함수 호출
  3. 함수가 응답 객체 생성 및 반환
  4. 브라우저는 view 함수가 반환한 응답 객체를 해석해 페이지를 렌더링
# urls.py
from django.contrib import admin
from django.urls import path
from articles import views

urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', views.index),
]

# articles/views.py
from django.shortcuts import render

def index(request):
    return render(request, 'articles/index.html')

render(request, template_name, context) — 주어진 템플릿을 주어진 context 데이터와 결합하고 렌더링된 텍스트와 함께 HttpResponse(응답 객체)를 반환하는 함수

교재 확인 문제 · 디자인 패턴 = 자주 마주치는 설계 문제를 해결하기 위한 표준화된 해결 방법 · render() = 데이터를 템플릿에 전달하여 응답을 반환 · 화면을 정의하는 것 = Template

DTL 변수·필터·태그

Django Template system · Variable · Filters · Tags · Comments · DTL 주의사항

개념Django Template Language (DTL)

Django Template system — 데이터 표현을 제어하면서, 표현과 관련된 부분을 담당. DTL을 활용해 조건, 반복, 변수 등의 프로그래밍적 기능을 제공

구분문법설명
Variable{{ variable }}render 함수의 세 번째 인자 딕셔너리(context)의 key. dot(.)으로 변수 속성 접근
Filters{{ variable|filter }}표시할 변수를 수정. 연결 가능, 일부 필터는 인자를 받음 {{ name|truncatewords:30 }}
Tags{% tag %}반복 또는 논리를 수행하여 제어 흐름을 만듦. 일부 태그는 시작과 종료 태그가 필요 {% if %}{% endif %}
Comments{# #}한 줄 주석 · 여러 줄은 {% comment %}{% endcomment %}

주의DTL 주의사항

  • Python처럼 일부 프로그래밍 구조(if, for 등)를 사용할 수 있지만 명칭을 그렇게 설계했을 뿐
  • Python 코드로 실행되는 것이 아니며 Python과는 관련 없음
  • 프로그래밍적 로직이 아니라 표현을 위한 것임을 명심하기
  • 프로그래밍적 로직은 되도록 view 함수에서 작성 및 처리할 것
# views.py
def greeting(request):
    foods = ['apple', 'banana', 'coconut',]
    info = {
        'name': 'Alice',
    }
    context = {
        'foods': foods,
        'info': info,
    }
    return render(request, 'articles/greeting.html', context)
교재 확인 문제 · 템플릿 시스템의 목적 = HTML과 Python 코드를 분리 · 변수 출력 = {{ 변수명 }} · 올바르지 않은 변수 출력 = {% title %}

템플릿 상속·템플릿 경로

extends · block · 추가 템플릿 경로 · BASE_DIR

개념템플릿 상속

페이지의 공통요소를 포함하고, 하위 템플릿이 재정의할 수 있는 공간을 정의하는 기본 'skeleton' 템플릿을 작성하여 상속 구조를 구축

태그설명
{% extends 'path' %}자식(하위) 템플릿이 부모 템플릿을 확장한다는 것을 알림 · 반드시 자식 템플릿 최상단에 작성 (2개 이상 사용 불가)
{% block name %}{% endblock name %}하위 템플릿에서 재정의(overridden)할 수 있는 블록을 정의
<!-- articles/index.html -->
{% extends 'articles/base.html' %}

{% block content %}
  <h1>Hello, {{ name }}</h1>
{% endblock content %}

설정추가 템플릿 경로

앱 폴더 내부 templates 폴더(기본 경로) 외에 템플릿을 위치하고 싶을 때 TEMPLATES의 'DIRS'에 추가

# settings.py
TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'],
        ...
    },
]
  • 새로운 경로로 옮긴 base.html은 하위 템플릿에서 {% extends 'base.html' %}로 경로 수정 필요
  • BASE_DIR — settings.py에서 경로 지정을 편하게 하기 위해 최상단 지점을 지정해 둔 변수 BASE_DIR = Path(__file__).resolve().parent.parent
교재 확인 문제 · 상위 템플릿 지정 태그 = {% extends %} · 템플릿 경로 설정 변수 = TEMPLATES (안의 'DIRS')

URL·Variable Routing

Django URLs · Variable Routing · Path converters · Trailing Slashes

개념Variable Routing

URL 일부에 변수를 포함시키는 것 (변수는 view 함수의 인자로 전달할 수 있음)

# <path_converter:variable_name>
path('articles/<int:num>/', views.detail)
path('hello/<str:name>/', views.greeting)

def detail(request, num):
    context = {
        'num': num,
    }
    return render(request, 'articles/detail.html', context)

Path converters — URL 변수의 타입을 지정 (str, int 등 5가지 타입 지원)

주의URL의 Trailing Slashes

  • Django는 URL 끝에 /가 없다면 자동으로 붙임
  • 기술적인 측면에서 foo.com/bar와 foo.com/bar/는 서로 다른 URL
  • 검색 엔진 로봇이나 웹 트래픽 분석 도구에서는 두 주소를 서로 다른 페이지로 보기 때문에, Django는 검색 엔진이 혼동하지 않게 무조건 붙이는 것을 선택
  • 그러나 모든 프레임워크가 이렇게 동작하는 것은 아니니 주의
교재 확인 문제 · URL 패턴에서 변수 전달 = path('user/<int:id>/', views.user_detail) · 변수는 <자료형:이름> 형태

include·app_name·url 태그

App URL mapping · include() · Naming URL patterns · DTL URL tag · app_name

개념App URL 정의 · include()

각 앱에 URL을 정의하는 것 — 프로젝트와 각 앱이 URL을 나누어 관리를 편하게 하기 위함

# firstpjt/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', include('articles.urls')),
    path('pages/', include('pages.urls')),
]

# articles/urls.py
from django.urls import path
from . import views

app_name = 'articles'
urlpatterns = [
    path('', views.index, name='index'),
    path('<int:num>/', views.detail, name='detail'),
]

include() — 프로젝트 내부 앱들의 URL을 참조할 수 있도록 매핑하는 함수. URL의 일치하는 부분까지 잘라내고, 남은 문자열 부분은 후속 처리를 위해 include된 URL로 전달

한 파일에서 두 앱의 views를 import 할 때는 별칭: from articles import views as article_views / from pages import views as page_views

개념Naming URL patterns · app_name

  • Naming URL patterns — URL에 이름을 지정하는 것. path 함수의 name 인자를 정의해서 사용 → URL이 바뀌어도 이름만 같으면 템플릿·view를 고칠 필요가 없음
  • DTL URL tag — {% url 'url name' arg1 arg2 %} 주어진 URL 패턴의 이름과 일치하는 절대 경로 주소를 반환
  • app_name — URL 이름이 중복되지 않도록 네임스페이스를 지정. 지정 후에는 {% url 'articles:index' %}처럼 :로 연결
  • app_name이 추가 또는 수정되면 url 태그에도 해당 내용이 반영되어야 함 (최종 링크는 변하지 않음)
<a href="{% url 'articles:detail' article.pk %}">상세</a>
<a href="{% url 'articles:index' %}">목록</a>

개념CSRF

  • CSRF (Cross-Site-Request-Forgery, 사이트 간 요청 위조) — 사용자가 자신의 의지와 무관하게 공격자가 의도한 행동을 하여 특정 웹페이지를 보안에 취약하게 하거나 수정, 삭제 등의 작업을 하게 만드는 공격 방법

쿠키·세션·Custom User

HTTP · 쿠키 · 세션 · Django Authentication System · User model 대체하기 · Login

개념HTTP · 쿠키 · 세션

  • HTTP 특징 — 비 연결 지향(connectionless) · 무상태(stateless): 연결을 끊는 순간 클라이언트와 서버 간의 통신이 끝나며 상태 정보가 유지되지 않음
  • 쿠키 (Cookie) — 서버가 사용자의 웹 브라우저에 전송하는 작은 데이터 조각 (key-value). 서버는 응답 시 Set-Cookie 헤더로 쿠키를 보냄 · 사용 목적: 세션 관리, 개인화, 트래킹
  • 세션 (Session) — 서버 측에서 생성되어 클라이언트와 서버 간의 상태를 유지. 서버가 발급한 session id를 쿠키에 저장해 이후 요청마다 전송
쿠키 종류Lifetime (수명)
Session cookie현재 세션(current session)이 종료되면 삭제됨
Persistent cookiesExpires 속성에 지정된 날짜 혹은 Max-Age 속성에 지정된 기간이 지나면 삭제됨

쿠키와 보안: 제한된 정보(세션 ID 등) · 만료 시간 · 도메인 제한 · Django는 sessionid 쿠키에 HttpOnly를 기본 적용 · Django는 'database-backed sessions'를 기본 값으로 사용 (django_session 테이블)

개념Custom User · Login

  • 기본 User 모델은 필드가 제한적 → 프로젝트 시작 시 커스텀 User 모델로 대체하는 것을 강력히 권장 (첫 migrate 전)
  • AbstractUser = 기본 User 모델의 모든 필드 포함 (토핑이 올려진 피자) / AbstractBaseUser = 최소한의 인증 필드만 제공, 최대의 자유도 (기본 피자 도우)
# accounts/models.py
from django.contrib.auth.models import AbstractUser

class User(AbstractUser):
    pass

# settings.py
AUTH_USER_MODEL = 'accounts.User'

# accounts/admin.py
from django.contrib.auth.admin import UserAdmin
admin.site.register(User, UserAdmin)

# accounts/views.py
from django.contrib.auth.forms import AuthenticationForm
from django.contrib.auth import login as auth_login

def login(request):
    if request.method == 'POST':
        form = AuthenticationForm(request, request.POST)
        if form.is_valid():
            auth_login(request, form.get_user())
            return redirect('articles:index')
    else:
        form = AuthenticationForm()
    ...

AuthenticationForm — 로그인 인증에 사용할 데이터를 입력 받는 built-in form (모델과 연결되지 않고 오직 "인증" 역할) · login(request, user) — 인증된 사용자를 로그인(세션 생성)

교재 확인 문제 · HTTP 특징이 아닌 것 = 상태 유지(Stateful) · 서버가 브라우저에 보내는 작은 데이터 = 쿠키 · 쿠키 목적이 아닌 것 = 데이터베이스 역할 · 서버 측 상태 저장 = 세션 · 세션 ID = 쿠키 · 기본 User에 없는 필드 = phone_number · 커스텀 User 설정 시점 = 프로젝트 시작 시 · 인증 폼 = AuthenticationForm · 세션 생성 함수 = login() · 설정 = AUTH_USER_MODEL

from django.contrib.auth import logout as auth_logout
from django.contrib.auth.decorators import login_required

# 로그아웃: 세션 데이터를 DB에서 삭제 + 클라이언트 쿠키에서 세션 ID 제거
def logout(request):
    auth_logout(request)
    return redirect('articles:index')

            user = form.save()
            auth_login(request, user)

# 회원 탈퇴: 탈퇴 후 로그아웃 순서
@login_required
def delete(request):
    request.user.delete()
    auth_logout(request)

# accounts/forms.py
class CustomUserCreationForm(UserCreationForm):
    class Meta(UserCreationForm.Meta):
        model = get_user_model()
  • 로그아웃 요청은 보통 POST 방식으로 처리 (GET은 데이터 변경을 유발해서는 안 됨)
  • UserCreationForm — 회원 가입 시 사용자 입력을 받는 built-in ModelForm. 커스텀 User를 쓰면 그대로 쓸 때 에러 → 상속받아 CustomUserCreationForm 작성
  • get_user_model() — 현재 프로젝트에서 활성화된 사용자 모델(active user model)을 반환
  • is_authenticated — 사용자의 인증 여부를 알려주는 User 모델의 읽기 전용 속성 (인증 True, 비인증 False) {% if user.is_authenticated %}
  • login_required — 인증된 사용자에 대해서만 view 함수를 실행시키는 데코레이터. 비인증 사용자는 로그인 페이지로 리디렉션
  • 회원 탈퇴는 탈퇴 후 로그아웃 순서 (반대로 하면 요청 객체 정보가 사라져 탈퇴할 유저 정보를 찾을 수 없음)

Auth 03회원정보 수정 · 비밀번호 변경

# 회원정보 수정
class CustomUserChangeForm(UserChangeForm):
    class Meta(UserChangeForm.Meta):
        model = get_user_model()
        fields = ('first_name', 'last_name', 'email',)

form = CustomUserChangeForm(request.POST, instance=request.user)

# 비밀번호 변경
from django.contrib.auth.forms import PasswordChangeForm
from django.contrib.auth import update_session_auth_hash

form = PasswordChangeForm(request.user, request.POST)
if form.is_valid():
    user = form.save()
    update_session_auth_hash(request, user)
    return redirect('articles:index')
  • UserChangeForm — 회원정보 수정 built-in ModelForm. 그대로 쓰면 일반 사용자가 접근하면 안 되는 정보까지 보이므로 Meta의 fields로 출력 필드 제한
  • PasswordChangeForm — 비밀번호 변경 built-in Form. 부모 클래스 SetPasswordForm의 생성자를 따르기 때문에 user를 첫 번째 인자로 받음
  • 암호 변경 시 세션 무효화 — 비밀번호가 변경되면 기존 세션과의 회원 인증 정보가 일치하지 않아 로그아웃 처리됨 → update_session_auth_hash(request, user)로 새 password의 Session Data로 기존 session을 갱신

Auth 03비밀번호 암호화 · 비밀번호 초기화

개념설명
해싱 (Hashing)임의의 데이터를 고정된 길이의 값으로 변환하는 단방향 과정. 같은 입력은 항상 같은 결과, 입력이 조금만 달라도 결과는 크게 달라짐, 해시값으로 원래 입력을 알기 거의 불가능
솔트 (Salt)각 비밀번호에 임의의 문자열을 추가하여 해싱 → 동일한 비밀번호라도 사용자마다 다른 해시값 → 레인보우 테이블 무력화
키 스트레칭 (Key Stretching)해시 연산을 의도적으로 수만 번 이상 반복해 검증 시간을 늘림 → 무차별 대입 공격 속도를 극단적으로 늦춤
PBKDF2솔트와 키 스트레칭을 구현한 Django의 기본 비밀번호 해싱 알고리즘. 해시값 = 알고리즘 · 반복 횟수 · 솔트 · 해시 (사용자 아이디는 포함되지 않음)
비밀번호 초기화비밀번호를 찾으려는 이메일 입력 → 이메일로 재설정 링크 전송 → 새 비밀번호 설정 → 다시 로그인. path('accounts/', include('django.contrib.auth.urls')) + EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend'(콘솔에서 확인)
교재 확인 문제 · 로그아웃 = 세션 데이터와 쿠키 모두 처리 · get_user_model() = 활성화된 User 모델 참조 · 회원가입 폼 = UserCreationForm · 탈퇴 = request.user.delete() · 인증 확인 = is_authenticated · login_required = 비인증 사용자 접근 제한 · 가입 후 자동 로그인 = form.save() 후 login() · 탈퇴 순서 = 계정 삭제 후 로그아웃 · 로그아웃 method = POST · 정보 수정 폼 = UserChangeForm · 비밀번호 변경 폼 = PasswordChangeForm · 로그아웃 방지 = update_session_auth_hash · 해싱 · 솔트 · 키 스트레칭 · PBKDF2 · EMAIL_BACKEND
