REST API

API · 날씨 데이터 예시 · Web API · Open API · REST · RESTful · REST API 구성

1-1API (Application Programming Interface)

두 소프트웨어가 서로 통신할 수 있게 하는 메커니즘. 클라이언트-서버처럼 서로 다른 프로그램에서 요청과 응답을 받을 수 있도록 만든 체계입니다. 서로 이해할 수 있는 공통된 규칙과 형식이 필요하고, 이 역할을 하는 것이 바로 API입니다.

API 예시 — 날씨 데이터 받기
  1. 기상청 서버에는 기상 데이터가 들어 있고, 스마트폰의 날씨 앱·웹 사이트의 날씨 정보 등 다양한 서비스가 이 서버에 데이터를 요청하고 응답받음
  2. 기상청 서버에는 "날씨 정보를 얻고 싶으면 이런 식으로 요청하라"는 지정된 형식(지역, 날짜, 조회할 내용 — 온도, 바람 등)을 제공하는 매뉴얼이 작성되어 있음
  3. 소프트웨어와 소프트웨어 간 지정된 정의(형식)로 소통하는 수단 → API. "이렇게 요청을 보내면, 이렇게 정보를 제공해 줄 것이다"라는 매뉴얼

→ 스마트폰의 날씨 앱은 기상청이 제공하는 API를 통해 기상청 시스템과 대화하여 매일 최신 날씨 정보를 표시합니다.

1-2API 비유 — 콘센트

우리 집 냉장고에 전기를 공급해야 한다고 가정하면, 우리는 그냥 냉장고의 플러그를 소켓에 꽂으면 제품이 작동합니다. 중요한 것은 "전기를 공급하기 위해 직접 배선을 하지 않는다"는 것 — 이는 매우 위험하면서도 비효율적인 일이기 때문입니다.

→ API는 복잡한 코드를 추상화하여 대신 사용할 수 있는 몇 가지 더 쉬운 구문을 제공합니다.

1-3Web API · Open API · Third Party

용어의미
Web API웹 서버 또는 웹 브라우저를 위한 API
Open API누구나 접근할 수 있도록 공개된, 외부 소프트웨어와 통신하기 위한 인터페이스
Third Party직접 개발하지 않은 외부의 서비스나 소프트웨어를 제공하거나 활용하는 주체

현대 웹 개발은 하나부터 열까지 직접 개발하기보다 여러 Open API를 활용하는 추세입니다. 대표적인 Third Party Open API: Youtube API, Google Map API, Naver Papago API, Kakao Map API.

1-4REST (Representational State Transfer)

API Server를 개발하기 위한 일종의 소프트웨어 설계 방법론. 엄격한 규칙을 의미하는 것은 아닙니다!

건축 설계 비유 — 지붕부터 만들고, 창문부터 만들고, 벽을 나중에 올리면 공사가 복잡해지겠죠? 그래서 집을 짓는 순서와 방식을 정해 두듯, API마다 제각각인 설계를 정리하고 누구나 예측 가능한 방식으로 사용할 수 있도록 설계 기준을 제안한 것이 바로 REST입니다.

1-5RESTful API

REST 원리를 따르는 시스템을 RESTful하다고 부릅니다. "자원을 정의"하고 "자원에 대한 주소를 지정"하는 전반적인 방법을 서술합니다.

"각각 API 서버 구조를 작성하는 모습이 너무 다르니 어느 정도 약속을 만들어서 다같이 통일해서 쓰자!"

REST API 활용 예시

Naver Cloud API, Kakao Login API 등 — REST API는 시스템 간 표준화된 통신 방식을 제공함으로써, 서로 다른 기술 스택 간에도 연동이 가능합니다.

1-6REST API — REST라는 설계 디자인 약속을 지켜 구현한 API

REST에서 자원을 정의하고 주소를 지정하는 방법무엇으로
1. 자원의 "식별"URI
2. 자원의 "행위"HTTP Methods
3. 자원의 "표현"JSON 데이터 (궁극적으로 표현되는 데이터 결과물)
URL만 보고도 무슨 데이터를, 어떤 방식으로 처리할지 예측할 수 있어야 합니다. 개발 시에는 항상 "자원 중심 + 동작 명확화 + 일관된 응답 형식"을 기준으로 설계하세요.

자원의 식별 — URI

자원 · URI · URL · Scheme · Domain Name · Port · Path · Parameters · Anchor

2-1URI (Uniform Resource Identifier, 통합 자원 식별자)

인터넷에서 리소스(자원)를 식별하는 문자열.

자원(Resource) — 웹에서 고유한 주소를 통해 접근할 수 있는 데이터나 기능의 단위

2-2URL (Uniform Resource Locator, 통합 자원 위치)

웹에서 주어진 리소스의 주소. 네트워크 상에 리소스가 어디 있는지를 알려주기 위한 약속입니다. 가장 일반적인 URI는 웹 주소로 알려진 URL입니다.

http://  www.example.com  :80  /path/to/myfile.html  ?key1=value1&key2=value2  #SomewhereInTheDocument
Scheme   Domain Name      Port Path to the file      Parameters                 Anchor

2-3URL 구성 요소

요소설명
Scheme (Protocol)브라우저가 리소스를 요청하는 데 사용해야 하는 규약. URL의 첫 부분은 어떤 규약을 사용하는지 나타냄. 기본적으로 웹은 http(s)를 요구하며, 메일을 열기 위한 mailto:, 파일을 전송하기 위한 ftp: 등 다른 프로토콜도 존재
Domain Name요청 중인 웹 서버를 나타냄. 직접 IP 주소를 사용하는 것도 가능하지만 사람이 외우기 어렵기 때문에 주로 Domain Name을 사용. 예) google.com의 IP 주소는 142.251.42.142
Port웹 서버의 리소스에 접근하는 데 사용되는 기술적인 문(Gate). HTTP 프로토콜의 표준 포트 — HTTP 80, HTTPS 443. 표준 포트만 작성 시 생략 가능
Path웹 서버의 리소스 경로. 초기에는 실제 파일의 물리적 위치였지만, 오늘날은 실제 위치가 아닌 추상화된 형태의 구조를 표현. 예) /articles/create/가 실제 articles 폴더 안의 create 폴더를 뜻하는 것은 아님
Parameters웹 서버에 제공하는 추가적인 데이터. '&' 기호로 구분되는 key-value 쌍 목록. 서버는 리소스를 응답하기 전에 이 파라미터로 추가 작업을 수행할 수 있음
Anchor일종의 "북마크"를 나타내며 브라우저에 해당 지점의 콘텐츠를 표시. '#'(fragment identifier, 부분 식별자) 이후 부분은 서버에 전송되지 않음. 예) https://docs.djangoproject.com/en/5.2/intro/install/#quick-install-guide 에서 #quick-install-guide는 서버에 전달되지 않고 브라우저가 해당 지점으로 이동하도록 함

3-1HTTP Request Methods

3-2HTTP response status codes

특정 HTTP 요청이 성공적으로 완료되었는지 여부를 나타냄. 클라이언트가 서버에 요청을 보내면, 서버는 요청이 성공했는지 실패했는지를 숫자로 알려주고, 클라이언트는 이 코드를 보고 어떤 일이 일어났는지 판단합니다.

범위분류의미
100-199Informational responses계속 진행 중이라는 중간 응답
200-299Successful responses정상적으로 처리되었음
300-399Redirection messages리소스가 다른 위치로 이동했을 때
400-499Client error responses클라이언트 요청에 문제가 있을 때
500-599Server error responses서버 내부의 문제로 요청을 처리하지 못했을 때
이 장에서 쓰는 코드 — 200 OK · 201 Created · 204 No Content · 400 Bad Request · 404 Not Found · 405 Method Not Allowed

자원의 표현 — JSON 데이터 응답

응답 데이터 타입의 변화 · 사전 준비 · Python으로 JSON 처리하기

4-1그동안 서버가 응답(자원을 표현)했던 것

  • 지금까지 Django 서버는 사용자에게 페이지(HTML)만 응답하고 있었음
  • 하지만 서버가 응답할 수 있는 것은 페이지뿐 아니라 다양한 데이터 타입이며, REST API는 이 중에서도 JSON 타입으로 응답하는 것을 권장

JSON — 데이터를 구조화된 텍스트 형태로 표현하는 형식. 데이터만을 전달하기 위한 최소한의 형식이라 어떤 클라이언트와도 언어와 플랫폼에 독립적으로 통신할 수 있음

응답 데이터 타입의 변화 (1~4/4)
  1. 페이지(HTML)만을 응답하는 서버 — 사용자가 웹 브라우저로 요청하면 서버가 HTML 페이지를 만들어 응답
  2. JSON 데이터를 응답하는 REST API 서버로의 변환 — 서버는 HTML 페이지를 만들지 않고 JSON 데이터만 응답. HTML 대신 JSON을 전달하므로 응답 용량이 줄고, 화면을 그리는 일은 클라이언트가 맡게 됨
  3. Django는 더 이상 화면(Template)을 그리는 역할을 하지 않음 — 대신 오직 데이터(JSON)만을 응답. 화면은 Vue 같은 Front-end 프레임워크가 전담하며, 전통적인 MTV 구조(서버가 화면까지 그리는 방식)에서 'Front-end / Back-end 분리' 구조로의 전환을 의미
  4. 이제부터 Django를 사용해 RESTful API 서버를 구축

5-1Django REST framework (DRF)

Django에서 RESTful API 서버를 쉽게 구축할 수 있도록 도와주는 오픈소스 라이브러리.

가구를 직접 만들려면 톱, 망치, 설계도, 재료가 모두 필요하지만, 조립식 가구는 드라이버 하나만 있으면 누구나 간단히 완성할 수 있습니다. DRF는 이처럼 복잡한 API 서버 개발 과정을 표준화하고 자동화하여, 초보자도 빠르고 안정적으로 RESTful API를 구현할 수 있도록 도와주는 개발 도구 세트입니다.

5-5ModelSerializer

# articles/views.py — article_list view 함수 구조 변경 (method에 따른 분기처리)
from rest_framework import status

@api_view(['GET', 'POST'])
def article_list(request):
    if request.method == 'GET':
        articles = Article.objects.all()
        serializer = ArticleListSerializer(articles, many=True)
        return Response(serializer.data)

    elif request.method == 'POST':
        serializer = ArticleSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

생성할 때는 입력받을 필드를 검사하고, 저장된 결과를 전체 정보로 돌려주어야 하므로 ArticleSerializer를 사용합니다. Postman에서 POST http://127.0.0.1:8000/api/v1/articles/ 에 form-data(title, content)로 요청 후, 새로 생성된 게시글을 GET으로 확인합니다 (article pk는 상황마다 다를 수 있음).

6-9DELETE (1~2/2) — 게시글 삭제

요청에 대한 데이터 삭제가 성공했을 경우 204 No Content 응답 (요청은 성공했지만, 클라이언트에게 보낼 콘텐츠가 없음을 나타내는 상태 코드).

# articles/views.py
@api_view(['GET', 'DELETE'])
def article_detail(request, article_pk):
    article = Article.objects.get(pk=article_pk)
    if request.method == 'GET':
        serializer = ArticleSerializer(article)
        return Response(serializer.data)

    elif request.method == 'DELETE':
        article.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)
DELETE 응답 시 Response 구성 방식
  • Response()는 기본적으로 data 인자를 필수로 하지 않음 (data=None, status=None, ...)
  • 아무런 데이터도 넘기지 않을 경우엔 응답 상태 코드만으로 결과를 전달
  • 첫 번째 인자를 비운 상태로 두 번째 인자에 값을 전달할 수 없으므로 status= 키워드로 작성

6-10DELETE 후 데이터를 반환하는 방법

  • 일반적으로 DELETE 요청은 204 No Content로 본문 없이 응답하는 것이 RESTful한 설계방식
  • 하지만 클라이언트에서 삭제 대상 데이터를 확인하거나, UI에서 알림 메시지로 활용할 경우(예: "게시글 'Django 소개'가 삭제되었습니다.") 삭제된 객체의 정보를 함께 반환해야 할 수도 있음
  • DELETE에서도 응답이 필요한 경우엔 204 대신 200 OK 상태 코드와 함께 데이터를 반환. 단, REST 원칙상 기본은 응답 없음(204)이므로 목적이 명확할 때만 사용
@api_view(['GET', 'DELETE'])
def article_detail(request, article_pk):
    article = Article.objects.get(pk=article_pk)
    ...
    elif request.method == 'DELETE':
        # 1. 반환할 데이터를 삭제 전에 미리 변수로 저장
        pk = article.pk
        title = article.title
        article.delete()
        data = {
            'delete': f'{pk}번 게시글 "{title}"이 삭제되었습니다.',
        }
        # 2. Response의 첫 번째 인자로 전달
        return Response(data, status=status.HTTP_200_OK)
delete() 실행 시 해당 객체는 데이터베이스에서 삭제되므로, 필요한 값은 삭제 전에 미리 변수로 저장해 두고 삭제 이후에는 변수만 사용하는 것이 더 안정적입니다.

학습 시작 — 가게와 리뷰를 API로 잇기

Onboarding · 학습 목표

"배달 앱의 한 가게에는 리뷰가 몇 개나 달릴까요?"

치킨집 하나에는 리뷰가 수십 개 달리지만, 리뷰 하나는 반드시 한 가게에만 속해요.

  1. 가게와 리뷰는 N(리뷰):1(가게) 관계입니다.
  2. 리뷰 쪽에 ForeignKey를 두어 "이 리뷰는 어느 가게의 것인지"를 기록합니다.
  3. 리뷰를 작성할 때 어느 가게의 리뷰인지는 주소(URL)로 정해지므로, read_only_fields로 클라이언트가 직접 바꾸지 못하게 보호할 수 있어요.
  4. 가게 상세 정보를 조회할 때 역참조를 활용해 그 가게의 리뷰 목록을 함께 보여줄 수 있어요.
  5. SerializerMethodField로 가공된 데이터(예: 총 리뷰 수)를 함께 제공할 수도 있습니다.
학습 목표
  • DRF에서 N:1 관계를 표현하는 방법을 이해한다.
  • 외래 키(ForeignKey)를 사용하는 모델 구조를 설계할 수 있다.
  • 댓글 데이터를 조회(GET), 생성(POST), 수정(PUT), 삭제(DELETE)하는 API를 구현할 수 있다.
  • read_only_fields를 활용해 클라이언트의 수정이 불가능한 필드를 설정할 수 있다.
  • SerializerMethodField를 사용해 응답에 추가적인 정보를 포함하는 방법을 익힌다.
  • 역참조를 통해 부모 객체에서 자식 객체 목록 또는 개수를 응답에 포함하는 방법을 사용할 수 있다.
  • annotate를 사용해 모델 데이터를 집계하고, Serializer에서 이를 활용할 수 있다.
  • get_object_or_404, get_list_or_404를 활용해 예외 처리를 구현할 수 있다.

8-7읽기 전용 필드 (read_only_fields)

서버가 조회 요청에 대한 응답 시에만 값을 표시하는 필드.

read_only_fields는 클라이언트가 입력해서는 안 되는 필드를 응답 전용 필드로 지정할 때 사용합니다. view에서 값을 직접 주입할 필드는 반드시 read_only_fields로 지정해 주세요. 그렇지 않으면 DRF는 해당 필드 값이 빠졌다고 판단해 400 에러를 발생시킵니다.
사용 목적
  • 클라이언트 측에서 직접 수정하면 안 되는 경우
  • 서버 로직에 의해 자동 생성·관리되는 값 활용
  • 입력은 받지 않지만 정보를 제공해야 하는 경우
  • 새로운 필드 값(추가 계산, 가공)을 만들어 제공해야 하는 경우
특징 및 주의사항
  • 유효성 검사에서 제외됨 — 클라이언트가 보내는 요청 데이터에서 고려되지 않으므로, 클라이언트가 해당 필드에 값을 넣어도 무시되며 검증 오류를 일으키지 않음
  • 생성·수정 요청 모두에서 적용 가능 — 생성(POST) 단계에서만 의미 있는 것이 아니라, 수정(PUT) 요청에서도 해당 필드는 여전히 클라이언트 입력을 받지 않고 응답 시에만 노출됨

def comment_detail(request, comment_pk):

    if request.method == 'GET':
        serializer = CommentSerializer(comment)

        if serializer.is_valid(raise_exception=True):

        return Response(status=status.HTTP_204_NO_CONTENT)

9-1댓글 조회 시 게시글 출력 내역 변경 (1~3/5)

목표: 댓글 조회 시 게시글 번호만 제공하는 것이 아니라 '게시글의 제목'까지 제공하기. "article": 20 → "article": { "title": "..." }

  • Comment는 Article과 N:1 관계를 맺고 있고, DRF의 ModelSerializer는 외래 키 필드를 기본적으로 id(PrimaryKeyRelatedField)로 표현함
  • Serializer는 DRF에서 응답 구조를 결정하는 주체 — 어떤 필드를 포함할지(fields = ('id', 'title', 'content',)) 지정할 수 있고, 특정 필드를 어떤 형식으로 보여줄지도 지정할 수 있음. 즉 article 필드가 "id가 아닌 게시글의 제목"을 보여주도록 지정할 수도 있음
  • 하지만 CommentSerializer는 Comment의 정보만 가지고 있을 뿐 Article에 대한 정보는 없음 → Article의 정보를 포함하고, 그 중 title 필드만 담는 Serializer를 별도로 정의해야 함
# articles/serializers.py
class ArticleTitleSerializer(serializers.ModelSerializer):
    class Meta:
        model = Article
        fields = ('title',)

9-2댓글 조회 시 게시글 출력 내역 변경 (4~5/5)

ArticleTitleSerializer는 어디에 정의해야 할까? CommentSerializer에서만 사용할 용도라면 굳이 독립적으로 선언할 필요가 없습니다. 코드의 응집도를 높이고 명확한 범위를 지정하기 위해 CommentSerializer 내부에 정의합니다.

# articles/serializers.py
class CommentSerializer(serializers.ModelSerializer):
    class ArticleTitleSerializer(serializers.ModelSerializer):
        class Meta:
            model = Article
            fields = ('title',)

    # Comment 모델의 article 필드를 ArticleTitleSerializer로 재정의
    article = ArticleTitleSerializer(read_only=True)

    class Meta:
        model = Comment
        fields = '__all__'
        # read_only_fields = ('article',)

이제 article 필드는 게시글의 title 필드만 포함한 구조로 응답합니다. GET http://127.0.0.1:8000/api/v1/comments/1/ → "article": { "title": "Water behavior return interesting ..." }

9-3읽기 전용 필드 지정 주의사항

  • 특정 필드를 재정의 혹은 추가한 경우 read_only_fields는 동작하지 않음
  • 이런 경우 새로운 필드에 read_only 키워드 인자로 작성해야 함 (위 코드의 ArticleTitleSerializer(read_only=True))

10-1Article → Comment 간 역참조 관계를 활용한 JSON 데이터 재구성

  1. 단일 게시글 조회 시 해당 게시글에 작성된 댓글 목록도 함께 붙여서 응답
  2. 단일 게시글 조회 시 해당 게시글에 작성된 댓글 개수도 함께 붙여서 응답

10-21. 단일 게시글 + 댓글 목록 (1~2/2) — Nested relationships

  • 모델 관계상으로 참조하는 대상(N)은 참조되는 대상(1)의 표현에도 포함되거나 중첩될 수 있음
  • Comment가 Article에 대한 참조를 article field로 표현했듯, Article도 자신을 참조하고 있는 Comment들에 대한 정보를 역참조 매니저를 통해 표현할 수 있음
# articles/serializers.py
class ArticleSerializer(serializers.ModelSerializer):
    class CommentDetailSerializer(serializers.ModelSerializer):
        class Meta:
            model = Comment
            fields = ('id', 'content',)

    comment_set = CommentDetailSerializer(many=True, read_only=True)

    class Meta:
        model = Article
        fields = '__all__'
필드 이름을 역참조 매니저 이름('comment_set')과 똑같이 작성해야 DRF가 해당 데이터를 찾아옵니다.

GET http://127.0.0.1:8000/api/v1/articles/2/ → "comment_set": [ { "id": 14, "content": "..." }, ... ]

10-32. 단일 게시글 + 댓글 개수 — 문제 상황

  • 기본적으로 게시글(Article)을 조회하면 참조 중인 댓글(Comment)의 개수는 알 수 없음
  • Comment 모델과의 관계는 Article.comment_set으로 연결되지만, 댓글의 개수를 저장하는 별도 필드는 Article 모델에 정의한 적이 없기 때문
  • 따라서 댓글 수를 응답하려면 직접 계산해서 응답에 포함시켜야 함

10-4View 로직 개선: annotate 사용

annotate는 Django ORM 함수로, SQL의 집계 함수를 활용하여 쿼리 단계에서 데이터 가공을 수행합니다. view에서 Article 객체를 조회할 때 annotate로 num_of_comments 필드를 추가합니다.

# articles/views.py
from django.db.models import Count

@api_view(['GET', 'DELETE', 'PUT'])
def article_detail(request, article_pk):
    article = Article.objects.annotate(num_of_comments=Count('comment')).get(pk=article_pk)
    ...
  • 조회와 동시에 댓글 수를 세어 num_of_comments라는 필드를 추가
  • 이제 serializer.data가 반환하는 article 객체에는 num_of_comments라는 "주석(annotation) 필드"가 포함되어 있음
Count('comment')의 'comment'는 Article을 참조하고 있는 모델 Comment의 소문자 표기입니다 (역참조 매니저 이름 'comment_set'과 다름).

10-5annotate 필드를 serializer에 추가하려면?

  • 단순히 fields = '__all__'만으로는 annotate된 필드가 포함되지 않음
  • annotate()는 실제 모델 필드를 생성하지 않음 — 쿼리 시점에만 존재하는 임시 필드를 추가하는 기능. 즉 Article 모델 클래스에는 num_of_comments라는 필드가 실제로 존재하지 않음
  • __all__은 모델의 필드 기준으로 작동하기 때문에 annotate로 만들어진 필드는 포함되지 않음
  • 이런 동적으로 계산된 필드를 응답에 포함하려면 SerializerMethodField를 사용할 수 있음 (또는 num_of_comments = serializers.IntegerField(read_only=True)로 작성)

10-6Serializer 개선: SerializerMethodField 사용 (1~2/2)

# articles/serializers.py
class ArticleSerializer(serializers.ModelSerializer):
    ...
    num_of_comments = serializers.SerializerMethodField()

    class Meta:
        model = Article
        fields = '__all__'

    def get_num_of_comments(self, obj):
        # obj: 지금 직렬화 중인 Article 인스턴스
        # 1. view에서 annotate로 개수를 미리 계산했다면 그 값을 사용
        if hasattr(obj, 'num_of_comments'):
            return obj.num_of_comments
        # 2. annotate 없이 들어온 경우(예: 게시글 생성)
        return obj.comment_set.count()
  • SerializerMethodField는 읽기 전용 필드를 커스터마이징하는 데 사용
  • 이 필드를 선언한 뒤 get_<필드명> 메서드를 정의하면, 해당 메서드의 반환 값이 직렬화 결과에 포함됨
  • view에서 data를 딕셔너리로 변환하거나 수정할 필요 없이 serializer.data를 바로 반환해도 최종 JSON에 num_of_comments 값이 반영됨
왜 hasattr로 먼저 확인할까? 같은 ArticleSerializer를 게시글 생성(POST)에서도 사용합니다. 새로 만든 게시글은 annotate를 거치지 않아 num_of_comments가 없기 때문에, 그대로 꺼내면 AttributeError가 발생합니다.

GET http://127.0.0.1:8000/api/v1/articles/3/ → 응답에 "num_of_comments": 3 포함 확인.

10-7SerializerMethodField

Serializer에서 추가적인 데이터 가공을 하고 싶을 때 사용. 예를 들어 특정 필드 값을 조합해 새로운 문자열 필드를 만들거나 부가적인 계산(비율, 합계, 평균)을 하는 경우에 활용합니다.

동작 원리

SerializerMethodField를 Serializer 클래스 내에서 필드로 선언하면, DRF는 get_<필드명>이라는 이름을 가진 메서드를 자동으로 찾습니다. 예를 들어 full_name = serializers.SerializerMethodField()라고 선언하면 DRF는 get_full_name(self, obj) 메서드를 찾아 해당 값을 직렬화 결과에 넣어 줍니다. obj는 현재 직렬화 중인 모델 인스턴스이며, 이 메서드에서 obj의 필드나 annotate된 필드를 활용해 값을 만듭니다.

class UserSerializer(serializers.ModelSerializer):
    full_name = serializers.SerializerMethodField()

    class Meta:
        model = User
        fields = ('id', 'username', 'full_name', 'email',)

    def get_full_name(self, obj):
        return f'{obj.first_name} {obj.last_name}'

10-8SerializerMethodField 주의사항 · 사용 목적

주의사항
  • 읽기 전용 — 생성(POST), 수정(PUT) 요청 시에는 사용되지 않음
  • get_ 메서드 — 메서드는 반드시 (self, obj) 형태로 정의해야 하며, obj는 현재 직렬화 중인 모델 인스턴스를 의미
  • 메서드 안에서 obj에 없을 수도 있는 값(annotate 결과 등)을 사용할 때는 hasattr로 먼저 확인
사용 목적
  • 다양한 계산 로직을 손쉽게 추가 가능 — 데이터 변환 로직을 Serializer 내부 메서드로 명확히 분리
  • 표현(응답 모양)과 관련된 가공은 Serializer에 모아 관리 — view에서 별도로 data 수정 없이도 직렬화 결과를 제어

10-9역참조 데이터 구성 참고 — related_name을 바꿨다면

11-1OpenAPI Specification (OAS)

RESTful API를 설명하고 시각화하는 표준화된 방법 → API에 대한 세부사항을 기술할 수 있는 공식 표준.

OAS 기반 API에 대한 문서를 생성하는 데 도움을 주는 오픈소스 프레임워크: Swagger, Redoc.

11-2"설계 우선" 접근법 — OAS의 핵심 이점

  • API를 먼저 설계하고 명세를 작성한 후, 이를 기반으로 코드를 구현하는 방식
  • OAS를 사용하면 API가 어떻게 작동하는지를 시각적으로 보여주는 문서를 생성할 수 있으며, 이는 API를 이해하고 테스트하는 데 매우 유용 — 이런 목적으로 사용되는 도구가 Swagger-UI 또는 ReDoc

12-1Django shortcuts — get_object_or_404()

Django shortcuts: render() · redirect() · get_object_or_404() · get_list_or_404()

get_object_or_404() — 모델 manager objects에서 get()을 호출하지만, 해당 객체가 없을 땐 기존 DoesNotExist 예외 대신 Http404를 raise함.

# articles/views.py
from django.shortcuts import get_object_or_404

# 기존 — 조회 대상이 없는 경우 500 Server Error 반환
article = Article.objects.get(pk=article_pk)
comment = Comment.objects.get(pk=comment_pk)

# 적용 — 조회 대상이 없는 경우 404 Not Found 반환
article = get_object_or_404(Article, pk=article_pk)
article = get_object_or_404(
    Article.objects.annotate(num_of_comments=Count('comment')),
    pk=article_pk,
)
comment = get_object_or_404(Comment, pk=comment_pk)

12-2get_list_or_404()

모델 manager objects에서 filter()의 결과를 반환하고, 해당 객체 목록이 없을 땐 Http404를 raise함.

# articles/views.py
from django.shortcuts import get_list_or_404

# 기존 — 조회 대상 목록이 없어도 200 OK 반환
articles = Article.objects.all()
comments = Comment.objects.all()

# 적용 — 조회 대상이 없는 경우 404 Not Found 반환
articles = get_list_or_404(Article)
comments = get_list_or_404(Comment)
전체 목록 조회에서 결과가 없으면 200 + []가 일반적입니다. get_list_or_404()는 "이 조건의 데이터는 반드시 있어야 하는 상황"(예: 존재하지 않는 게시글의 댓글 목록 요청)에 사용합니다.

12-3왜 사용해야 할까?

  • get_object_or_404()를 사용하지 않은 경우 — 클라이언트에게 "서버에 오류가 발생하여 요청을 수행할 수 없다(500)"라는 원인이 정확하지 않은 에러를 제공하게 되어, 클라이언트의 요청이 올바르지 않았음에도 서버의 문제로 오해할 수 있음
  • get_list_or_404()를 사용하지 않은 경우 — 조건에 맞는 데이터가 하나도 없는데도 단순히 빈 리스트를 응답받으면, 클라이언트는 요청이 올바르지 않았는지 진짜 데이터가 없는 건지 명확하게 판단하기 어려움

적절한 예외 처리를 통해 클라이언트에게 보다 정확한 에러 내용을 전달하는 것은 매우 중요한 개발 요소입니다. 조건에 맞는 객체가 하나도 없을 경우 명확하게 404를 반환해야 "해당 조건에 맞는 리소스가 존재하지 않는다"는 정확한 상황을 전달할 수 있습니다.

12-4View와 Serializer의 역할

  • view와 queryset 로직에서는 비즈니스 로직(데이터 가공, annotate, 필터링)을 처리
  • serializer는 그 결과물을 직렬화하는 역할에 집중하는 것이 일반적인 권장사항
  • 복잡한 query나 로직은 View 함수에서 진행 — 여러 모델을 조인하거나 복잡한 집계가 필요한 경우 View 함수에서 처리
  • 필요한 경우 View 함수에서 select_related()나 prefetch_related()로 query를 최적화

12-5왜 DRF를 배웠을까?

  • 백엔드와 프론트엔드의 분리 경험 — 기존 Django 템플릿 기반의 서버 렌더링 방식을 벗어나, 백엔드(데이터·로직)와 프론트엔드(화면)를 명확히 분리하는 방식을 간접적으로 체험
  • 표준화된 API 구축 역량 확보 — DRF로 RESTful API를 손쉽게 만들고 관리하는 방법을 학습했고, 이는 다양한 클라이언트(웹, 모바일 앱, 외부 서비스)와 연동하는 데 필수적인 능력
  • 프론트엔드 기술과의 연결 고리 — JavaScript·Vue는 주로 API를 통해 데이터를 받아와 화면을 구성하며, DRF로 구축한 일관된 API는 Vue 등 프론트엔드 프레임워크와 매끄럽게 호환됨

정답 · 해설 보기
b) 모델 객체가 없을 때 404로 처리하기 위해 — get_object_or_404()는 객체가 존재하지 않을 경우 Http404를 발생시킨다. 이를 통해 API는 500 오류가 아닌, 클라이언트가 이해할 수 있는 404 상태 코드를 반환할 수 있다.
22. get_list_or_404()의 특징으로 옳지 않은 것은?
  1. 조건에 맞는 객체가 없으면 404 응답을 반환한다
  2. 내부적으로 filter()를 사용한다
  3. 항상 빈 리스트를 반환한다
  4. 목록 응답에서도 404 처리를 적용할 수 있다
정답 · 해설 보기
c) 항상 빈 리스트를 반환한다 — get_list_or_404()는 filter() 결과가 비어 있을 경우, 빈 리스트가 아닌 404 예외를 발생시킨다. 클라이언트는 리소스가 없음을 명확하게 인식할 수 있다.
23. 다음 중 SerializerMethodField의 특징으로 적절하지 않은 것은?
  1. 읽기 전용 필드이다
  2. get_<필드명>() 형태의 메서드가 필요하다
  3. annotate 없이도 모델 필드처럼 저장된다
  4. 응답 데이터에 동적으로 생성된 값을 추가할 수 있다
정답 · 해설 보기
c) annotate 없이도 모델 필드처럼 저장된다 — SerializerMethodField는 읽기 전용이며, 모델 필드처럼 저장되거나 DB에 존재하는 값이 아니다. view나 다른 로직에서 annotate로 값을 제공하거나, 메서드 내부에서 계산해 반환해야 한다. annotate 없이 그대로 참조하면 오류가 난다.
24. 다음 중 읽기 전용 필드를 정의하는 방식으로 옳은 것은?
  1. title = serializers.CharField(read_only=True)
  2. read_only_fields = ('title')
  3. fields = ['id'], read_only = True
  4. fields = '__all__', required=False
정답 · 해설 보기
a) title = serializers.CharField(read_only=True) — read_only_fields는 Meta에서 필드명을 나열하는 방식이고, 필드를 명시적으로 정의했다면 직접 read_only=True를 설정해야 한다. 특히 재정의 필드나 중첩 serializer에서 이 방식이 필요하다. (b는 쉼표가 없어 튜플이 아니라 문자열이다.)
25. 다음 코드 실행 결과로 올바른 응답 형태는? (CommentSerializer 안에 ArticleTitleSerializer(fields = ('title',))를 정의하고 article = ArticleTitleSerializer(read_only=True), Meta는 Comment / '__all__')
  1. "article": { "title": "..." }
  2. "article": { "id": 3 }
  3. "article": 3
  4. "article": "게시글 제목"
정답 · 해설 보기
a) "article": { "title": "..." } — article 필드를 중첩 serializer로 정의했기 때문에 응답 결과에서 article은 숫자가 아닌 JSON 객체로 출력된다. 이 객체에는 'title' 필드만 포함되도록 설정했으므로 { "title": "..." } 형태로 응답된다.
26. 다음 코드에서 유효성 검사 오류가 발생하는 원인은? @api_view(['POST']) def comment_create(request, article_pk): serializer = CommentSerializer(data=request.data); if serializer.is_valid(raise_exception=True): serializer.save(); return Response(serializer.data, status=201)
  1. article 필드가 read_only로 되어 있어서
  2. article 값을 클라이언트가 누락했기 때문에
  3. article을 serializer.save()에 전달하지 않았기 때문에
  4. CommentSerializer가 존재하지 않기 때문에
정답 · 해설 보기
c) article을 serializer.save()에 전달하지 않았기 때문에 — Comment 모델의 필수 필드인 article이 read_only_fields로 지정되어 있어 클라이언트 요청에서는 입력되지 않는다. 따라서 view에서 serializer.save(article=article)처럼 명시적으로 값을 넘겨주지 않으면 누락된 필드 오류가 발생한다.
27. 다음 코드에서 get_object_or_404를 사용하는 목적은? article = get_object_or_404(Article, pk=article_pk)
  1. article이 존재하지 않으면 빈 리스트를 반환하기 위해
  2. 존재하지 않는 article에 대한 요청을 404로 응답하기 위해
  3. article이 없을 경우 자동으로 500 오류를 발생시키기 위해
  4. article 모델을 serializer에 자동 등록하기 위해
정답 · 해설 보기
b) 존재하지 않는 article에 대한 요청을 404로 응답하기 위해 — get_object_or_404()는 get()처럼 객체를 가져오되, 대상이 없을 경우 Http404 예외를 발생시켜 클라이언트에게 명확한 "리소스를 찾을 수 없음(404)" 상태를 전달한다. 서버 오류(500)가 아닌 정확한 응답 처리를 위한 도구이다.
28. 다음 serializer 정의에 대한 설명으로 옳은 것은? (num_of_comments = serializers.SerializerMethodField(), def get_num_of_comments(self, obj): return obj.num_of_comments)
  1. num_of_comments는 모델 필드로 저장된다.
  2. annotate() 없이도 항상 응답에 포함된다.
  3. view에서 annotate가 누락되면 오류가 발생할 수 있다.
  4. SerializerMethodField는 클라이언트로부터 입력을 받는다
정답 · 해설 보기
c) view에서 annotate가 누락되면 오류가 발생할 수 있다. — 응답 시 get_num_of_comments()가 호출되어 obj.num_of_comments를 참조하는데, 이는 annotate로 추가한 필드이므로 view에서 annotate(num_of_comments=Count(...))를 하지 않으면 해당 속성이 없어 AttributeError가 발생한다. (그래서 강의 코드는 hasattr로 먼저 확인한다.)
29. 다음 코드 실행 결과로 올바른 설명은? (단, Comment 모델에서 related_name='comments'로 설정된 경우) Article.objects.annotate(num_of_comments=Count('comments'))
  1. 댓글 개수를 계산할 수 없다
  2. annotate된 필드는 serializer에 자동으로 포함된다
  3. Article 모델의 필드가 추가된다
  4. num_of_comments 필드는 쿼리 결과에만 존재한다
정답 · 해설 보기
d) num_of_comments 필드는 쿼리 결과에만 존재한다 — annotate로 추가된 필드는 모델 정의에는 존재하지 않고 쿼리 결과에만 임시로 붙는 필드이다. 저장되지 않으며, serializer에서 사용하려면 SerializerMethodField 등을 통해 수동으로 포함해야 한다.

이 문서의 큰 줄기

  • API는 소프트웨어끼리 약속된 형식으로 대화하는 창구이고, REST는 그 약속을 통일하자는 설계 방법론이다.
  • REST API = 식별(URI) + 행위(HTTP Method) + 표현(JSON). URL에는 자원의 위치만, 동작은 메서드로 구분한다. 결과는 상태 코드(2xx 성공 · 4xx 클라이언트 · 5xx 서버)로 알린다.
  • Django는 화면 대신 JSON만 응답하는 서버가 되고, 화면은 프론트엔드가 맡는다(Front/Back 분리).
  • DRF: Serializer(=JSON용 ModelForm)로 직렬화·검증·저장 → @api_view로 메서드 제한 → Response(data, status=...)로 응답.
  • CRUD 응답 코드: GET 200 · POST 201(실패 400) · PUT/PATCH 200 · DELETE 204. 부분 수정은 partial=True+PATCH, 검증 실패 응답은 is_valid(raise_exception=True)로 줄일 수 있다.

개념설명예시
ForeignKey다른 모델을 참조하여 관계를 설정하는 필드article = models.ForeignKey(Article, ...)
역참조 (related name)참조된 모델에서 역으로 연결된 데이터를 조회할 수 있게 하는 속성article.comment_set, related_name='comments'

annotate쿼리 단계에서 집계 계산 필드를 동적으로 생성하는 ORM 함수annotate(num_of_comments=Count('comment'))

이 문서의 큰 줄기

  • N:1 API: 댓글 생성은 articles/<pk>/comments/로 받고, 외래 키는 클라이언트가 아니라 view가 serializer.save(article=article)로 넣는다. 그래서 article은 read_only_fields(안 하면 400).
  • 응답 모양 바꾸기: article을 중첩 Serializer(ArticleTitleSerializer(read_only=True))로 재정의하면 id 대신 제목이 나온다. 재정의·추가한 필드에는 read_only_fields가 안 먹으므로 read_only=True 인자를 쓴다.
  • 역참조 데이터: 목록은 comment_set = CommentDetailSerializer(many=True, read_only=True)(이름을 매니저명과 같게), 개수는 view의 annotate(Count('comment')) + SerializerMethodField(hasattr로 방어).
  • 문서화: drf-spectacular로 OAS 스키마를 만들고 Swagger-UI·ReDoc으로 본다(Code First).
  • 정확한 에러: get_object_or_404로 500 대신 404. 가공·집계·최적화는 View, 표현은 Serializer.
