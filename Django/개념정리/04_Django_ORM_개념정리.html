1

ORM

Object-Relational Mapping · 언어 차이 문제 · Django의 데이터 상호작용

1-1ORM이란?

ORM (Object-Relational Mapping) — 객체 지향 프로그래밍 언어의 객체(Object)와 데이터베이스의 데이터를 매핑(Mapping)하는 기술.

매핑(Mapping) — 서로 다른 형태를 가진 코드 상의 '객체'와 데이터베이스의 '테이블(데이터)'이 서로 1:1로 대응되도록 연결해 주는 것

문제 상황: 언어 차이로 인한 소통 불가

Django는 Python 언어를 사용하지만 데이터베이스는 SQL 언어를 사용합니다. ORM은 마치 외국인과 대화할 때 '통역사'가 중간에서 언어를 번역해 주는 것과 같습니다.

Django (Python Object)⇄ORM (통역사)⇄DB (SQL)
Tip — 덕분에 개발자는 SQL을 직접 작성하지 않고도 파이썬 코드로 데이터를 다룰 수 있습니다. 코드 작성 시간을 줄이고, 실수를 줄이는 데 큰 도움을 줍니다.

1-2Django의 데이터 상호작용: ORM이 일하는 방법

ORM은 Django 개발자를 위해 'QuerySet API'라는 특별한 도구를 제공합니다. QuerySet API는 ORM의 기능을 개발자가 Python 코드 안에서 객체 지향적이고 직관적인 방식으로 조작할 수 있도록 제공하는 인터페이스입니다.

2

QuerySet API

QuerySet API · Query · QuerySet · 동작 방식 · 구문 구조

2-1QuerySet API란?

복잡한 SQL 쿼리 대신 직관적인 Python 코드로 데이터베이스에 요청할 수 있게 해주는 도구(인터페이스).

  • 개발자는 SQL을 직접 작성하지 않고도, .filter(), .exclude(), .order_by() 등 파이썬다운 메서드를 사용하여 원하는 데이터를 손쉽게 생성, 조회, 수정, 삭제할 수 있습니다.
  • 코드의 가독성을 높이고, 개발 생산성을 극대화하는 Django ORM의 핵심 기능입니다.

2-2Query

  • 데이터베이스에 특정한 데이터를 보여 달라는 요청
  • "쿼리문을 작성한다." = "원하는 데이터를 얻기 위해 데이터베이스에 요청을 보낼 코드를 작성한다."
Django에서 Query가 처리되는 과정
  1. 파이썬 코드 → ORM: 개발자의 QuerySet API(파이썬 코드)가 ORM에 전달
  2. ORM → SQL 변환: ORM이 이를 데이터베이스용 SQL 쿼리로 변환하여 데이터베이스에 전달
  3. DB 응답 → ORM: 데이터베이스가 SQL 쿼리를 처리하고 결과 데이터를 ORM에 반환
  4. ORM → QuerySet 변환: ORM이 데이터베이스의 결과를 QuerySet(파이썬 객체) 형태로 변환하여 개발자에게 전달

2-3QuerySet

  • Django ORM을 통해 만들어진 자료형
  • 데이터베이스에서 전달받은 객체 목록(데이터 모음)
  • 순회 가능한 데이터로 1개 이상의 데이터를 불러와 사용 가능 (0개면 빈 QuerySet)
  • 단, get()처럼 단일 객체를 조회하는 경우 QuerySet이 아닌 모델(Class)의 인스턴스로 반환됨
QuerySet API와 ORM의 동작 방식
  1. Django → DB: QuerySet API로 ORM을 통해 정보를 요청하면 SQL 쿼리로 변환되어 데이터베이스로 전달됨
  2. DB → Django: 데이터베이스가 응답을 보내면 ORM은 SQL 결과를 파이썬이 이해할 수 있는 Python Object(QuerySet 혹은 Instance)로 변환하여 Django로 반환

2-4QuerySet API 구문 기본 구조

Article.objects.all()
# Model class . Manager . QuerySet API
부분이름역할
Article모델 클래스데이터베이스 테이블에 대한 Python 클래스 표현. articles_article 테이블의 스키마(필드, 데이터 타입 등)를 정의하며, Django ORM이 데이터베이스와 상호작용하는 기본 단위
.objects매니저 (manager)모델 클래스와 데이터베이스 질의(쿼리 = 질문과 요청)를 연결해 주는 인터페이스. 모델 클래스가 데이터베이스 쿼리 작업을 수행할 수 있게 함. Django는 모든 모델에 objects라는 이름의 매니저를 자동으로 추가하며, 이 매니저를 통해 QuerySet API를 사용
.all()QuerySet API 메서드특정 데이터베이스 작업을 수행하는 메서드. 매니저를 통해 호출되는 메서드로, 결과로 QuerySet(혹은 인스턴스)을 반환

예시: "전체 게시글 받아줘" → Article.objects.all() → ORM → SQL(SELECT * FROM articles_article;) → DB → QuerySet

3-3Create — 데이터 객체를 만드는(생성하는) 3가지 방법

첫 번째 방법: 빈 객체 생성 후 값 할당 및 저장
>>> article = Article()          # Article(class)로부터 article(instance) 생성
>>> article
<Article: Article object (None)>
>>> article.title = 'first'      # 인스턴스 변수(title)에 값을 할당
>>> article.content = 'django!'  # 인스턴스 변수(content)에 값을 할당
# save를 하지 않으면 아직 DB에 값이 저장되지 않음
>>> article
<Article: Article object (None)>
>>> Article.objects.all()
<QuerySet []>

# save를 호출하고 확인하면 저장된 것을 확인
>>> article.save()
>>> article
<Article: Article object (1)>
>>> article.id
1
>>> article.pk
1
>>> Article.objects.all()
<QuerySet [<Article: Article object (1)>]>

# 인스턴스 article을 활용하여 인스턴스 변수 활용하기
>>> article.title
'first'
>>> article.content
'django!'
>>> article.created_at
datetime.datetime(2026, 12, 31, 6, 55, 42, 322526, tzinfo=datetime.timezone.utc)
두 번째 방법: 초기 값과 함께 객체 생성 및 저장
>>> article = Article(title='second', content='django!')
>>> article                       # 아직 저장 되어있지 않음
<Article: Article object (None)>
>>> article.save()                # save를 호출해야 저장됨
>>> article
<Article: Article object (2)>
>>> Article.objects.all()
<QuerySet [<Article: Article object (1)>, <Article: Article object (2)>]>
>>> article.pk
2

첫 번째 방법과 두 번째 방법 모두 결국 save 메서드를 호출해야 비로소 DB에 데이터가 저장됩니다 (테이블에 한 행(레코드)이 쓰여진 것).

세 번째 방법: create 메서드 활용
# 위 2가지 방법과 달리 생성과 동시에 저장되고, 생성된 객체를 반환
>>> Article.objects.create(title='third', content='django!')
<Article: Article object (3)>
  • save() 메서드 — 객체를 데이터베이스에 저장하는 인스턴스 메서드
  • save()가 필요한 경우 — 객체를 만든 뒤 저장 전에 값을 더 채우거나 바꿔야 할 때, 생성과 저장이 나뉘어 save()를 씀
  • create()가 save()를 명시적으로 호출하지 않는 것처럼 보이는 이유 — create() 메서드 자체가 객체 생성과 데이터베이스 저장을 한 번에 처리하는 단축 메서드이기 때문
주의 — save()는 입력값이 올바른지 검사하지 않고 그대로 저장합니다. 입력값 검사는 이후 Form에서 다룹니다.

3-4Read — 대표적인 조회 메서드

분류메서드설명

QuerySet 반환filter()주어진 매개변수와 일치하는 객체를 포함하는 QuerySet 반환

>>> Article.objects.filter(content='django!')

>>> Article.objects.get(pk=1)

get() 특징
  • 객체를 찾을 수 없으면 DoesNotExist 예외를 발생시키고, 둘 이상의 객체를 찾으면 MultipleObjectsReturned 예외를 발생시킴
  • 위와 같은 특징을 가지고 있기 때문에 primary key와 같이 고유성(uniqueness)을 보장하는 조회에서 사용해야 함

Primary key(pk) — DB 테이블에서 각 행을 고유하게 식별할 수 있는 속성. Django ORM에서는 id

3-5Update

# 수정할 인스턴스 조회
>>> article = Article.objects.get(pk=1)
# 인스턴스 변수를 변경
>>> article.title = 'byebye'
# 저장
>>> article.save()
# 정상적으로 변경된 것을 확인
>>> article.title
'byebye'
Tip — save()는 pk가 없으면 새로 생성(INSERT), pk가 있으면 수정(UPDATE)합니다. 그래서 Create와 Update 모두 save()를 사용합니다.

3-6Delete

# 삭제할 인스턴스 조회
>>> article = Article.objects.get(pk=1)
# delete 메서드 호출 (삭제된 개수와 모델별 삭제 개수가 튜플로 반환)
>>> article.delete()
(1, {'articles.Article': 1})
# 삭제한 데이터는 더이상 조회할 수 없음
>>> Article.objects.get(pk=1)

1번 글을 지운 뒤 새 글을 만들면 1번이 아니라 4번이 됩니다. 한 번 쓴 id는 다시 쓰지 않습니다.

ORM with view — 전체 게시글 조회

View 함수에서의 QuerySet API · 요청 정의 · 빈 문자열 path의 의미 · 전체 조회 구현

4-1View 함수에서 QuerySet API 활용하기

  • 웹 페이지에 보여줄 데이터를 DB에서 가져올 때 사용함
  • 사용자가 입력한 새로운 데이터를 DB에 저장할 때 사용함

2가지 Read(조회): ① 전체 게시글 조회(이번 시간) ② 단일 게시글 조회(다음 시간)

요청 흐름: http://127.0.0.1:8000/articles/ → urls → views(Model에서 데이터 조회) → template → 응답

4-2요청 정의와 구현

# crud/urls.py
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('articles/', include('articles.urls')),
]

# articles/urls.py
from django.urls import path
from . import views

app_name = 'articles'
urlpatterns = [
    path('', views.index, name='index'),
]

# articles/views.py
from .models import Article

def index(request):
    articles = Article.objects.all()
    context = {
        'articles': articles,
    }
    return render(request, 'articles/index.html', context)
<!-- templates/articles/index.html -->
<h1>Articles</h1>
<hr>
{% for article in articles %}
  <p>글 번호: {{ article.pk }}</p>
  <p>글 제목: {{ article.title }}</p>
  <p>글 내용: {{ article.content }}</p>
  <hr>
{% endfor %}
path에서 빈 문자열('')의 의미 — 프로젝트 urls.py에서 include("articles.urls")는 articles/로 시작하는 모든 요청을 articles 앱의 urls.py로 넘겨줍니다. 이때 articles/ 부분은 잘려나가고 나머지 URL만 앱의 urls.py로 전달됩니다. 따라서 path('', views.index)는 articles/ 바로 뒤에 아무것도 없는 경우(articles/ 자체)를 의미하여, 해당 view 함수를 실행하게 됩니다.

참고

Field lookups · ORM과 QuerySet API를 사용하는 이유

5-1Field lookups — 데이터 필터링의 마법

Query에서 조건을 구성하는 방법. 단순 동치 비교(=)를 넘어, '특정 단어가 포함된 제목', '특정 날짜 이후에 작성된 글' 등을 찾을 수 있게 해줍니다. 이를 통해 복잡한 데이터 조회도 파이썬 코드로 간결하고 강력하게 처리할 수 있습니다.

# title 필드가 'second'로 시작하는 Article 데이터(레코드)를 모두 찾고 싶다면?
Article.objects.filter(title__startswith='second')
#                      모델 필드명 __ 조회 조건 = 비교할 값

# "내용에 'dja'가 포함된 모든 게시글 조회"
Article.objects.filter(content__contains='dja')
# "제목이 he로 시작하는 모든 게시글 조회"
Article.objects.filter(title__startswith='he')
  • Field lookups는 모델의 필드 이름 뒤에 이중 밑줄(double underscore, __)을 붙이고, 원하는 조회 조건을 명시하는 방식으로 사용
  • filter(), exclude() 및 get()에 대한 키워드 인자로 지정, 손쉽게 필터링 로직을 구성
조회 조건의미
exact / iexactexact: 대소문자를 구분하여 정확히 일치하는 값을 찾음 · iexact: 대소문자 구분 없이(대소문자 무시) 정확히 일치

5-2ORM, QuerySet API를 사용하는 이유는?

  1. 데이터베이스 추상화 — 개발자는 특정 데이터베이스 시스템에 종속되지 않고 일관된 방식으로 데이터를 다룰 수 있음
  2. 생산성 향상 — 복잡한 SQL 쿼리를 직접 작성하는 대신 Python 코드로 데이터베이스 작업을 수행할 수 있음
  3. 객체 지향적 접근 — 데이터베이스 테이블을 Python 객체로 다룰 수 있어 객체 지향 프로그래밍의 이점을 활용할 수 있음

HTTP request methods

HTTP · GET · POST · 특징 비교 · POST로 변경

9-1HTTP request methods란?

HTTP — 네트워크 상에서 데이터(리소스)를 주고 받기 위한 약속. HTTP request methods는 데이터(리소스)에 어떤 요청(행동)을 원하는지를 나타내는 것으로, 서버에게 원하는 작업의 종류를 알려주는 역할을 합니다.

GETPOST
리소스 조회 · URL에 데이터가 노출됨 · 캐싱 가능데이터 생성/전송 · URL에 데이터가 드러나지 않음

캐싱 — 자주 사용하는 데이터나 결과를 임시로 저장해두고 재활용하여 처리 속도를 높이는 기술 · https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods

9-2GET Method

서버로부터 데이터를 요청하고 받아오는(조회) 데 사용. 주로 검색 쿼리 전송, 웹 페이지 요청, 그리고 API에서 데이터를 조회하는 것과 같이 서버로부터 데이터를 요청하고 받아오는 데 사용됩니다.

  1. 데이터 전송 — URL의 쿼리 문자열(Query String)을 통해 데이터를 전송 (예: /articles/create/?title=제목&content=내용)
  2. 데이터 제한 — URL 길이에 제한이 있어 대량의 데이터 전송에는 적합하지 않음
  3. 브라우저 히스토리 — 요청 URL이 브라우저 히스토리에 남음
  4. 캐싱 — 브라우저는 GET 요청의 응답을 로컬에 저장할 수 있음. 동일한 URL로 다시 요청할 때, 서버에 접속하지 않고 저장된 결과를 사용. 페이지 로딩 시간을 크게 단축

9-3POST Method

서버에 데이터를 제출하여 리소스를 변경(생성, 수정, 삭제)하는 데 사용. 주로 로그인 정보 제출, 파일 업로드, 새 데이터 생성(예: 새 게시글 작성), API에서 데이터 변경을 요청하는 것과 같이 클라이언트가 서버로 데이터를 전송하여 서버의 상태를 변경할 때 사용됩니다.

  1. 데이터 전송 — HTTP Body를 통해 데이터를 전송
  2. 데이터 제한 — GET에 비해 더 많은 양의 데이터를 전송할 수 있음
  3. 브라우저 히스토리 — POST 요청은 브라우저 히스토리에 남지 않음
  4. 캐싱 — POST 요청은 기본적으로 캐시할 수 없음. POST 요청이 일반적으로 서버의 상태를 변경하는 작업을 수행하기 때문
HTML form은 GET과 POST만 지원하기 때문에, 데이터 생성·수정·삭제를 모두 POST로 처리합니다. 수정은 PUT, 삭제는 DELETE처럼 더 세분화된 메서드는 추후 REST API 시간에 다룹니다.

9-4'GET' & 'POST' Method 정리 · Create 로직을 POST로 변경

GET과 POST는 각각의 특성에 맞게 적절하게 사용해야 합니다. GET은 데이터 조회, POST는 데이터 생성이나 수정에 주로 사용합니다.

10

HTTP response status code · CSRF

status code · 403 Forbidden · CSRF 공격과 방어 · csrf_token · 왜 POST일 때만?

10-1HTTP response status code

서버가 클라이언트의 요청에 대한 처리 결과를 나타내는 3자리 숫자.

403 Forbidden — 서버에 요청이 전달되었지만, 권한 때문에 거절되었다는 것을 의미합니다.

403으로 거절된 이유 — "CSRF token이 누락되었다"라는 응답.

https://developer.mozilla.org/en-US/docs/Web/HTTP/Status

10-2CSRF (Cross-Site-Request-Forgery)

사이트 간 요청 위조 — 사용자가 자신의 의지와 무관하게 공격자가 의도한 행동(글쓰기, 정보 수정, 송금 등)을 특정 웹사이트에 요청하게 만드는 공격.

해킹 방식 (은행 예시)
  1. 사용자가 bank.com에 로그인해 세션 쿠키(도장)를 가진 상태
  2. 공격자가 만든 미끼 링크·페이지를 방문
  3. 그 페이지가 몰래 "내 계좌로 100만 원 송금" 요청을 bank.com에 보냄 → 브라우저가 bank.com의 쿠키를 자동으로 붙여 보내므로, 자기도 모르게 정상 요청처럼 처리됨

CSRF 공격의 방어 — CSRF 토큰이라는 비밀 값을 사용해 이러한 공격을 막습니다: "Django가 직접 내려준 페이지에서 보낸 요청인가?"

10-3CSRF Token 적용

DTL의 csrf_token 태그를 사용해 손쉽게 사용자에게 토큰 값을 부여합니다. 요청 시 토큰 값도 함께 서버로 전송될 수 있도록 합니다.

<form action="{% url 'articles:create' %}" method="POST">
  {% csrf_token %}
  ...
</form>
<!-- 렌더링 결과(개발자 도구): -->
<input type="hidden" name="csrfmiddlewaretoken" value="r0d8...ZkY2">
요청 시 CSRF Token을 함께 보내야 하는 이유
  • Django 서버는 해당 요청이 DB에 데이터를 하나 생성하는(DB에 영향을 주는) 요청에 대해 "Django가 직접 제공한 페이지에서 데이터를 작성하고 있는 것인지"에 대한 확인 수단이 필요한 것
  • 겉모습이 똑같은 위조 사이트나 정상적이지 않은 요청에 대한 방어 수단
  • 기존 요청 형태: 요청 데이터 → 게시글 작성 / 변경 요청 형태: 요청 데이터 + CSRF 토큰 → 게시글 작성
"왜 POST일 때만?"
  • POST는 단순 조회를 위한 GET과 달리 특정 리소스에 변경(생성, 수정, 삭제)을 요청하는 의미와 기술적 특성을 지님
  • DB에 조작을 가하는 요청은 반드시 "우리 사이트에서 보낸 요청인지" 확인하는 수단이 필요
  • "GET은 원래 서버 데이터를 바꾸지 않는 요청으로 약속되어 있기 때문에 보호 대상이 아님. 만약 GET으로 데이터를 바꾸도록 만들면 CSRF 보호를 받을 수 없음"

POST 변경 결과 확인 — 요청 URL에 Query String으로 보냈던 데이터가 표기되지 않습니다. 게시글 생성 후 개발자 도구(Network → Payload)에서 Form Data가 전송되는 것을 확인할 수 있습니다.

redirect

작성 성공 페이지 응답의 문제점 · redirect() · 동작 원리

11-1게시글 작성 후 완료를 알리는 페이지를 응답하는 것

현재 서비스는 게시글 작성(POST 요청) 이후, "게시글이 성공적으로 작성되었습니다." 페이지를 직접 반환합니다. 게시글 저장 후 페이지를 응답하는 것은 POST 요청에 대한 적절한 응답이 아닙니다. 이는 후속 행동(예: 새로고침, 뒤로 가기)에서 예상치 않은 동작을 유발할 수 있습니다.

HTTP 표준 관점사용자 경험(UX) 관점
POST 요청은 데이터 생성/변경에 사용되며, 동일 요청이 반복되면 안 됨. 현재 방식에선 사용자가 완료 페이지에서 새로고침 시 중복 게시물 작성의 위험이 있음 (REFRESH → SERVER → DUPLICATE DATA)작성 완료 후 완료 페이지를 보여주는 것은 직관적이지 않고, 사용자가 예상하는 흐름과 다름. 브라우저의 뒤로 가기 동작도 혼란을 줄 수 있음
해결 — 서버는 데이터 저장 후 페이지를 응답하는 것이 아닌 사용자를 적절한 기존 페이지로 보내야 한다. "사용자를 보낸다." = "사용자가 GET 요청을 한번 더 보내도록 해야 한다." 실제로 서버가 클라이언트를 직접 다른 페이지로 보내는 것이 아닌, 클라이언트가 GET 요청을 한번 더 보내도록 응답하는 것입니다.

11-2redirect()

클라이언트가 인자에 작성된 주소로 다시 요청을 보내도록 하는 함수.

# articles/views.py
from django.shortcuts import render, redirect

def create(request):
    title = request.POST.get('title')
    content = request.POST.get('content')
    article = Article(title=title, content=content)
    article.save()
    return redirect('articles:detail', article.pk)

create.html 템플릿은 더 이상 필요 없으므로 삭제합니다.

https://docs.djangoproject.com/en/5.2/topics/http/shortcuts/#redirect

  1. [POST] 게시글 작성 요청 (+ 입력 데이터) → create view 함수 호출 → 게시글 작성
  2. 응답: redirect (detail 주소로 요청을 보내라) — status 302 Found
  3. [GET] 브라우저가 detail 페이지를 다시 요청 → detail view 함수 호출
  4. detail 페이지 응답 → 결국 사용자는 게시글 작성 후 작성된 게시글의 detail 페이지로 이동하는 것으로 느끼게 됨

개발자 도구 Network 탭에서 create 요청(302) 이후 detail 요청(200)이 이어지는 것을 확인할 수 있습니다.

def edit(request, pk):

    }

  • input 요소 — 한 줄 텍스트(예: 제목). value 속성으로 기존 데이터 입력

12-4update — 기능 구현

# articles/urls.py
path('<int:pk>/update/', views.update, name='update'),

# articles/views.py
def update(request, pk):
    article = Article.objects.get(pk=pk)
    article.title = request.POST.get('title')
    article.content = request.POST.get('content')

    return redirect('articles:detail', article.pk)

13-1GET & POST 비교

사용 목적데이터 검색 및 조회데이터 제출 및 변경

13-2GET 요청이 필요한 이유

  1. 캐싱 및 성능 — GET 요청은 캐시(Cache)될 수 있고, 이전에 요청한 정보를 새로 요청하지 않고 사용할 수 있음. 특히, 동일한 검색 결과를 여러 번 요청하는 경우 GET 요청은 캐시를 활용하여 더 빠르게 응답
  2. 가시성 및 공유 — GET 요청은 URL에 데이터가 노출되어 사용자가 해당 URL을 북마크하거나 다른 사람과 공유하기 용이
  3. RESTful API 설계 — HTTP 메서드의 의미에 따라 동작하도록 디자인된 API의 일관성을 유지할 수 있음

13-3HTTP request methods를 활용한 효율적인 URL 구성

  • 동일한 URL 한 개로 method에 따라 서버에 요구하는 행동을 다르게 요구
  • HTTP Methods를 통해 웹 서버와 클라이언트 간의 통신에서 '내가 무엇을 할지'를 명시적으로 표현
  • URL이 같아도 사용되는 메서드(GET, POST 등)에 따라 서버의 동작이 달라짐
요청의미
(GET) articles/1/1번 게시글 조회 요청
(POST) articles/1/1번 게시글 조작 요청

실제 활용 예시: TMDB API 가이드 문서 — 같은 리소스 주소에 GET(조회), POST(추가), DELETE(삭제)가 나뉘어 있음. Django 후반기 RESTful API 시간에 자세히 다룰 예정입니다.

13-4캐시 (Cache)

데이터나 정보를 임시로 저장하여, 다시 요청할 때 빠르게 제공하는 저장 공간.

  • 빠른 응답 시간 — 이미 저장된 데이터를 즉시 제공하여 사용자 경험 향상
  • 서버 부하 감소 — 반복적인 데이터 요청을 줄여 서버 자원 절약

  1. 조건에 맞는 모든 레코드를 QuerySet으로 반환한다
  2. 조건과 일치하는 단 하나의 객체를 반환하며, 없으면 DoesNotExist 예외를 발생시킨다
  3. 항상 새로운 객체를 생성하고 저장한다
  4. 조건이 여러 개여도 예외 없이 첫 번째 객체만 반환한다
정답 · 해설 보기
b) — get()은 단일 객체 조회 전용이며, 결과가 없거나 2개 이상이면 예외를 발생시킨다.
